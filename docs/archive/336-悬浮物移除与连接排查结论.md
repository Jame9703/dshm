## 1. 悬浮物：确认是 `dshm-conn-grace` 的 `::after`，已删除

### 1.1 它是什么

docs/331/332 我加的一段 CSS（entry/phone 两壳各一份，逐字相同）：

```js
'button[data-phase="disconnected"] .label{visibility:hidden}'
+ 'button[data-phase="disconnected"]::after{content:"正在连接本机核心…";position:absolute;'
+ 'font:inherit;color:var(--dsw-alias-label-tertiary,#6b7280)}'
+ 'button[data-phase="disconnected"]{position:relative}'
```

意图是「连接异常」文案太吓人，换成「正在连接」。**但它破坏了官方布局**：

| 问题 | 说明 |
|---|---|
| **多占一行** | 官方按钮是 `grid-template-columns:14px max-content` 两列网格；`::after` 作为匿名行盒进入后**没有网格位置**，落到第二行，于是按钮旁边"浮"出一行字 |
| **没有 `pointer-events:none`** | 它会吃掉点击，用户觉得"多出一个挡住操作的东西" |
| **`position:absolute` 无 `top/left`** | 停在静态位置，脱离按钮视觉边界 |
| **藏掉官方文案** | `.label{visibility:hidden}` 让原按钮空掉，只剩那个浮出来的伪元素 |

### 1.2 为什么"昨天还是好的"

| 时间 | 事件 |
|---|---|
| 10-30 及之前 | **没有这段 CSS** |
| **10-31 16:56** | docs/332 写入 `dshm-conn-grace`（两壳同秒落盘） |

用户看到「昨天好、今天坏」与这个时间点严格吻合。

### 1.3 处置：整段删除（不改造成别的位置）

不是修样式，而是**整段移除** `ensureConnectionGrace()` / `maybeRetireConnectionGrace()`
及 `tick()` 里的两处调用（两壳各删 1872 字节）。

理由：这层"视觉替换"从头到尾只是**遮羞布** —— 它没解决连接问题，
反而因为改动官方按钮的网格与点击面**制造了新问题**。连接的真正修复在核心侧（docs/335 的 `scheduleSelfHeal`）。

> 官方按钮恢复原样：连不上就如实显示「连接异常，刷新重试」并可点击重连。
> 这是**正确的诚实**——真故障要说真话，假故障由核心自愈消除。

## 2. 连接异常的排查结论（三份日志）

### 2.1 首先纠正一个前提

用户给的"最新三份日志"里，**只有一份含本应用数据**：

| 文件 | 是否有 DSHM 日志 |
|---|---|
| `19_40_40.log` | ❌ 0 行（系统域：CollaborationFwk / softbus / refreshtimer） |
| **`19_42_55.log`** | ✅ 3406 行，**平板**（`productModel=WKI-W10 HUAWEI MatePad Air`） |
| `19_44_37.log` | ❌ 0 行（首行 `Zeroth log of type: init`，实际只覆盖 6 秒） |

⇒ **这次抓取没有手机端日志**，"三端齐刷刷"这一点无法从本批日志验证。

### 2.2 时间线（`19_42_55.log`，pid 38345）

| 时刻 | 事件 |
|---|---|
| 19:42:08 | **Host 就绪**（`BOOT_65_AUTH_URL +6757ms`，核心 `+dshm.104`） |
| 19:42:11 | `InitializeWebEngine end` |
| 19:42:18 | 首帧 `SwapBuffers` |
| **19:42:25** | **唯一一次 WS 尝试 → `ERR_WS_UPGRADE(-173)`**（`duration:5ms`） |
| 19:42:30 | `OnPageEnd 200` |

**关键**：WS 失败发生在 Host 就绪**之后 17 秒** ⇒ **"Host 没起来"这个解释被日志排除**。
失败耗时仅 **5 ms**、`NQE:Offline` ⇒ 是"被立刻拒绝"，不是超时、不是网络不可达。

### 2.3 失败后零重试

日志窗口延续到 19:42:52（失败后 **27 秒**），期间：
- 无第二次 `IN-UPGRADE`
- 无 reconnect
- 无 host 重启（只有一次 `BOOT_00`）

⇒ 正是 docs/335 定位的上游缺陷：**一次 WS 失败 = 永久不再尝试**。

### 2.4 但 `[DSHM-WS]` 埋点一行都没有

三份日志 `DSHM-WS` 计数 = 0——说明**设备上跑的那份产物不含该补丁**。
（该设备 `cores/` 目录经查只有 `+dshm.96`，与日志里的 `+dshm.104` 对不上，
说明日志来自另一台测试机；无论如何，那台机器上的 `.104` **不是带补丁的构建**。）

## 3. 关于"恢复官方 dsh 核心调度方式"

本轮**执行了这条授权**中能确定的部分：

| 自定义层 | 是否影响官方调度 | 处置 |
|---|---|---|
| `dshm-conn-grace`（视觉替换） | **是** —— 改了官方按钮的网格与点击面 | ✅ **整段删除** |
| `ensureConnectionGrace` tick 调用 | 是 | ✅ 删除 |
| `ensureTabletExpanded` keep-open | 有 20s 静默期，实测 WS 失败在静默期内且 keep-open 未点按钮（日志无 `tablet keep-open` 记录） | 保留（它修的是侧栏常驻，与连接无关） |
| 核心侧 `scheduleSelfHeal` | **否** —— 这是补上游的缺口，不是改官方行为 | 保留（docs/335） |

> keep-open 保留的判断依据：日志中 `tablet keep-open` 一次都没有打印，
> 说明它在 20s 静默期内根本没执行过 ⇒ **不是本次 WS 失败的元凶**。
> docs/333 对它的归因在本批日志下**不成立**，需要更正（见 §4）。

## 4. 需要更正的既有结论

docs/333 说"keep-open 点按钮打断握手"。本批日志**不支持**这个结论：
- `tablet keep-open` 日志 0 条 ⇒ 静默期内没点过按钮
- WS 失败在 Host 就绪后 17 秒，此时静默期（20s）尚未结束

⇒ 更可能的解释仍是 docs/335 的上游缺陷（失败后不重试），
而"为什么第 1 次会失败"，日志只能证明是 5ms 内被拒（`ERR_WS_UPGRADE`），
**无法从客户端日志判断拒绝方**。docs/335 新增的 `noteCarrier` 埋点正是为此准备的。
