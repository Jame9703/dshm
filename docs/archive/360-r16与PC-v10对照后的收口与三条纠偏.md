## 0. 三条纠偏（先看，避免再按错的口径查）

### ① 上一条给用户的验收命令是错的（我的问题）

用户在 zsh 里贴了：

```zsh
for f in node npm npx pnpm dsh; do printf '%-5s %s\n' "$f" "$(wc -c < bin/$f)"; done   # 五个都应 52120
cat files/diag-glass
```

实际结果：`parse error near '#'`，随后 `bin/node: no such file` 等。两个原因**都在我**：

1. `bin/`、`files/` 是**应用沙箱内**的相对路径，用户 cwd 是工作区
   `~/data/test`，那里没有它们；
2. zsh 交互模式把行尾 `# …` 当语法，直接 `parse error`。

**替代**：本轮新增 `tools/dshm-verify.mjs`，全部用**绝对路径**、无注释、可 JSON：

```sh
node tools/dshm-verify.mjs          # PASS/FAIL + 每个文件的绝对路径
node tools/dshm-verify.mjs --json
```

实测输出会直接告诉你"启动器是不是 ELF、toolchain 哪一项为空、diag-glass 有没有写"。

### ② r16「RUNPATH 仍指向 el1」是**误读**

r16 用 `strings` 在二进制里搜到 `/data/storage/el1/bundle/libs/arm64`，就判成 RUNPATH。
那条字符串是 **nodecli 源码里的 libnode 候选路径**（`nodecli.c` 的 `relative[]` 数组），
不是动态段。用 `llvm-readelf -d` 复核（1010010 起的产物）：

```text
Dynamic section ...
  NEEDED  libc++_shared.so
  NEEDED  libc.so
  （没有 RUNPATH / RPATH 行）
```

### ③ `$ORIGIN` 在本机加载器上**不生效**（r16 P0 建议不可行）

用同一套工具链做了对照实验：自建 `libfoo.so` + `use` 链接
`-Wl,-rpath,'$ORIGIN'`，把两者放同一目录运行：

```text
$ readelf -d use | grep RUNPATH
  RUNPATH  [$ORIGIN]
$ ./use
Error loading shared library libfoo.so: (needed by …/use)
```

⇒ 这条加载器**不解析 `$ORIGIN`**。所以"把 RUNPATH 改成 `$ORIGIN`"解决不了 r16 的报错，
只会把失败从"找不到 libc++"换成"找不到 libc++"（同样的错，换了理由）。

**更重要的口径**：`bin/{node,dsh,pnpm,…}` 是**宿主侧**入口（Host 的 PATH），
**不是 guest 工具**。guest 里有自己的 node v22 / git / tmux；guest 里跑宿主 ELF 会同时缺：
`/system` 库、`libnode`（el1 在 guest 不可见）、musl `libc++`。r16 把"guest 里跑不了宿主
launcher"当成缺陷，其实是跨层误用。宿主侧（PC）已实测 5/5 ELF、四个版本命令真实可用
（PC v10 报告）。

## 4. 仍未落实的两项（给出下一步，不假装完成）

1. **qemu-ga 空转**：需要 guest 内证据（`ps | grep qemu-ga`、两次 `/proc/<pid>/stat` 差、
   `/var/log/qemu-ga.log` 尾部）。拿到后有三种处置：改 qemu-ga 启动参数、限制其日志/轮询、

   包，进 `guestpkgs/` 并更新 `place-vm-assets.mjs` 的 `GUEST_PKG_FILES` 与指纹；属换资产，
   要一次全量 guest 复测。
