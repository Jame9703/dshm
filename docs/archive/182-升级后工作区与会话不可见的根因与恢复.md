# 182 · 升级后工作区与会话不可见的根因与恢复

> 2026-10-17。场外反馈：部分用户从 `1.1.2` 升级到 `1.1.3` 后，工作区和会话记录
> 像是丢失了。本文只基于实际代码、格式与真机数据链路判断，不把安装来源问题混进
> 核心数据迁移问题。

## 1. 先排除的项

| 项 | 1.1.2 | 1.1.3 | 结论 |
|---|---|---|---|
| 用户数据根 | `<filesDir>/dsh/home` | 同左 | 未变 |
| Session 格式 | v4 | v4 | 未变 |
| `workspace` domain | version 2 | version 2 | 未变 |
| JSON storage 后端 | 同一实现 | 同一实现 | 未变 |
| 核心清理 | 只清 `dsh/cores/*` | 同左 | 不碰 `home/` |
| 包内 session/workspace 数据 | `home/sessions`、`home/storages/workspace.json` | 同左 | 不会被核心安装器移动 |

因此，“新版本核心把旧会话目录删掉”不成立：核心安装器没有删除 `dsh/home` 的路径，
会话格式也没有发生 v4 升级。

## 2. 命中的实际缺陷：授权恢复与工作区索引存在竞态

1. `EntryAbility.onCreate` 调 `restoreFolderGrants()` 时**没有等待它完成**；
2. `scheduleHostStartAfterFirstFrame()` 在首帧后只延迟 400 ms 就启动 Host；
3. 用户自选目录在 `activatePermission()` 完成前会返回 `EPERM`，不是 `ENOENT`；
4. `dsh-workspace` 在 Host 启动时对 session header 的 `cwd` 做 `realpath`：
   - `ENOENT` 被 alpha.4 暂时当作 missing；
   - `EPERM` 仍进入 invalid，工作区的 `sessionIds` 会被过滤；
5. 若随后发生一次工作区 `mutate()`，过滤后的空成员会被写回注册表；之后即使授权恢复，
   当前 Host 进程也不会重建成员关系，界面就表现为“工作区还在但会话没了”，
   或默认工作区行被撤回后整体不可见。

这解释了为什么只有**部分用户**遇到：只有使用 picker 目录、且授权恢复慢于 Host
启动的用户命中；沙箱内工作区不依赖这份临时授权，不会复现。

## 3. 修复

### 3.1 Host 启动前必须等授权恢复

`EntryAbility` 新增 `folderGrantsReady`：

- 首帧仍先画，不阻塞 UI；
- `scheduleHostStartAfterFirstFrame()` 在实际调用 `autoStartHostForDiagnosis()` 前
  `await this.folderGrantsReady`；
- 恢复失败只降级记录，Host 仍会启动，不会因授权服务异常把 App 卡死。

### 3.2 已有工作区成员从会话 header 非破坏性补回

`dshm-workspace-claim` 增加一次只读扫描：

- 读 `sessionPersistence.list()` 的 header；
- 对每个未被任何工作区计入的会话，按 `realpath(header.cwd)` 匹配**已经存在**的同路径工作区；
- 调官方 `workspace.attachSession(id)` 补回成员；
- 不创建新工作区、不删除工作区、不碰会话日志；
- cwd 当前不可解析时跳过，不猜。

这条修复能恢复“工作区行还在，但 sessionIds 已被剪掉”的情况。若连工作区行本身都被
删除，会话日志仍不会消失，但本插件刻意不自动复活已删除的工作区；需要用户重新添加
该目录，或后续做显式恢复入口。

## 4. 门禁

- `check-feature-wiring.mjs`：要求 `folderGrantsReady` 赋值并在 Host 启动前 await；
- `check-workspace-claim.mjs`：新增 5 条行为断言：
  - 缺成员从同路径 header 补回；
  - 已计入不重复；
  - 不同路径不硬塞；
  - 没有匹配工作区不新建；
  - cwd 不可解析时跳过；
- 原有“绝不 create”对照臂继续保留。
