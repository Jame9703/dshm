### 1.1 `evictFilePages` 的精确契约（对 P0-A 关键）

```ts
function evictFilePages(fileNames: Array<string>): Promise<void>;
// @throws 16000163 - File type error. 文件名不以 .so / .hap / .hsp 结尾
// @stagemodelonly  @syscap SystemCapability.Ability.AbilityRuntime.Core  @since 26.0.0

function evictModuleFilePages(moduleNames: Array<string>): Promise<void>;
// 读 {Module}/src/main/resources/rawfile/memory_optimizer.json 里的 evictFilePages 数组
// @throws 16000163 文件类型错；16000164 配置文件解析失败
```

**两个关键事实（190 没写全）**：

1. **系统不保证真释放**——"The system determines whether to actually perform the release based on the
   current memory status, and success is not guaranteed." ⇒ **验收不能用"内存降了多少"判**，
   只能判"调用发出的时机对不对 + 有没有报错"。
2. **有模块清单模式**（`evictModuleFilePages`）：可以放一个 `rawfile/memory_optimizer.json`
   声明要清的文件，**不用在代码里硬编码路径**——这比 190 提的"用当前 HAP 内已加载清单"更干净。

## 2. 当前可做的阶段

### 阶段 A：P0-A 文件页缓存释放（**建议现在做**）

| 项 | 内容 |
|---|---|
| 为什么现在做 | 零权限、API 已核实、与 `docs/291` 的"VmSwap 184 MB 有内存压力"直接相关 |
| 落点 | 新增 `platform/src/main/ets/system/MemoryTrim.ets`（**不放 entry**，与其它平台能力同层） |
| 判据 | `canIUse('SystemCapability.Ability.AbilityRuntime.Core')` + `deviceInfo.sdkApiVersion >= 26`；任一不满足 ⇒ 整条静默返回 |
| 触发点 | ① `onBackground()`（已有 `onMemoryLevel` 钩子，见 `entry/…/EntryAbility.ets:1150`）② `onMemoryLevel(CRITICAL)` ③ **手持 VM 冷启动前**（`docs/205` 内存风暴的同类场景） |
| 参数来源 | **优先用 `evictModuleFilePages([...])` + `rawfile/memory_optimizer.json`**（不硬编码路径）；文件列表只放 `.so/.hsp/.hap` |
| 禁止 | 不在前台活跃期调用（重载抖动）；不对任意路径调用（`16000163`）；失败只落 diag 不阻断 |
| 验收 | `diag-memtrim` 每次一行（时间/触发点/模块/成功失败）；API 23 设备上不报错、功能照常；`check-permission-surface` 仍 17/9 |
| 工作量 | **0.5 d**（与 190 一致） |

**建议同时补的门禁**：`tools/check-memory-trim.mjs` ——
判据：① `canIUse` + `sdkApiVersion` 双守卫在位；② 只在三处触发点被调用；③ 参数只来自
`memory_optimizer.json`（代码里无裸路径）；④ 失败路径不抛。带 2 个变异体。

## 3. 与 `docs/291` 的关联（为什么 P0-A 值得优先）

`docs/291 §3.4` 的真机读数：

```text
VmRSS 613 MB / VmHWM 805 MB / RssFile 216 MB / VmSwap 184 MB
系统 MemAvailable 3.8 GB（充裕）但宿主自身 swap 了 184 MB
```

`RssFile` 216 MB 是**文件页映射**（随包 `.so` + 核心树 js）——正是 `evictFilePages` 的目标面。
系统内存充裕时它未必真释放（API 明说"不保证"），但**在 `onMemoryLevel(CRITICAL)` 与手持 VM
启动前**调用，是这套 API 唯一正确的用法，且零成本试错。
