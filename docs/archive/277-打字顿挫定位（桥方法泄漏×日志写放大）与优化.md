## 1. 定位过程（每一步都是实测，不是猜）

| # | 观察 | 数据 | 结论 |
|---|---|---|---|
| 1 | 系统内存总况 | `MemAvailable 12.5 GiB`（24 GiB 机） | 表面不缺内存 |
| 2 | 但系统到过**内存危急档** | `diag-mem-critical`：10-29 10:46 本地 `onMemoryLevel=critical`（同款 10-26/10-28 还有 2 次） | 卡的时段**系统确实紧张过** |
| 3 | `diag-mem` 24h 画像（9760 样本） | P5=3.2G / P10=3.5G / P50=5.2G；**17% 时间低于 4 GiB**；最低 1.6 GiB | "可用内存"长尾很差——够解释间歇卡顿 |
| 4 | 宿主自身内存 | rss 425–615 MiB（`diag-mem` 全程），缓慢爬升 | **不是**主因（DSHM host 只占 ~0.6G） |
| 5 | 调度抖动实测（30s，100ms/拍） | 中位 100.1ms，**0 次 >150ms 跳变** | 我这侧（bash 子进程）**没有**抖动 ⇒ "顿挫"在**前台 UI 线程**，不在宿主 |
| 6 | `node-output.log` 全链体量 | **263 MiB**（4 档：29+4.7+9.4+233） | 持续文件写放大 |
| 7 | 该日志的构成 | `native proxy object not found, name:__DSHM_BRIDGES__` 全链 **124,648 次**，占日志行约 **60%**；每次报错伴随 **5 行** OhGin 调度日志 | 一个桥调用泄漏制造了大半日志 |
| 8 | 报错频率实测 | 90 秒内 93 次 ⇒ **约 3720 次/小时**，与 300ms tick（3 拍 1 次）吻合 | **常驻轮询**在调一个不存在的方法 |
| 9 | 溯源 | 侧栏垫片 `applyHandheld()` 每拍调 `b.platformPcMode()`；**entry 的 `methodList` 漏了 `platformPcMode`**（phone 的有，对照 phone:5540 ⇒ 迁移遗漏） | **根因坐实** |

**因果链**：`methodList` 漏登记 → 原生侧不给该方法注册代理 → 页面 300ms 轮询调用 → ArkWeb 每次打 6 行错误日志 → 3720 行/小时持续写盘 + OhGin 权限检查的 CPU 开销 → 长期运行后 UI 侧可感知的顿挫 + 日志膨胀。

> 说明：内存压力（§2）与本泄漏是**叠加**关系，不是同一件事。泄漏是 DSHM 自己的缺陷（已修）；内存压力里有系统其它进程的份额。

## 2. 根因与修复

### 2.1 已修：`platformPcMode` 未登记（entry 模块）

`entry/src/main/ets/pages/WebApp.ets` 的 `methodList` 补上 `'platformPcMode'`。桥对象本体一直有定义
（`,'platformPcMode': (): boolean => this.pcMode === true`），只是名单漏了——修的是一行字符串。

**修复效果预期**（需重启应用后生效）：
- 每小时少写 **~2.2 万行**错误日志（3720 次调用 × 6 行）；
- 少 3720 次/小时的 ArkWeb 代理查找 + 权限检查路径；
- `node-output.log` 增速从 ~6KB/min 降到接近静默。

### 2.2 新门禁：`tools/check-bridge-methodlist.mjs`

这类错**不报编译错、不崩**，只有性能慢慢劣化——静态钉住：
- 判据：垫片**调用**的桥方法 ⊆ `methodList` **登记** ⊆ bridges **定义**（entry + phone 双模块）；
- 自检臂：删掉 methodList 里一个名字必须判红（实测判红 ✓）。
- 跑法：`node tools/check-bridge-methodlist.mjs [--self-test]`。

### 2.3 已做：旧日志清理（应用运行中，不动当前档）

- 清掉 `node-output.log.1/.2/.3`（**247 MiB**；当前档是运行中进程的 stdout，删了会写进已 unlink 的 inode，**保留**）；
- `diag-mem` 561KB → 11.5KB（保留最近 200 行采样能力）。

## 3. 内存压力画像（系统层，非 DSHM 单方面）

- 24 GiB 机，`onMemoryLevel=critical` 三天内 **3 次**（10-26、10-28、10-29 各一）；
- P5 可用内存 3.2 GiB，17% 时间低于 4 GiB —— **长尾紧张**；
- swap 几乎没动（in/out 增量≈0 in 15s）⇒ 顿挫不是 swap 抖动，更像**回收停摆的瞬时**；
- DSHM host 稳定在 0.6 GiB 量级，**不是大头**；大头在系统其它进程（我这边 pid namespace 受限，无法枚举归属，如实说明）。

## 6. 方案 A 落地（2026-10-29 12:20，用户拍板"A 吧"）

### 6.1 实现（entry + phone 两模块、四个轮询垫片全接）

| 垫片 | 原频 | hidden 行为 | visible 恢复 |
|---|---|---|---|
| SIDEBAR（300ms） | 300ms | **降频 1500ms**（保底：React 重建后的侧栏自愈链仍活着） | 恢复 300ms + **当拍补跑** |
| SETTINGS（300ms） | 300ms | **停摆**（本有 phone() 闸门，可见时才有意义） | 恢复 + 当拍补跑 |
| ONBOARDING（300ms） | 300ms | **停摆** | 同上 |
| HANDHELD_GRID（500ms） | 500ms | **停摆**（scan 本有 SCAN_EVERY 节流） | 同上 |

- 用标准 `visibilitychange` 事件（垫片是纯 JS，ArkWeb 支持；比轮询时间戳准且零成本）；
- 初始化读一次 `document.visibilityState` 作初值（注入时页面可能已 hidden）；
- 无 TDZ 风险（插入块顶层只注册回调，不立即调 tick）；
- 两模块共 **8 处** `visibilitychange` 监听、各自 `armTick`/`*TickTimer`；
- 裸启动行已清（避免与节流器双跑）。

### 6.2 门禁（`check-bridge-methodlist.mjs` 追加判据）

- 每模块 `visibilitychange` 监听 **≥4 处**；
- 必须有 `TICK_BG_MS`（SIDEBAR 的 300→1500 降频常量）。
- entry + phone 双模块同判。

### 6.3 预期收益（后台/失焦时）

- DOM 扫描 + 桥调用从**每秒 200+ 次**降到：SIDEBAR 1 次/1.5s，其余**归零**；
- 叠加 §2.1 的桥修复（`platformPcMode` 进 methodList），后台的持续写放大与代理查找双双归零。
