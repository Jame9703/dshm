## 1. 分三类：同步 / 不同步 / 待你定

### ✅ A 类：**必须同步**（用户真正的价值）

| 项 | 体积 | 理由 |
|---|---:|---|
| **`sessions/`** 整个会话树 | 15.1 MB | 对话记录 = 用户最不可再生的资产。换设备最想带走的就是它 |
| ├ 会话代际文件 `.jsonl.zstd` | — | 上游不可变格式，一个代际 = 一个同步单元 |
| ├ 会话目录里的其它元数据 | — | 与代际同目录，一起走 |
| **`workspace.json`** | ~0 | 工作区索引。**但 cwd 绝对路径跨端不同**，见 §2 |

### ❌ B 类：**绝不同步**（可重建 / 敏感 / 平台专属）

| 项 | 体积 | 为什么不能同步 |
|---|---:|---|
| **`profiles/ondevice`** | **143 MB** | 核心树 + 依赖。**每端按架构重建**，传输纯属浪费；且写进别人设备会破坏其运行环境 |
| **`storages/session_projcache`** | 5.6 MB | 投影缓存，**可从会话重建** |
| **`.credentials.yaml`** | ~0 | **凭据**。上传 = 把密钥交给云端，绝不允许 |
| `card-usage.jsonl` / `card-state.json` | <0.2 MB | 本机 UI 状态（桌面卡片），跨端无意义 |
| `host-ready.json` / `app-lifecycle.json` | ~0 | 本机运行时状态 |
| `.anonymous-user-id` | ~0 | 本机设备标识，同步会污染 |
| `open-link/` / `.xdpool/` / `install-queue/` | ~0 | 临时队列 |

### 🟡 C 类：**需要你拍板**（有理由同步，也有理由不同步）

## 2. 一个必须先解决的语义问题：**工作区路径跨端不同**

会话按 **cwd 绝对路径**分组：

```text
PC  端: --storage-Users-currentUser-data-DSHM-deveco-workspace--
手机端: 路径完全不同
另一台PC: 用户名可能不同
```

**如果原样同步目录名，跨端会得到一堆"打不开的孤儿会话"。**

### 三个方案

| 方案 | 做法 | 代价 |
|---|---|---|
| **① workspaceId 抽象** | 云端存 `workspaceId`（稳定 ID），端侧维护 `workspaceId ↔ 本机 cwd` 映射表 | 要建映射表，**首次同步需用户确认一次** |
| **② 按目录名匹配** | 末段目录名相同就当同一工作区 | 省事，但同名不同项目会**串数据** |
| **③ 原样保留路径** | 云端存原路径 | 跨端恢复到原路径，**路径不存在就废了** |

**我建议 ①**（docs/301 里也预留了它：`ManifestSession.projectKey` 与 `relativePathOf`）。
代价是**首次同步弹一次"云端工作区 X ↔ 本机工作区 Y"的确认**。

## 3. 关于 `cost-meter`（13 MB）：一个折中

它 13 MB 但只是用量统计。三个选择：

| 选择 | 说明 |
|---|---|
| **A. 全同步** | 简单，但每次传 13 MB（虽然有增量） |
| **B. 不同步** | 省流量，但换设备后用量从零开始 |
| **C. 只同步"汇总"** | 把 `cost-meter` 聚合成本端无关的日统计再同步（几十 KB） |

**我建议 B（暂不同步）**：用量统计本来就是"这台设备花了多少"，跨端合并语义不清。
真要做，等有了明确需求再上 C。

## 4. 同步的粒度：一条记录 = 什么？

统一口径（沿用 `docs/307` 的 Asset 架构）：

```text
一个同步单元（unit）= 一个**不可变**的实体
├─ 会话代际文件      → <workspaceId>/<sessionId>/<version>
├─ 附件文件          → attachments/<hash>
├─ 技能文件          → skills/<name>
└─ 工作区索引        → workspace.json（单条，可覆盖）
```

**为什么按"不可变单元"切**：写入一次即定稿 → 端云同步天然增量，不会反复改同一行。

## 6. 按我的建议，同步范围就是

```text
总计约 18 MB（首次），之后只传变化
├─ sessions/        15.1 MB   ← 核心
├─ attachments/      2.7 MB
├─ skills/           0.02 MB
└─ workspace.json    ~0        ← 需配映射表

不同步：profiles(143MB) / projcache(5.6MB) / cost-meter(13MB)
        / covers(4.1MB) / 凭据 / 本机状态
```

**这个口径下，首次全量约 18 MB，之后增量通常只有几百 KB。**

## 7. 一句话交接

实测 183.9 MB 里 **143 MB 是不可同步的核心树**，
用户真正不可再生的数据是 **会话 15 MB**。
建议同步 `sessions` + `attachments` + `skills` + `workspace.json`（约 18 MB），
**不同步** `profiles` / `projcache` / `cost-meter` / `covers` / 凭据。
**最需要你决定的是工作区映射方案**（我建议 workspaceId + 首次确认）。
