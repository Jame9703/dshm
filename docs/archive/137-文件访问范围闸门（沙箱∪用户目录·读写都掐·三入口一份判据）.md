## 1. 需求拆解与裁定

| # | 用户的话 | 落实 |
|---|---|---|
| ① | 「沙箱内不变」 | 应用自身沙箱照旧全可读写 —— 允许面**包含**它，判据对它恒真 |
| ② | 「`~/` 下全域可读写」 | 用户家目录整棵进允许面（**读与写都放**，不区分目录） |
| ③ | 「不碰系统数据区，读写都掐死」 | 面外一律拒 —— 注意是**读也拒**：上游工具本来能读 `/etc`、`/system` |
| ④ | 「三端同步」 | 判据落在一份随包代码里，与设备形态无关（PC / 手机 / 平板同一份） |

**为什么用白名单而不是黑名单**：系统面是一个**开放集合** —— 新分区、新挂载点、别的应用的沙箱、
以后新增的 `/xxx` 都算。黑名单必然漏一项，而漏掉的那一项就是「能读系统数据」。
白名单的代价是「新加一个合法位置要改一行」，这是可接受的方向。

**为什么不接 approval（先问一句再放行）**：用户要的是**范围**，不是**逐次确认**。
仓库里已经有四档权限预设 + `sandbox_permissions` 那套越权审批（`docs/126` §4.2 逐条对过）。
本闸门是**静态边界**：能碰的、不能碰的，在写代码时就定了，不需要模型/用户每次拍板。

## 2. 缺口：上游**没有读闸门**

端侧 fs 后端是 `dshm-fs-write-nonchmod`（`SandboxedFileSystem` 的写入替换版）。
上游 `@deepseek-ai/dsh-fs-sandbox` 的头注**逐字**写着：

```
* Reads pass through untouched: every mode permits reading
```

并且 `checkedTarget()` 在 `danger-full-access` 下**直接返回调用方的 target**（连写闸门也不做），
而端侧 profile（`hostcore/profile/ondevice/cordis.patch.yml`）的 `sandbox-policy` 正是
`danger-full-access` ⇒ **工具层对「能碰哪里」没有任何边界**：应用身份可以列 `/etc`、
读 `/system/...`，也能往用户目录之外写。

⇒ 这一层是本端**补**出来的边界。路径语义（归一化、realpath 身份、per-target 锁、版本守卫）
仍**逐字继承上游** —— 本闸门只加一个「先判一次」的前置条件。

## 4. 实现：三个入口，一份判据

判据的**唯一真源**是 `hostcore/plugins/dshm-fs-write-nonchmod/lib/fs-fence.js`，
`dshm-tool-fs-remove/lib/fs-fence.js` 是它的**逐字节副本**（`Get-FileHash` 实测相同；
`tools/check-fs-fence.mjs` 的 A 段钉住这件事）。

### 4.1 判据为什么是「纯字符串块」

`fs-fence.js` 里 `/* ==== DSHM-FS-SCOPE-BEGIN ==== */` … `/* ==== DSHM-FS-SCOPE-END ==== */`
之间那一段**不含 import / export、不碰文件系统、只用 JS 内建**：
`tools/pack-core.mjs` 要把它**原样**嵌进核心树的 `dsh-tool-fs-search/lib/index.js`
（那个文件在某段代码的中间，既不能加 import，也拿不到 `fs` 标识符）。

于是「三个入口一份判据」是**结构上的事实**，不是靠人工同步：

```
                          hostcore/plugins/dshm-fs-write-nonchmod/lib/fs-fence.js
                                 │  (BEGIN/END 之间那一段)
      ┌──────────────────────────┼───────────────────────────┐
      ▼                          ▼                           ▼
  入口① ctx.fs 后端          入口② publish 目标          入口③ glob / grep 搜索根
  (本包 lib/index.js)        (dshm-tool-fs-remove)       (pack-core 注入树里的
                                                          dsh-tool-fs-search)
```

### 4.2 入口① `ctx.fs` 后端（`dshm-fs-write-nonchmod`）

`resolve` / `stat` / `lstat` / `readText` / `streamText` / `readBytes` / `readByteRange` / `listDir` / `watch`
九个**只读**方法，加 `writeText` / `editText` 两个写方法，**动手之前**先判一次：

- 大多数方法判 `target.targetKey` —— 那是 `resolve()` 用「最深已存在祖先 realpath + 缺失尾巴词法回接」
  算出来的**真实身份**，所以「允许面**内**的软链指向面**外**」在这里被挡住，且**零额外系统调用**；
- `lstat()` 收的是**模型原始路径**（可能尚不存在），用会 realpath 的 `assertFsScope()`；
- 写方法的判据插在 `checkedTarget()` **之后、进临界区之前**（与上游「先算 target 再进临界区」同一时机，
  不会出现 check-here-write-there）。

**副产品**：`remove` / `move` 的**源**与 `publish` 的**源**都要经 `ctx.fs.resolve()` ⇒ 它们**免费**被覆盖，
不在 `dshm-tool-fs-remove` 里重复判。

### 4.3 入口② `publish` 的**目标**

`publish` 的目标是 `dshm-tool-fs-remove` **自己**用 `node:fs` 落盘的（不过 `ctx.fs`）⇒ 那一处必须显式调
`assertFsScope(destination)`；位置在 `publishDestination(...)` **之后**、`writeFileAtomicBytes(...)` **之前**
（三处顺序由门禁钉住 —— 顺序错了会出现「先落盘再拒绝」）。

### 4.4 入口③ `glob` / `grep` 的**搜索根**

`dsh-tool-fs-search` **不过 `ctx.fs`**（它 spawn 随包 ripgrep，搜索根直接进 argv）⇒ 在把根交给 spawn 之前
再判一次。注入的是「`refuseOutOfScopeSearch()` 薄壳 + 从 `fs-fence.js` 原样搬来的判据块」：

- 相对路径按 `ctx.workingDirectory.ensure(exec.agent, exec.signal)` 折成绝对路径；
- 越界抛 `SearchError`（**同一工具错误面**，不会变成「工具内部异常」）；
- 两处 `execute` 的注入点都在 `runRipgrep(...)` **之前**（`assert-fs-search-fallback` 的 A2 段钉住）。

### 4.5 允许面是怎么算出来的（`scopeRoots(env)`）

| 来源 | 值 | 为什么 |
|---|---|---|
| 常量 | `/data/storage/el1/base`、`/data/storage/el2/base` | 应用自身数据的两个根（真机实测都在） |
| 常量 | `~` | 用户家目录（用户明确要的那一棵） |
| env | `DSHM_SANDBOX_HOME` / `HOME` / `TMPDIR` 推出的**应用数据根** + `el1`/`el2` 孪生 | 换设备/换包名时不必改代码（按 `/haps/` 或最末 `base` 段切） |
| env | `DSHM_PUBLIC_DOWNLOAD` | **已认领的工作区** —— 万一被放到家目录之外（换卷/换目录），工作区**必须**仍可用 |

两个细节：

- **`import { dirname } from "node:path/posix"`**（**不是** `node:path`）：本模块的整个路径域就是 POSIX 形态
  （`/data/...`、`/storage/...`），用宿主平台的 `dirname` 会在开发机（Windows）上把 `/data/x` 切成 `\data`；
- `DSHM_FS_SCOPE=off` 是**排障逃生口**（与 `DSHM_VM_BASH=force|off` 同一惯例）：让整条闸门惰性。
  它**不落任何用户可见开关**。

## 6. 已知边界与未做项（如实登记）

### 6.1 PC 档的**真 shell**（`bash` 工具）**不在**本闸门可达面内

PC 上 `bash` = `dsh-bash-local` → 本机 `execve`，那是**进程级能力**：
`cat /etc/hosts` 照样能读到（闸门管的是文件工具，不是进程）。
**手持档不存在这个缺口** —— 那边的 bash 走 guest 虚拟机（`docs/120`），9p 只导出
`[沙箱根, 工作区]`，天然在允许面内。

⇒ **这是需要用户拍板的一条岔路**：要不要在 PC 上也把 shell 的文件面掐住？
本轮的取舍是**不动**（用户上一轮刚说过「修归修，别到时候鸿蒙PC端又给改坏了」；
PC 上 shell 的全量能力是它的正常形态，掐它需要 OS 级沙箱，代价与风险都不在本轮范围内）。

### 6.2 `/data/app/el2/<uid>/base/<bundle>/…` 这种**别名形态**会被拒

真机实测：`realpath` **不**把 `/data/app/el2/100/base/<bundle>` 折叠成 `/data/storage/el2/base`
（两者是同一份沙箱的两个**挂载视图**，不是软链）⇒ 走词法白名单时别名形态落在面外。
**影响面为零**：应用侧所有路径都从 env 来（`/data/storage/...`），全仓 `rg "/data/app/el2"`
只命中 hdc 工具脚本与文档，**没有一处是宿主进程自己拼的**。
（`/data/app/...` 是 hdc/shell 那一侧的视角，不是应用进程的。）

### 6.3 未做 / 未验

1. **手机 / 平板真机未验**（设备未连）—— 判据与形态无关，但**必须复验**（用户下一步就连手机）；
2. **`glob` / `grep` 入口只有离线门禁**：那两个接口不在 HTTP 面上，无法像 `/api/file` 那样从外部驱动，
   端到端要靠模型真发一次 `glob`/`grep`（用户手测即可）；
3. **attachment 上传/下载**走 `readBytes`/`writeText` ⇒ 已被覆盖，但**未在真机逐条验**；
4. **PC 档回归未做**：侧栏工作区文件/预览已用 `/api/file` 取证（§3.3），但皮肤市场一键安装、终端、
   `publish` 三处要用户手测确认（离线门禁里它们的接线都还在）；
5. **`/data/storage/el1/bundle/entry/resources/resfile/…`（随包资源）落在允许面外**：
   实测它确实是应用自己的 resfile（`ohos-skills` / `toolchain` / `vm` / `busybox` 都在里面），
   但**运行期没有任何模型可见的工具从那里读**（skills 已同步进 `dsh/home/skills`、
   toolchain 已解包进 `files/toolchain`、vm 资产由插件用 `node:fs` 直读**不走** `ctx.fs`）⇒
   按用户「只给沙箱 + 用户目录」的字面口径**不加**这一条。若日后有工具需要它，加一行即可（附门禁）。
