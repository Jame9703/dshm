## 2. 卡顿根因

`hostcore/app/main.js` 在正式包里无条件执行：

```js
Profiler.setSamplingInterval({ interval: 1000 })
Profiler.start()
```

即应用启动后常驻一个 V8 CPU profiler，按 **1000µs** 连续采样。这正好对应
运行进程中长期存在的 `v8:ProfEvntProc` 线程和上述 430ms/10s 的线程 CPU。
同一份文件还把同步 fs 计时环、逐请求 `IN-REQ`/`IN-DONE` 日志和每秒心跳
当成正式默认值，这些都属于历史 LOOP-GAP 取证设施。

修复后：

- 正式默认关闭 V8 profiler；
- 同步 fs / child_process 计时环默认关闭；
- 逐请求入站日志默认关闭；
- 心跳线程默认关闭；
- `DSHM_RUNTIME_DIAG=1` 一次开启整组诊断；
- 仍保留单项开关 `DSHM_CPU_PROFILE=1`、`DSHM_HB=1`、`DSHM_IN_LOG=1`、
  `DSHM_TS_LOG=1`，现场排障不需要改代码。

## 3. 官方插件安装仍失败的原因

之前修的是两条不完整路径：

1. 设置页自定义输入框的 `dsh plugin … add` 文本解析；
2. `runProfilePnpm()` 的 `add/remove` 进程内分叉。

官方插件页还会在安装前后执行三跳直接 `execa("pnpm", …)`：

- `readProfileRegistry()` → `pnpm config get registry`
- `viewProfilePackage()` → `pnpm view … --json`
- `namedSpecManifest()` → 安装前兼容性预检同样调用 `pnpm view`

GitHub 来源还会在安装前另起一次 `git ls-remote`。这些入口都绕过了已有
`runProfilePnpm()` 桥。只要应用内 `bin/pnpm` 薄壳在某台
PC 上“版本探针能跑、真实 view/config 又失败”，官方页就会停在“检查安装包”
或兼容性预检；自定义安装框却可能仍然正常。这正是此前“看起来修了、官方方式
仍不行”的接线缺口。

修复后：

- 应用沙箱（`DSHM_HOME` 与 `DSHM_SANDBOX_HOME` 均位于
  `/data/storage/`）内优先使用进程内通道，不再让 `--version` 探针的偶然成功
  绕过桥；
- `config` 读取 `$DSH_HOME/installer.json`，缺省与安装器一致使用
  `https://registry.npmmirror.com/`；
- 官方 `view` 与兼容性预检转发到 Host 已有的
  `/dshm-registry/view`，保持 pnpm stdout 的 JSON 形状；
- GitHub 安装的应用内预检不再 spawn `git ls-remote`；真正的 codeload 下载、
  失败分类和落位仍由 `dshm-installer` 负责；
- 私有或非公共 registry 不冒充 Host 默认源，仍交回上游原实现；
- `DSHM_PROFILE_PNPM_BRIDGE=off` 可整条关闭，`force` 可现场强制接管。
- 下一次真机复测时，`dshm-host.log` / 插件输出应能直接看到
  `[dshm-profile-pnpm] registry bridge:`、`view bridge:` 与
  `GitHub preflight skipped:`，用来证明官方页确实走了新通道。
