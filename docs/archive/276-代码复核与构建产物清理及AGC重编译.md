## 2. 审出并已修的 2 个真缺陷

### 2.1 【高】`isExternalNavigation` 的主机名前缀绕过（我上一轮引入）

```ts
const host: string = rest.split('/')[0];
if (host.startsWith('127.0.0.1') || host.startsWith('localhost') || host.startsWith('[::1]')) {
  return false;   // ← 当"应用自身"放行
}
```

**复现（可执行判据）**：

| URL | 旧判据 | 应为 | 后果 |
|---|---|---|---|
| `http://127.0.0.1.evil.com/` | 放行（判成应用自身） | 外链 | 外站在**应用 WebView 内**打开 |
| `http://localhost.attacker.net/` | 放行 | 外链 | 同上 |
| `http://127.0.0.1@evil.com/` | 放行 | 外链 | `@` 前是 userinfo，真主机是 `evil.com` |

⇒ 这**正是"链接不跳浏览器"要消灭的现象**，只是换了个入口。

**修法**：先剥 `userinfo`（`authority.split('@').pop()`）、再剥端口（`[::1]:3120` → `[::1]`），
然后与 `127.0.0.1` / `localhost` / `[::1]` **全等**比较。修正后 8 个用例（含 `[::1]`、
`https://evil.com/?u=127.0.0.1` 这种 query 里带回环的）**全部判对，绕过归零**。

> 顺带审了垫片侧 `isSameOriginAsApp`：它比的是 `location.origin + '/'`，是精确前缀，
> `127.0.0.1:3120.evil.com` / `:31200` 都不会被误判 ⇒ **无需改动**（有用例佐证）。

### 2.2 【中】px→vp 换算用错了密度字段

```ts
const dpi: number = d.densityDPI > 0 ? d.densityDPI : 160;
widthVp = d.width * 160 / dpi;        // ← densityDPI 是"每英寸物理像素数"
```

本机 SDK `@ohos.display.d.ts` 原文：

- `densityDPI` = "**Physical** pixel density … the number of pixels per **inch**"；
- `densityPixels` = "**Logical** pixel density … the scaling coefficient between px and vp"，
  `[0.5, 4.0]`，一般 `1.0` / `3.0`。

**偏差量级**：

| 情形 | 旧（densityDPI） | 新（densityPixels） | 偏差 |
|---|---|---|---|
| 折叠屏内屏 3120px / 440dpi / scale 3.25 | 1134.5 vp | 960.0 vp | **+174.5 vp** |
| 平板 2800px / scale 2.0 | 1400.0 vp | 1400.0 vp | 0 |
| 直板机 1260px / scale 3.25 | 420.0 vp | 387.7 vp | **+32.3 vp** |

⇒ 断点（600/900 vp）整体偏大，**折叠屏"单屏"可能被误判成展开**：设置面板就不手机化、
朝向也不锁竖屏 —— 与 `docs/271` 的目标相反。修成 `width / densityPixels`。

### 11.1 又审出 2 个真缺陷（均已修 + 门禁钉住）

**① 【中高】`onLoadIntercept` 缺 `isMainFrame()` 判断**
SDK 原文确认：`onLoadIntercept` 对**所有导航**触发（含 iframe 的 src 加载），且
`WebResourceRequest` 专门提供 `isMainFrame()`（`@since 8`，本机 API 23 可用）。
旧实现不判主帧 ⇒ 聊天内容里一个指向外部站点的 iframe 会让浏览器在**无用户交互**时自动弹出。
修法：主帧外链 ⇒ 拦下并交系统浏览器；**子帧外链 ⇒ 同样拦下（不许嵌进应用 WebView）但不外开**。

**② 【中】`applyFoldableOrientation` 缺主窗守卫**
本应用存在非 MAIN 的 UIAbility 实例（会议窗 / spec 窗，`WindowKind` 其它分支可证）。无守卫时：
子窗创建会覆盖模块级 `foldWin` 并对**子窗口**锁竖屏，之后折叠重算也作用于那个子窗——主窗朝向反而没人管。
修法：`onWindowStageCreate` 里用 `this.launchParams.kind === WindowKind.MAIN` 守卫调用；
**`onWindowStageDestroy` 的解绑同样对齐**（否则子窗先销毁会把仍活着的主窗的折叠监听一并拆掉——
`onWindowStageCreate` 不会重跑 ⇒ 主窗从此失去折叠感知）。phone 模块无 `WindowKind`/多实例概念
（纯手机壳），保持无守卫是正确的，未改。
