# 381-平板改走手机壳（移动逻辑）与「PC 应用」标签消除 + 终端探测段瘦身

> ⚠️ **已被 [`docs/386`](386-三端分离重整方案-PC平板手机各走各的.md) 推翻，勿按本档实施**（2026-11-06）：把 tablet 划给 phone 会把同样上报 tablet 的 Edge/ProMax 一起塞进手机壳 ⇒ 9 条权限、无 CUSTOM_SANDBOX、原生终端失效。

- 日期：2026-11-06
- 触发：用户第三次要求「平板端的顶栏恢复到手机端这样、平板不要再显示 PC 应用、使用手机端逻辑」；同时终端仍报错且「一直在启动」
- 结论：**平板不再走 `entry`（PC 壳），改走 `phone`（手机壳）**。`entry` 只保留 `2in1`。`phone` 承载 `phone + tablet`。

---

## 1. 为什么之前三次都没"恢复成手机端"

`entry` 与 `phone` 是**两套完全独立的壳**：

| | `entry` 壳 | `phone` 壳 |
| --- | --- | --- |
| 原生顶栏 | **有**（自绘标题栏 + 三键，PC/平板共用） | **没有**（"移动端 APP 没有顶栏"） |
| 侧栏入口 | 原生顶栏那颗按钮代点官方 toggle | 页面内 ⊞（`ensureFab`） |
| 窗口形态 | 自由窗口 / 托盘 / `BackGroundAbility` | 全屏移动形态 |
| `deviceTypes` | `tablet` + `2in1` | `phone` |

过去几轮我一直在 `entry` 壳里调 CSS（侧栏几何、抽屉、inert），但**顶栏是 ArkUI 原生组件，不是网页 CSS 能改的**；而平板之所以被系统认成「PC 应用」，根因是它安装的模块声明了 `2in1` 设备面。

⇒ 只要平板继续装 `entry`，这两件事都不可能满足用户的原始要求。

## 2. 本轮改法（模块设备面）

```diff
  entry/src/main/module.json5
- "deviceTypes": ["tablet", "2in1"]
+ "deviceTypes": ["2in1"]

  phone/src/main/module.json5
- "deviceTypes": ["phone"]
+ "deviceTypes": ["phone", "tablet"]
```

- **平板** → 安装 `phone` 模块 ⇒ 手机壳：无原生顶栏、⊞ 入口、移动侧栏，任务列表里就是普通移动应用。
- **PC / 2in1** → 仍安装 `entry` 模块 ⇒ 原生顶栏 + 三键 + 托盘 + 后台常驻，能力一个不少。
- 共享 HSP `hostruntime` 的设备面不变（`phone / tablet / 2in1`）。

**覆盖安装安全性**：模块集合没变（仍只有 `entry` / `phone` / `hostruntime` 三个 HAP），只改了 `deviceTypes` 列表 ⇒ 同签名覆盖安装即可，不涉及卸载、不动 el2 用户数据。

**权限面不变**：`entry` 17 条 / `phone` 9 条的口径与判据（`tools/check-permission-surface.mjs`）一个字节没动。平板改用 9 条那套与手机完全一致——手机侧早已验证 Host / 终端 / 文件桥可用。

### 同步更新的门禁期望（设备面是"契约"，必须一起改，否则门禁自相矛盾）

| 文件 | 改动 |
| --- | --- |
| `tools/build-agc.mjs` | `entry → ['2in1']`、`phone → ['phone','tablet']` |
| `tools/check-pc-api26.mjs` | 同上（`moduleEntry` / `modulePhone`） |
| `tools/check-store-readiness.mjs` | `EXPECTED_DELIVERY_DEVICE_TYPES` 同上 |

`REQUIRED_DEVICE_TYPES`（phone/tablet/2in1 必须全覆盖）仍然满足：三个设备面分别落在 `phone` 与 `entry` 上。

## 3. 终端：探测段再瘦身（"一直在启动"的直接成因）

上一轮把探测预算改成 30s→60s→120s 阶梯后，用户看到的现象从"30 秒报错"变成"一直在启动"——因为探测段里原本还塞着三组**可选安装**：

```js
probeLines.push(...guestSshBootstrapLines());        // dropbear 等
probeLines.push(...guestExtraToolBootstrapLines());  // tmux / gh
probeLines.push(...guestBaseExtrasLines());          // libcurl 闭包 / pnpm / dsh
```

在 TCG 软件模拟的 guest 上，这些是分钟级工作量。于是**"`/bin/bash` 到没到"这个几秒钟就能回答的问题，被一堆可选安装拖成了超时**，整台 VM 被判 `failed`。

本轮拆分：

- **探测段**只做四件事：挂 9p 共享、建符号链接、挂工作区、`[ -x /bin/bash ]`。命中即返回。
- **引导段**（`runGuestBootstrap()`）单独一段，预算同样走阶梯，**失败不阻塞**（SSH / tmux / gh / pnpm 都是可选工具）。
- 新增日志：`guest 探测段开始（预算 …）` / `guest 引导段完成（… ms；SSH=…）` / `guest 引导段失败（不影响 bash 可用性）：…`

这样首启关键路径只等"bash 是否可执行"，终端不再被可选安装拖住。

## 4. 验收口径

| 项 | 判据 |
| --- | --- |
| 平板安装哪个壳 | `pack.info`：`phone` 的 deviceType 含 `tablet`，`entry` 只有 `2in1` |
| 平板 UI | 无原生顶栏、左上 ⊞、抽屉为官方形态，与手机一致 |
| 平板任务列表 | 不再显示「PC 应用」 |
| PC | `entry` 仍在，顶栏三键 / 托盘 / 后台常驻不受影响 |
| 权限面 | entry 17 / phone 9，`check-permission-surface.mjs` 原样通过 |
| 终端 | 首条命令应在秒级拿到 bash；失败报文带阶段与耗时 |

**真机仍需验证**：平板覆盖安装后是否直接进入手机壳、旧数据是否完好、终端首启耗时。
