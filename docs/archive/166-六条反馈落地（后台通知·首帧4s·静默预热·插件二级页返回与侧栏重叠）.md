## 1. 后台「正在运行数据传输任务」通知（第 1 条）

**现象**：手机切后台时状态栏常驻一条系统通知「正在运行数据传输任务」；用户删掉通知后行为异常。

**根因（代码 + 官方文档）**：
- 本应用申请的是长时任务 `dataTransfer`（`platform/.../KeepAlive.ets` + `module.json5` 的
  `backgroundModes:["dataTransfer"]`）。通知文案**由系统按类型写死**，应用不能改
  （官方《Background Tasks Kit 接入规范》：「不得修改长时任务通知内容」；数据传输只允许补进度）。
- 原实现在 **`onWindowStageCreate` 一进来就 `acquire()`**，且**全文件没有 `onBackground` /
  `onForeground` 配对释放** ⇒ 只要进程活着通知就常驻（连前台都在）。
- 用户删通知 = 官方定义的「用户主动停止」，平台随即取消任务；《接入规范》还禁止
  「用户主动停止并取消长时任务后**立即**再次申请」。

**修法**（三条一起）：
1. **按平台分档**：PC / 2in1 仍在启动时申请（三键「关闭」= 收进后台，那里通知是必要代价）；
   **手持档改到 `onBackground` 申请、`onForeground` 释放** —— 正是官方《长时任务(ArkTS)》
   的建议（"如果应用在前台时不希望存在长时任务通知，建议把申请推迟到 onBackground"）。
2. **按需**：手持档进后台时先看 `SessionHub.snapshot()` —— `running`（有一轮在跑）或
   `pending`（待审批 / 待回答）才申请；**空闲切后台完全不弹**。读不到状态时按"有事"处理（fail-safe）。
3. **感知用户取消**：注册 `backgroundTaskManager.on('continuousTaskCancel')`（API 15+），
   记下 `reason` 并置 `userStopped`；该标志在下次回前台时清除 ⇒ 同一个后台周期内**不再重申请**。

**真机读数**（手机 `62T0225B18039433`，hilog 原文）：
```
10:13:59.805 entry/ability: 手持档：长时任务改到 onBackground 按需申请（前台不申请 ⇒ 无通知）
10:14:57.954 testTag: Ability onBackground
10:14:57.955 entry/ability: 手持档进后台：当前没有在跑的任务 / 待决事项 ⇒ 不申请保活（无通知）
10:15:04.339 testTag: Ability onForeground
```

## 2. 首次启动 ≤ 4 s（第 4 条）

**口径（官方）**：冷启动 = "用户点击桌面图标 → **应用首页首帧渲染完成**"
（《应用冷启动时延优化》）；且"ArkTS 单线程 EventLoop：异步调用会被同步逻辑挤到 UI 绘制之后"。
AGC 自检读到的 9039 ms / 目标 4000 ms 就是这条。

**根因**：`EntryAbility.onCreate` 里**立刻**拉起 `autoStartHostForDiagnosis()`
（probe → 解包内置核心 95 MB / 4 万条目 → `host.start()`）。这条链的同步段
（`docs/146` 实测 `LOOP-GAP 1680 ms` + 同步调用 1037 ms，主要在建树模块加载）与**首帧抢同一个
ArkTS 线程** ⇒ 首帧被顶到 9 s 级。

**修法**：把整条宿主启动链**后置到首帧之后**：`onWindowStageCreate` 的 `loadContent` 回调里
`scheduleHostStartAfterFirstFrame()` 延迟 400 ms（常量 `HOST_START_DELAY_AFTER_FIRST_FRAME_MS`，
页面加载失败则 0 延迟立刻跑；每个 Ability 实例只排一次）。

**真机读数**（同一次冷启动的 hilog）：
```
10:13:59.783 Ability onCreate
10:13:59.884 Succeeded in loading the content.      ← 页面加载完成（首帧）
10:14:00.287 首帧后启动宿主链（延迟 400 ms）        ← +403 ms 才开始拉宿主
10:14:00.288 DSHM-AUTO 开始：入口=…/main.js
10:14:13.874 DSHM-AUTO 启动 Host：ok=true
```

> 说明：解包（首次安装那一次）与 Host 启动现在都发生在**首帧之后**；页面先出来、再"正在启动"。

## 3. 终端静默预热（第 5 条）

**改动前**：`docs/155` 的口径是"启动期一根手指都不碰 VM"（避免和应用冷启动抢资源；且
"沙箱之外的工作区"要在**启动那一刻**由 cwd 定死第二份 9p，一进程一 VM 挂上就改不了）。

**新设计（三条约束一起满足，落在 `dshm-vm-bash`）**：
1. **延迟**：默认 **60 s**（`DSHM_VM_PREWARM_SEC` 可改，夹在 5..600），避开 App 冷启动窗口；
   `DSHM_VM_PREWARM=off` 可整条关闭。
2. **更严的内存闸门**：预热前判 `MemAvailable ≥ VM_MIN_AVAILABLE_MIB + PREWARM_HEADROOM_MIB`
   （1280 + **512** MiB）—— 预热是后台行为，不许贴着可用内存下限偷。
3. **cwd 取真实记录**：`vm/prewarm-cwd.txt` 存**上一次真实请求用过的目录**（`spawn` 与
   `spawnTerminal` 两条链都记）⇒ **首次冷启动没有记录就不预热**，让第一次真实请求照旧决定
   9p 绑定，绝不把用户的工作区绑错。

**真机读数**（`.56` 首次冷启动）：
```
02:23:07.151 [dshm-vm-bash] 静默预热已排程：延迟 60s 后预热（DSHM_VM_PREWARM=off 可关）
02:24:07.158 [dshm-vm-bash] 静默预热跳过：还没有任何真实请求记录过 cwd（首次冷启动不预热，避免把 9p 绑错目录）
```

**待验收的一步**：先用一次终端 / bash（写下 `prewarm-cwd.txt`），再重启应用 ⇒ 应看到
`静默预热开始：cwd=…` 与 `静默预热结果：ok=true`，随后**第一次开终端不再等冷启动**。

> **内存那半条只做到"可控"，没做到"自动变小"**：guest 内存默认仍是 384 MiB
> （`DSHM_VM_MEMORY_MIB` 可降到 256，但首装 `apk add` 需要余量，故没改默认）；
> `tb-size` 也维持 256。要不要把默认压到 256 / 降 tb-size，建议等这轮预热跑起来后
> 用真机 VmRSS 读数再定（见 §6 的"下一步"）。

## 4. 插件二级页返回 + ⊞ 与面板重叠（第 6 条）

**根因（两处，都在 web 垫片侧）**：
- **重叠**：⊞ 是 `position:fixed; top:6px; left:6px` 的自绘浮动按钮，而设置面板（含插件二级页）
  是 body 上的**全屏 portal** ⇒ 必然压住面板左上角那行（「插件」标题 / 「返回插件」按钮）。
- **手势**：`WebApp.onBackPress()` 的链是 `accessBackward()` → `__DSHM_BACK__.consume()`
  （只认 `OVERLAY_SEL` 浮层 + 抽屉）→ 都不是就 `minimizeToBackground()`。
  插件二级页既不是浮层、也不进 web 历史 ⇒ **侧滑必然落回桌面**。

**修法**：
1. **面板打开时藏掉 ⊞**：侧栏垫片新增 `data-dshm-panel="open|closed"`（300 ms 巡检按
   `OVERLAY_SEL` 的可见性写；判据与 BACK_SHIM 同一组），CSS
   `html.dshm-handheld[data-dshm-panel="open"] #fab{display:none !important}`。
   面板自带返回/关闭，⊞ 在面板里本来也没有用武之地。
2. **二级页"回上一层"**：BACK_SHIM 新增 `consumePanelBack()` —— 认客户端自己的
   「返回插件 / Back to plugins」按钮（跨版本稳定锚点，不认哈希类名），排在**浮层分支之前**
   点击它并返回新裁决串 `panel`；`readWebVerdict` 白名单与 `finishWebBack` 的"已消费"集合
   同步加上 `panel`。

**门禁**：`check-handheld-back` 正例 **40 passed / 0 failed** + **5 条对照臂**全部有效
（第 4 条：删掉 panel 分支 ⇒ 必红；第 5 条：删掉主面板回会话分支 ⇒ 必红）；`check-sidebar-shim-css` **9 / 0**。
**手测（手机，2026-10-16）**：插件二级页 → 返回 = `panel`（回列表）；插件列表 → 返回 = `home`（回会话）。

### 4.1 第二轮：插件**主面板**右划仍回桌面（用户复报）

**现场**：用户进插件页后侧滑，`diag-web-back` 记 `none`、console `consume: none` ⇒ 落回"最小化到桌面"。
**根因（只读排查，两处）**：
- 插件页在上游是 **main 槽的主面板**（`dsh-client-ui-plugin-manager` 的 `slots.register({name:'main', key:PANEL_ID})`），
  既不是 `[data-shortcut-modal]` 浮层、也不进 Web 历史 ⇒ 第一轮那三条分支全不认。
- 回会话的**唯一官方入口**是 `ctx.layout.selectPanel(null)`，它没挂 `globalThis`；
  DOM 上的等价入口 = 侧栏里一条会话行（`data-row-key="session:<id>"` → `onOpen` → `selectPanel(null)`）。
  而**主面板激活时没有任何会话行带 `aria-selected="true"`**（选中的是 panel row），
  且侧栏收起时那份列表是**虚拟列表**（行不渲染）⇒ 第一轮"找当前选中会话行"的判据恒落空。

**修法**（`WebApp.ets` 的 `BACK_SHIM_JS`）：
1. `selectedSessionRow()` → `sessionRow()`：**优选取 `aria-selected="true"` 的那条，取不到就取第一条可见会话行**
   （列表按"最近更新"排序 ⇒ 第一条 = 刚待过的会话）。
2. 新增 `consumeMainPanelHome()`：激活判据用官方 PanelRow 的 `aria-current="page"`（= 确实停在主面板上）；
   收起态走**两步走** —— 先 `__DSHM_SIDEBAR__.toggle()` 展开抽屉 → 轮询等会话行渲染
   （16 × 150 ms ≈ 2.4 s；1.2 s 在真机上不够）→ 点它（= 回会话）→ 400 ms 后把抽屉收回；
   仍等不到就**把抽屉留着**并记 `consume: home aborted (…; drawer left open)`（不再一路沉到桌面）。
3. 裁决串 `home` 进 `readWebVerdict` 白名单与 `finishWebBack` 的"已消费"集合。

**真机验证（手机 `62T0225B18039433`）**：抽屉收起 + 插件列表 →
`uitest uiInput keyEvent 2` ⇒ `diag-web-back` = `home`，console
`consume: home via drawer (session rows are virtualized while collapsed)` +
`consume: home div[role=treeitem]…sessionRow`，截图 = **会话页且抽屉已收回**（未最小化、未回桌面）。
> 手势说明：`uitest uiInput swipe` **不触发系统边缘手势**（实测无 `diag-web-back` 新条目），
> 故用返回键（KEYCODE_BACK=2）走**同一条** `onBackPress` → `consume()` 链做等价验证。

## 5. 第 2 条的竞态修复 + 第 3 条的现场需求

### 5.1 第 2 条：已定位为**竞态**并修掉（待用户对照图确认）

**实测（手机 `62T0225B18039433`，2026-10-16）**：把 `ui-theme.preference` 切成 `light`、等 3 s
再切到任务卡片 —— **卡片顶栏是浅色、正常**（截图存 `%TEMP%\dshm-light-recents.jpeg`）。
⇒ 用户报的"可能是黑色"不是稳态，而是**切换外观后立刻切后台**那一拍：任务卡片取的是**窗口快照**，
而取色原先散在两处（页面 `applySystemBarTheme()` 跟随 web 侧观测 / 能力层只重设三键配色），
**前后台边界上没有任何一处把三件套按当前外观收敛一次**。

**修法**：
1. 取色收成**唯一一份**：新增 `platform/.../system/WindowChrome.ets` 的 `windowChromeFor(mode)`
   （深 `#151517`/白字/浅图标，浅 `#FFFFFF`/`#0F1115`/深图标），页面改用它。
2. 能力层新增 `reassertWindowChrome(why)`：按 `appearanceMode()` 重放**状态栏属性 + 窗口底色 +
   三键配色**，并在 **`onBackground` 与 `onForeground` 两个边界**各调一次 ⇒ 快照一定带当前外观。

**待用户验**：切外观后**立刻**切后台，看卡片顶栏是否仍会黑；另外"深色沉浸哪里不对"仍需要你指认界面
（我抓的深色屏看起来正常）。

### 5.2 第 3 条：PC 依据已取到，缺"平板在线"

**PC 现场（`86E0226429000417`，2026-10-16）**：
```
diag-decor-caps : visible=ok set=ok get=H=37 style=ok mode=light status=4:FLOATING -> present=true
diag-decor-top  : handheld=false keys=true rect.w=0 rect.h=0 inset=0
```
⇒ **PC 按设计不让位**（`decorTopInsetVp` 第一条：非手持恒 0）—— 因为 PC 那套自绘顶栏本来就占据
三键区、且内容是从顶栏下方开始的；截图（`%TEMP%\dshm-pc.jpeg`）里三键贴在窗口右上、菜单在左，
两者天然不打架。**这正是"平板要向 PC 看齐"的那个参照形态。**

**为什么还需要平板**：平板走的是 `dshm-handheld` 那条链（自绘顶栏不渲染 ⇒ 让位量兜底），
而 `HANDHELD_DECOR_INSET_VP = 24` 是**上一轮平板真机验收定的值**（当时用户反馈 38 偏宽、
实测最小只需 8）。现在又报重叠 ⇒ 要知道是"换了设备 / 系统改了装饰高度 / 只有某个窗口态重叠"，
得拿**那台平板的** `diag-decor-caps` / `diag-decor-top` 两行读数（以及一张现场截图）才能定档。
拿到后二选一：① 只修让位量（把实测装饰高度用起来，读不到再退常量）；
② 按用户已定的方向把**平板整体切到 PC 形态**（不再走抽屉/⊞ 那一套）。
