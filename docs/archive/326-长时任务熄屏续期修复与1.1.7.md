# 326 · 长时任务熄屏续期修复 + 版本 1.1.7

> 日期：2026-10-31 ｜ 状态：**已实施，审核通过，出包**

---

## 0. 结论

**长时任务此前的实现是完整的**（`backgroundTaskManager.startBackgroundRunning` +
`continuousTaskCancel` 监听 + 退避续期，2026-10-28 那轮就做好了）。
但**熄屏场景仍会停止执行**，本轮找到两个真实缺陷并修复。

| # | 缺陷 | 影响 |
|---|---|---|
| 1 | 续期窗口只有 **60 秒**（10s 基数 × 3 次） | 撑不过"熄屏 10 分钟才被系统取消"的间隔 |
| 2 | 续期依赖 `setTimeout`，**熄屏后 JS 定时器被冻结** | "被取消后再续期"在熄屏时天然失效 |
| 3 | 熄屏瞬间不做任何校准 | 系统的 600s 无进度计时不被重置 |

---

## 1. 机制事实（先说清楚，避免误判）

手持档只能用 `DATA_TRANSFER`：

- `TASK_KEEPING` 需要受限 ACL `KEEP_BACKGROUND_RUNNING_SYSTEM`；
- 本仓权限铁律 **entry 17 / phone 9 条**，加不了（AGENTS.md）。
- 官方契约：`DATA_TRANSFER` **首次进度后 10 分钟（600s）无更新即被系统取消**。

⇒ "熄屏一段时间就断"在这个约束下是**必然**，只能靠续期兜住。

PC/2in1 走 `TASK_KEEPING`（计算型），不受 600s 约束 —— 所以这个问题主要在手机/平板。

---

## 2. 缺陷与修法

### 2.1 续期窗口太短

```ts
RENEW_BASE_DELAY_MS = 10000        // 10s
RENEW_MAX_ATTEMPTS  = 3            // ⇒ 10+20+30 = 60s 总窗口
```

系统取消点在 600s ⇒ 60 秒的续期窗口**必然错过**。

改为 `5000 / 8` ⇒ 序列 5/10/15/…/40s，总窗口约 **3 分钟**，覆盖熄屏-解锁抖动，且仍是有限重试。

### 2.2 熄屏时定时器被冻结（结构性）

```text
T+0      熄屏，任务在跑
T+600s   系统取消 → onCancel → scheduleRenew(10s)
T+610s   setTimeout 回调 —— 熄屏期间 JS 定时器冻结 ⇒ 不执行
解锁后    定时器解冻才续期 ⇒ 期间任务一直停着   ← 用户看到的现象
```

**唯一可靠解法：不等被取消，在熄屏前主动重置计时。**

新增 `KeepAlive.noteScreenState(screenOff)`：

| 场景 | 行为 | 理由 |
|---|---|---|
| 熄屏 + 应用在前台（`refs=0 && !active`） | **跳过** | 前台无后台工作；抢申请会多挂一条"正在运行后台任务"通知 |
| 熄屏 + 已在后台保活 | **停-起**重申请 | 只有"停再起"能把系统的 600s 计时归零；`startBackgroundRunning` 对已存在的任务不重置计时 |
| 亮屏 | 若未保活则**立即补一次**，并重置退避计数 | 解锁后第一件事就是恢复 |

### 2.3 壳层接上屏幕事件

两壳 `EntryAbility` 新增 `setupScreenWatcher()`（逐字一致）：

```ts
commonEventManager.subscribe(subscriber, (err, data) => {
  const off = data.event === COMMON_EVENT_SCREEN_OFF;
  this.keepAlive.noteScreenState(off);
});
```

订阅 `COMMON_EVENT_SCREEN_OFF` / `COMMON_EVENT_SCREEN_ON`，在 `onCreate` 里
`setupNotifications()` 之后挂上。失败只记日志（老设备降级为原行为）。
