# 174 · 浏览器自动化 PoC（海泰扩展 + 本地桥，端到端打通）

> 承接 `docs/173`（浏览器自动化调研）。用户 2026-10-16：「先做个 POC 测试看看」。
> **结果：端到端跑通** —— 打开网页 → 读元素树 → 点击 → CDP 执行 JS → 抓正文，全链路实测完成
> （`DEMO COMPLETE ✅`）。本档记录架构、实测流水、暴露的硬限制与工程坑、以及产品化建议。

## 1. PoC 形态（实测架构）

```
海泰浏览器（设备）
 └─ 自研扩展 "DSHM Browser Bridge (PoC v3)"（MV3：debugger/tabs/scripting）
      ├─ chrome.debugger（CDP 1.3）：Page.navigate / Runtime.evaluate
      ├─ chrome.scripting：注入元素树 / 点击 / 取正文
      └─ Service Worker ⇄ ws://127.0.0.1:18888/extension
              ↑ 设备 18888 →（hdc rport 反向转发）→ PC 18888
PC（本机）：Node 桥 dist/poc-bridge/server.mjs（协议：ping / tools/discover / tools/invoke）
```

**部署链路**（全程脚本化，可复跑）：
1. `dist/poc-bridge/deploy-ext.mjs`：经 **DSHM 的 `/dshm-python` 桥**（`hdc file recv host-ready.json` 取 token/port +
   `hdc fport`）把扩展文件**分块写入设备共享区** `<下载>/com.dshm.dshmbeta/poc-ext-v3/`，**逐文件 sha256 校验**；
2. `hdc rport tcp:18888 tcp:18888`：把设备侧 18888 反向转发到 PC 上的桥；
3. 用户在海泰扩展页「加载已解压的扩展程序」选中该目录（30 秒操作）。

## 2. 实测流水（桥端实录，节选）

| 步 | 调用 | 结果 |
|---|---|---|
| 1 | `tools/discover` | 工具注册：`navigate / get_tree / click / get_text / cdp_eval` |
| 2 | `navigate(example.com)` | `chrome.debugger.attach(tab,"1.3")` → **CDP `Page.navigate`** → `load=complete` |
| 3 | `get_tree` | `scripting.executeScript` 注入 → `[ref_0] link "Learn more"`（ref 机制可用） |
| 4 | `click(ref_0)` | 页面真实跳转（`example.com` → `iana.org/help/example-domains`） |
| 5 | `cdp_eval` | **CDP `Runtime.evaluate`** 返回 `{title:"Example Domains", url: 跳转后地址}` |
| 6 | `get_text` | 正文提取（含跳转后页面内容）成功 |

## 3. 海泰浏览器的两条硬限制（实测，写进设计约束）

1. **禁止扩展创建/激活标签页**：`chrome.tabs.create` / `chrome.tabs.update(active)` **永久挂起**（不 resolve 不 reject）
   ⇒ **一切导航走 CDP `Page.navigate`**（对已存在的 http(s) tab 操作）；目标 tab 用 `chrome.tabs.query` 选取（可用）。
2. **调试器独占**：一个 tab 同时只允许一个 `chrome.debugger` 附着。实测与 **Ultron（WorkBuddy 的扩展）**冲突
   （`Debugger is not attached…` / attach 失败）；**停掉 Ultron 后 attach 立即成功**。
   ⇒ DSHM 产品化时要**显式处理**：检测/提示用户先断开 WorkBuddy 的浏览器连接（或与 WorkBuddy 协调交替使用）。

## 4. 两条工程坑（都很贵）

1. **MV3 Service Worker 生命周期**：空闲（无 WS 活动）时 SW 会被停 → WS 断 → 反复重连（实测连断循环）。
   **修法**：桥端 **15s `ping` 保活** + 扩展端 3s 自动重连。该修正后连接稳定。
2. **海泰对"解压扩展"有内部缓存**：改了磁盘上的 `background.js` 后，扩展页点"重新加载"甚至"移除+重装"
   **都不重读新代码**（用 `build` 标记实测判定）。**唯一可靠路径：换新目录名 + 升版本号重新加载**
   （PoC 依次用了 `poc-ext` → `poc-ext-v2` → `poc-ext-v3`）。⇒ 正式产品的升级引导必须考虑这一点。

## 6. 产品化建议（下一步，待拍板）

1. **桥归属**：正式形态应由 **DSHM 宿主（设备侧 Node）** 内置 WS 端点（取代 PC 桥；`hdc rport` 仅用于开发调试）；
   端口发现可先用"固定端口 + 配置"最简路径。
2. **扩展工具面**：对齐 `docs/173` §3 的千问面（computer / accessibility-tree ref / 网络观测 / 截图），
   按 DSHM 场景裁剪；**视觉指示**（操作高亮+状态徽章）建议保留（用户体验好）。
3. **安装引导**：DSHM 释放扩展目录到共享区 + 界面引导"加载已解压扩展"（沿用 PoC 的部署器模式）；
   升级引导需处理 §4.2 的缓存坑（换目录/升版本）。
4. **与 Ultron/WorkBuddy 的 debugger 冲突**：在工具错误里给可操作的提示（"请先断开 WorkBuddy 浏览器连接"）。
5. **安全面**：桥只监听 127.0.0.1 + token 校验（PoC 未做 token，正式必须加）；工具面默认只读、危险动作（点击/输入）沿用 DSHM 的审批机制。

## 7. 环境备注

- 本档落档时：PC 桥会话与 `hdc rport` 仍保留（便于用户复验）；验证完成后清理方式 =
  关掉桥进程 + `hdc rport rm tcp:18888 tcp:18888`；海泰里的 `PoC v1/v2/v3` 扩展可随时移除。
- 全程未改 DSHM 产品代码；DSHM 仅被临时启动（提供 python 桥）+ 被读取 host-ready.json 取会话 token
  （token 随每次宿主重启更换）。
