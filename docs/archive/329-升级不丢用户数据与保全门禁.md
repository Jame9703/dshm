# 329 · 升级不得丢用户数据：机制核实 + 新增保全门禁

> 日期：2026-10-31 ｜ 状态：**已核实 + 已上门禁**
>
> 用户口径：「确保不会清理用户数据完整升级」。

## 1. 机制：`home/` 与 `cores/` 是两套互不相交的生命周期

`<filesDir>/dsh/` 的布局（`hostruntime/src/main/ets/core/CoreStore.ets` 头注，也正是本门禁钉住的"书面契约"）：

```text
<filesDir>/dsh/
  ├── cores/<version>/          已安装的核心树（每版一份，约 350MB/棵，可增可删）
  ├── cores/<version>.staging/  正在解包，未激活
  ├── home/                     $DSH_HOME：会话/设置/凭据/工作区注册（**跨版本共享，唯一一份**）
  └── state.json                { current, previous, history }
```

**升级换的是 `cores/`，用户数据在 `home/`。** 两者在代码里由两个不同的方法拼出来：

```ts
coreDir(version) { return `${this.coresDir()}/${version}`; }   // cores/<version>
homeDir()        { return `${this.baseDir()}/home`; }          // home
```

没有任何一条路径把 `home` 拼进 `cores`，也没有任何删除调用指向 `home`。

## 3. 清理范围：`evict()` 只删 `cores/<version>`

```ts
async evict(keep, keepExtra = []) {
  for (const v of evictionCandidates(state, this.listInstalled(), keep, keepExtra)) {
    await fs.rmdir(this.coreDir(v));   // ← 唯一删除目标，参数必须是 coreDir()
  }
}
```

`evictionCandidates()`（纯函数）还额外保护两类：
- `state.current` 与 `state.previous`（会启动的那两棵）；
- **`current` 为空时正在跑的最新那棵** —— 源码注释写着这是"别把自己脚下的地板拆掉"。

## 4. 自愈机制也不删用户数据

启动失败自愈（`dshm-user-rows.js`）用的是**改名隔离**：

```js
fs.renameSync(rowsPath, `${rowsPath}.quarantine-${Date.now()}`);
// 注释：原样保留，可手工恢复
```

三处 `rmSync` 的对象分别是：市场配置行文件（包卸载后的坏行）、**超过取证窗口的** `*.quarantine-*` 副本、启动失败标记 —— 都是本进程自己写的中间产物。

## 5. 新增门禁：`check-user-data-preserved.mjs`

### 5.1 为什么必须静态判

"删了用户数据"在测试里**不可观测**：跑完看不出丢了什么，测试环境本来也没有真用户数据。
静态判据能覆盖**全部**删除调用点；运行时判据只能覆盖走到的分支。

### 5.2 三条判据

| 判据 | 内容 |
|---|---|
| A **静态无删除面** | 产品代码里凡是删除型调用（`rmdir*`/`unlink*`/`rmSync`/`rm(`）**同一行或前两行**出现 `home`/`DSH_HOME`/`HOME_DIR`/`sessions`/`workspace` 的，一律判红。白名单只允许两条，且**必须同时匹配删除参数的形态**（防止"文件在白名单里 ⇒ 删什么都放行"） |
| B **布局契约在位** | `CoreStore.ets` 里必须仍有「`home/` … 跨版本共享，唯一一份」这句话 —— 改布局的人必须同步改判据，而不是悄悄把 home 挪进 cores |
| C **清理范围** | `evict()` 里的删除调用，参数只允许 `this.coreDir(...)` |

### 5.3 白名单只有两条（每条都写了"删的是什么、为什么不是用户数据"）

| 文件 | 删除对象 |
|---|---|
| `CoreStore.ets` | `staging` 壳子 / `this.coreDir(v)`（旧核心树） |
| `dshm-user-rows.js` | `rowsPath`（市场配置行）/ `full`（过期隔离副本）/ `markerPath`（启动失败标记） |

### 5.4 判据收窄的两轮（记录思路）

第一版把**注释**里的 `unlink` 也当成删除调用，误报 2 处（"create+write+unlink 全部成功才算真能当工作区"）；
第二版又漏了**字符串续行**（`+ '选择理由=…unlink 全部通过）'`）。两次都收紧到"只判真正的代码行"：

```js
if (trimmed.startsWith('//') || trimmed.startsWith('*') || trimmed.startsWith('/*')) continue;
if (/^\+\s*['"`]/.test(trimmed) || /^['"`]/.test(trimmed)) continue;
```

> 取舍：宁可判据窄一点，也不要靠白名单去吞注释噪音 —— **白名单一膨胀就没人看了**。

### 5.5 自检：4 个变异体全部判红

| 变异 | 结果 |
|---|---|
| 在 CoreStore 加一条删 `home` 的调用（未登记） | ✅ 判红 |
| 把白名单文件的删除参数换成 `home/sessions` | ✅ 判红（参数形态卡住） |
| 删掉布局契约那句话 | ✅ 判红 |
| 让 `evict()` 去删 `home` | ✅ 判红 |
