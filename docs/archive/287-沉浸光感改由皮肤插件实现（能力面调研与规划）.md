## 0. 结论先行

| 判断 | 结论 |
|---|---|
| 用户"刷新时能看到皮肤"说明什么 | **皮肤本身是好的**，只是被我们的玻璃 `!important` 盖住（`docs/286`） |
| "思路错了"这个直觉对不对 | **对了一半** —— 用垫片「抢列背景」这条路确实走歪了 |
| 皮肤插件能不能实现沉浸光感 | **能，但有一个硬约束**（见 §3） |
| 推荐路线 | **皮肤插件接管配色 + 材质，DSHM 停止注入自己的玻璃 CSS** |
| 最大风险 | 皮肤用 `overrideTokens` 走**变量层**，仍绕不开"官方列有实色背景"这件事 |

## 1. 为什么这个直觉是对的：两条路的本质差异

| 维度 | 现在的垫片（`docs/283`） | 皮肤插件 |
|---|---|---|
| 注入位置 | DSHM 的 ArkTS 往 WebView 里**注入 `<style>`** | 走**官方插件体系**（`dsh.client` 契约） |
| 与官方的关系 | **对抗**：`!important` 抢列背景 | **协作**：用官方开放的 API |
| 配色来源 | **写死** `rgba(214,223,240,0.86)` | **主题变量**（`overrideTokens`） |
| 第三方皮肤 | **冲突**（`docs/286`：被 `!important` 盖死） | **同类**，天然共存 |
| 用户可见性 | 用户既看不见也控制不了 | **插件市场可见、可开关、可切换** |
| 调试手段 | 只能靠日志探针 | 有 slot / theme 面板，UI 里直接调 |

**一句话**：垫片是"从外面硬撬"，皮肤是"按官方规则参与"。前者注定和所有主题打架，
后者本来就是主题体系的一员。

## 2. 插件能力面（实读，`@iasiv5/dsh-skins@1.5.19` + 核心树）

### 2.1 插件声明（`package.json` 的 `dsh` 字段）

```json
"dsh": {
  "engines": { "dsh": ">=0.2.0-rc.1 || >=0.2.1-rc.1" },
  "bundle": { "patch": "./cordis.patch.yml" },
  "client": {
    "inject": ["@deepseek-ai/dsh-client-runtime", "@deepseek-ai/dsh-client-connection",
               "@deepseek-ai/dsh-client-locale", "@deepseek-ai/dsh-client-ui-theme",
               "@deepseek-ai/dsh-client-ui-conversation", "@deepseek-ai/dsh-client-ui-sidebar"],
    "platform": "web"
  }
}
```

**要点**：`platform: "web"` + `client.inject` 声明依赖 ⇒ 这是**正规的 Web 客户端插件**，
不是 hack。DSHM 侧不需要改任何 ArkTS 代码。

### 2.2 宿主侧（`lib/index.js`，Node 环境）

直接 `import { … } from "node:fs"` / `node:path` / `node:crypto`
（`copyFileSync` / `mkdirSync` / `statfsSync` / `createHash` …）
⇒ **可以做持久化**（皮肤包解压、用户选择落盘、配额检查）。

### 2.3 客户端侧（`lib/client.js`，Web 环境）——关键 API

| API | 用法（实读） | 对沉浸光感的价值 |
|---|---|---|
| **`ctx.theme.overrideTokens(source, tokens)`** | `:731` `ctx.theme.overrideTokens(\`dsh-skins/${skin.id}\`, effects.tokenOverrides)` | **核心**：批量覆写设计令牌（含 `background` 类） |
| `ctx.theme.setTheme(id)` | `:2008` | 切内置 light/dark |
| **`ctx.slots.inject(name, fn)`** | `:654` / `:2150` | **往官方插槽塞自绘组件**（见 2.4） |
| `ctx.slots.register({name, priority}, component)` | `:631` | 注册组件 |
| `ctx.slots.entries(name)` | `:620` | 查已注册项与优先级 |
| `ctx.effect(fn, label)` | 多处 | 生命周期，自动释放 |
| `ctx.locale.register()` | — | 国际化 |
| `ctx.on(...)` | — | 事件订阅 |

### 2.4 已知插槽名（皮肤实际在用）

```text
sidebar.brand.mark           侧栏品牌标记
sidebar.brand.name           侧栏品牌名
conversation.hero.brand.mark 会话空白页品牌标记
sidebar.footer.action        侧栏底部动作
sidebar.workspaces           侧栏工作区
```

⇒ **能精确插到侧栏的多个位置**，这是垫片做不到的（垫片只能整列盖一层）。

### 2.5 注入原始 CSS 的能力（皮肤也在用）

```js
// :558-561  与  :2128-2132
tag = document.createElement("style");
tag.dataset.plugin = "dsh-skins";      // 带归属标记，便于排查/清理
tag.dataset.pluginCss = id;
document.head.appendChild(tag);
```

⇒ **能注入任意 CSS**，包括 `backdrop-filter`。**能力上完全够做玻璃。**

### 2.6 官方主题令牌契约（`dsh-client-ui-theme` `:1636`）

```text
overrideTokens stacks partial token layers over the active theme
without touching the registry.
```

令牌目录里与材质直接相关的：

| 令牌 | 说明（官方原文） |
|---|---|
| `--dsw-alias-bg-base` | 主背景 |
| `--dsw-specific-sidebar-fill` | "Sidebar column and title-row background." |
| `--dsw-menu-backdrop-filter` | `blur(40px) saturate(150%)`（**官方菜单就是这么做的**） |
| `--dsw-static-neutral-bluish-*` | 中性色阶 |

**关键发现**：**官方自己就在用 `backdrop-filter` 做菜单毛玻璃**（`--dsw-menu-backdrop-filter`）。
说明这条路**官方认可、且已在生产使用** —— 我们的方向正确，只是实现方式太粗暴。

## 3. 硬约束：为什么"皮肤路线"也不是银弹

### 3.1 约束一：变量层赢不了 `!important`

`overrideTokens` 写的是**CSS 变量**。官方列规则是：

```css
.pI_x6G_centerCol { background: var(--dsw-alias-bg-base) }
```

我们知道皮肤改这个变量 ⇒ 列变色 ⇒ **这条路是通的**（这正是皮肤能显示的原因）。

**但**：任何一方写了 `background: … !important`，变量层立刻失效（`docs/286` 的教训）。
⇒ **皮肤方案必须遵守"绝不写 `!important` 抢官方属性"的纪律**，否则重蹈覆辙。

### 3.2 约束二：白底上模糊无意义（老问题依旧）

`docs/282` §8 的物理事实不变：**背景是纯白 ⇒ `blur()` 模糊白色仍是白色**。
皮肤能改的是**颜色**（让底色不再是纯白），但**改不了"背后没有可模糊内容"**这件事。

⇒ **沉浸光感的观感上限由"背后有没有东西"决定，不由实现方式决定。**
这条不会因为换成插件而改变，必须向用户说清楚。

### 3.3 约束三：`backdrop-filter` 只能"透出背后"，不能"凭空造质感"

玻璃要好看，`backdrop-filter` 背后必须有**可模糊的内容**（滚动文字、图片、色块）。
纯色画布 + 玻璃 = 一层半透明色膜，仅此而已。

**⇒ 真正的改善方向不是"玻璃更强"，而是"让背后有内容"** —— 例如：
壁纸（皮肤已经在做 `#root::before` 背景图！）、渐变、噪点纹理。
**这恰恰是皮肤插件最擅长的领域。**

## 4. 规划：三条路线，推荐 R2

### R1 · 最小可用（先止血）

**目标**：让皮肤不再被玻璃盖住。

| 步骤 | 动作 |
|---|---|
| 1 | DSHM 玻璃规则检测到 `body[data-dsh-*-skin]` 时**整体不注入**（`docs/286` 方案 A） |
| 2 | 保留现有垫片作为"无皮肤时的默认" |
| 3 | 加门禁：皮肤存在时玻璃让路 |

- **工作量**：小（改一处判断 + 一条门禁）
- **收益**：皮肤立刻完整呈现，用户不再看到"被遮住"
- **代价**：该皮肤下没有玻璃

### R2 · 推荐：皮肤即沉浸光感（用户提的新思路）

**目标**：由皮肤插件统一负责"配色 + 材质 + 背景"，DSHM 不再有自己的玻璃 CSS。

```text
┌─────────────────────────────────────────┐
│ 皮肤插件（本仓或第三方）                  │
│  ├─ ctx.theme.overrideTokens  配色层     │
│  ├─ <style> 注入 backdrop-filter 材质层  │
│  ├─ #root::before 背景图/渐变（有内容了！）│
│  └─ ctx.slots.inject  局部装饰           │
└─────────────────────────────────────────┘
        ↓ 官方列规则 var(--dsw-alias-bg-base)
┌─────────────────────────────────────────┐
│ 官方 .centerCol / .sidebarCol            │
│  background: var(--dsw-alias-bg-base)    │  ← 变量传导，无 !important
└─────────────────────────────────────────┘
```

| 步骤 | 动作 | 判据 |
|---|---|---|
| 1 | 写一个 `dshm-glass` 插件骨架（`package.json` `dsh.client.platform=web` + `cordis.patch.yml`） | 能装、能挂载、日志有记录 |
| 2 | 用 `ctx.theme.overrideTokens` 把 `--dsw-alias-bg-base` / `--dsw-specific-sidebar-fill` 改成**半透明** | 列不再是实色 |
| 3 | 注入 `<style>` 给列加 `backdrop-filter`，**不写 `background`** | 列半透明 + 模糊生效 |
| 4 | 加 `#root::before` 背景（壁纸/渐变/噪点） | **背后终于有内容可模糊** |
| 5 | 提供 UI 开关（`ctx.slots.inject`） | 用户可调强度/开关 |
| 6 | DSHM 侧**删掉**自己的玻璃 CSS | 无双写、无冲突 |

- **工作量**：中（插件骨架 + 令牌映射 + 调参 UI）
- **收益**：与所有皮肤天然共存；用户可开关；观感上限**实质提高**（因为有了背景内容）
- **风险**：需要真机验证 ArkWeb 对令牌层 `backdrop-filter` 的表现

### R3 · 融合（把玻璃做进皮肤体系）

在 R2 基础上，让**第三方皮肤也能声明材质**（如皮肤 JSON 里加 `material: { blur, opacity }`），
DSHM 提供通用渲染层。**这是生态级方案，工作量最大。**

## 5. 推荐执行顺序

```text
① R1 止血（皮肤不被遮）           ← 立刻可做，1 处判断
        ↓
② 重启验证皮肤本身是否正常         ← 需要用户配合
        ↓
③ R2 骨架（插件能跑起来）          ← 建议先做最小闭环
        ↓
④ R2 材质层（令牌 + backdrop）      ← 核心
        ↓
⑤ R2 背景内容（#root::before）      ← 观感质变的关键
        ↓
⑥ DSHM 删掉自有玻璃 CSS            ← 收尾，去双写
```

**⚠️ 第 ⑥ 步之前，不要删 DSHM 的玻璃** —— 否则中间态会出现"两边都没有"的空窗。

---

## 6. 必须向用户说清的预期（避免再次"看不出来"）

| 期望 | 现实 |
|---|---|
| 「换成插件就能明显看出玻璃」 | **不一定**。纯白底 + 无背景内容时，玻璃仍是一层淡色膜 |
| 「沉浸光感」是什么 | **不是**"更强的模糊"，而是**"背景有内容 + 材质透出内容"** 的整体效果 |
| 明显的观感从哪来 | **来自背景图/壁纸/渐变**（R2 第 ⑤ 步），不是来自调大 blur |
| 皮肤为什么一刷新就能看见 | 因为皮肤**有背景图**（`#root::before`）—— 这恰恰证明"背景内容"才是观感来源 |

> **这一条是本轮调研最有价值的结论**：
> 用户"刷新时能看到皮肤"不是巧合，而是因为皮肤**真的在画背景图**。
> 沉浸光感要复现这种"看得见"，路线也一样 —— **得先有背景，再谈材质**。

## 8. 一句话交接

**你的直觉对了一半**：垫片"抢列背景 + `!important`"这条路确实走歪了，它注定和所有主题冲突；
**皮肤插件路线在能力上完全可行**（`ctx.theme.overrideTokens` + `<style>` 注入 + `slots.inject`
三件套都在，官方自己就用 `--dsw-menu-backdrop-filter` 做菜单毛玻璃）。

**但要认清一个物理事实**：玻璃的观感上限不取决于实现方式，而取决于**背后有没有可模糊的内容**。
用户"刷新时能看到皮肤"正是因为皮肤在画背景图 —— **这也指明了正确方向：先有背景，再谈材质。**

**建议**：先 R1 止血（皮肤不被遮），再走 R2（皮肤插件接管配色 + 材质 + 背景），
最后删掉 DSHM 自有玻璃。
