## 1. 侧栏：前两次为什么没修好

| 轮次 | 改了什么 | 为什么不够 |
|---|---|---|
| docs/325 | 纯函数改为「没存过 ⇒ 常驻展开」 | 规则对，但**不是根因** |
| docs/330 | 收起不再持久化（不落盘、启动不读回） | 也对，但**仍不是根因** |

真机证据：`/data/storage/el2/base/haps/entry/preferences/` 下**根本没有 sidebar 相关的偏好文件**
⇒ `sidebarStored` 一直是 `undefined` ⇒ 纯函数一直返回 `true`。
**展开判定从来就是对的**，问题在别处。

### 1.1 真正的根因：`browserInSidebar` 用了「形态默认」而不是「实际呈现」

```ts
// entry/src/main/ets/pages/Index.ets（修复前）
browserInSidebar: shellTracksOf(this.mode).sidebar === TrackPresentation.PANEL,
```

而 `shellTracksOf(DOUBLE).sidebar` **恒为 `RAIL`**。

于是**双栏档**（平板竖屏、以及平板/PC 把窗口拉窄一点）下：

- 侧栏的真实呈现是 `PANEL`、宽度 240vp、**确实是展开的**；
- 但 `browserInSidebar` 判成 `false` ⇒ 侧栏里**不挂"工作区 → 会话树"**；
- 用户看到的就是一条**空的窄条** —— 与"侧栏被收起"体感完全一样。

这也解释了为什么前两次改偏好的持久化毫无效果：**判定链一路都是对的，只是内容没挂进去**。

### 1.2 修法

```ts
browserInSidebar: sidebarPresentationOf(this.mode, sidebarExpandedForMode(this.mode, this.sidebarStored))
  === TrackPresentation.PANEL,
```

统一走「**实际生效的呈现**」，与 `navPanel()` / `sidebarTrackWidthVp` 同源。
并清掉因此变成零使用的 `shellTracksOf` import（`check-dead-code` 抓到）。

> 全仓复扫确认：`shellTracksOf` 在视图层已无其它消费点，不存在同类写法。

## 2. 连接：这一次找到的是**自动重连进不去**

### 2.1 上一轮（docs/330）的缺陷

docs/330 加了"首次连接 12 秒宽限"：失败时**故意把 `phase` 留在 `CONNECTING`** 等重连。
但 `connect()` 第二行的旧守卫是：

```ts
if (this.phase === HubPhase.LIVE || this.phase === HubPhase.CONNECTING) {
  return this.phase === HubPhase.LIVE;   // ← CONNECTING ⇒ 直接 false
}
```

⇒ 宽限期虽然在"等"，**新 token 到达后根本进不来 `connect()`**，12 秒后必然降级。
而"点一下重连"之所以有效，是因为手动重连先 `disconnect()` 把 phase 清成 `IDLE`。
**这就是"点一下才连上"的机制。**

修法：并发闸与呈现状态分开。

```ts
if (this.phase === HubPhase.LIVE) return true;   // 已连上就不重连
if (this.connecting) return false;               // 并发闸（独立标志）
this.connecting = true;
```

`connecting` 在**全部 5 个出口**复位：authenticate 失败、start 失败、成功、`disconnect()`。

### 2.2 还有一处：首次失败被当成"已定论"

`Index.ets` 的自动重连回调里，原来**无条件** `connectSettled = true` + 写 `hubError`。
而这段代码自己的注释就写着「先到的那份凭据**通常是过期的**」：
页面 250ms 就能读到落盘的旧 token，dsh 每次启动都换新 token。

⇒ 旧 token 的第一次失败**立刻**把「连接异常」横幅摆出来，而 250ms 后新 token 就到了。

修法：
- 失败时 `connectSettled = ok`（失败仍显示"正在连接"），原因先存进 `pendingConnectError`；
- 轮询窗口结束时 `settleAutoConnect()` 才做结论：**已 LIVE 就什么都不显示**，
  否则才把原因交给横幅。

## 3. 思考过程翻译不再默认开启

用户口径：「官方插件里面的思考过程翻译一直是启用的，默认都是关闭，**不要给用户预设这些个性化设置**」。

根因：它被写进了 profile 的默认 `dsh.profile.bundles`，于是每个用户一装就有翻译控件。

修法：

```json
"bundles": ["@deepseek-ai/dsh-base", "@deepseek-ai/dsh-web-app"],
"removeBundles": ["@deepseek-ai/dsh-experimental-cot-translation-bundle"]
```

> **为什么还要 `removeBundles`**：设备 profile 是「种子 ∪ 设备已有」的并集，
> 只在种子里删掉的话，**已经装过它的设备仍会继续启用**。
> 用户想用时仍可在「设置 → 插件 → 更多」里自己打开（它在市场的 `MORE_BUNDLES` 里）。

`check-cot-translation` 的判据随之**反转**（原来要求"必须启用"）：
现在是「默认 bundles 不得包含它」+「removeBundles 必须包含它」，
两个变异体（塞回 bundles / 从 removeBundles 删掉）都必须判红。

全仓复扫 profile：没有其它预设个性化（主题 / 语言 / 目标语言等）的配置项。
