## 1 结论（一句话）

`docs/142` §7「按官方路线把三条 `system_basic` 声明从源码撤掉」的**前提不成立**：
三条权限**各自独挡一面**，撤哪条瘫哪块。其中 域权限 的后果已在 `docs/143` 钉死；
本档补齐另外两条 —— **全盘访问权限 + 用户文件读写权限 是"用户目录的通行证"**，
撤掉后用户在 `~` 下的**两个已登记工作区**变成不可达 ⇒ 侧边栏列表空、
终端 pty 子进程 `chdir` 直接 `EACCES`。

修法：**源码回滚为全量声明 11 条**（功能面），**发布 / AGC 档在签名之前自动摘除**（合规面）——
这正是 `docs/142` §3 设计的正解，§7 改源码是走偏了。

## 2 症状与根因（全部为原文读数，不是推断）

### 2.1 症状一：终端一开就死

设备截图（`snapshot_display` + `hdc file recv`）画面原文：

```
进程已退出 (1)
chdir(2) failed.: Permission denied
```

`chdir(2) failed.` 是 **node-pty** 的原句（`perror`），源码位置：

| 项 | 值 |
|---|---|
| 报错点 | `dist/core/work/…/node_modules/node-pty/src/unix/pty.cc:419` → `perror("chdir(2) failed."); _exit(1);` |
| `cwd_` 从哪来 | `@deepseek-ai/dsh-terminal-bash/lib/index.js:1056` → `cwd: spec.cwd ?? await this.ctx.workingDirectory.ensure(spec.owner, spec.signal)` |

### 2.2 那个 `cwd` 到底是什么（RPC 直读）

```
POST /api/terminal/environment  {"agentId":"session-f1dcf1b0-…"}
→ {"ok":true,"value":{"cwd":"~/harness", …}}
```

**不是**宿主日志里那个"默认工作区"（`~/Download/com.dshm.dshclient`）。
会话的 cwd 是**会话头里记着的原始目录**（`dsh-working-directory` 的 sessionProjection：
`get() = stateOf(session,'workingDirectory') ?? defaultDirectory`），也就是用户当初建会话时的目录。

### 2.3 为什么这个目录现在不可达（同进程实测）

用 `/dshm-python/run-get` 在**宿主进程内**跑（同一 uid / 同一 SELinux 域）：

| 路径 | 读数 |
|---|---|
| `listdir('~')` | `PermissionError: [Errno 1] Operation not permitted` |
| `listdir('~/Download')` | `PermissionError: [Errno 1] Operation not permitted` |
| `listdir('~/Download/com.dshm.dshclient')` | **正常**（13 个条目） |
| `listdir('~/harness')` | `PermissionError: [Errno 1] Operation not permitted` |
| `chdir('~/harness')` | `PermissionError: [Errno 13] Permission denied` ← **与 §2.1 的 pty 报错逐字同因** |

⇒ 撤掉那两条权限后，应用**只剩**"经 `DocumentPickerMode.DOWNLOAD` 认领的 `Download/<包名>/`"这一块，
`~` 及其下**一切**（连 `listdir` 都）一律 `EPERM`。

### 2.4 症状二：侧边栏「工作区文件」空的根因（同一条）

`dsh/home/storages/workspace.json` 原文（**已登记的两个工作区全在用户目录下**）：

```json
"workspaces": {
  "efdcd677-…": { "path": "~/harness",    "title": "harness",
                  "sessionIds": [ … 12 条 … ] },
  "4041e097-…": { "path": "~/data/token", "title": "token",
                  "sessionIds": [ "session-bef46927-…" ] }
}
```

`dsh/home/sessions/` 下的分目录名也是按 cwd 编的：`--storage-Users-currentUser-harness--`（20 条会话）、
`--storage-Users-currentUser-data-token--`（7 条）⇒ 会话与工作区**共同指向同一个不可达根**。
列表要列的就是这些目录 ⇒ 空；`resolveWorkspaceDir()` 那个可写的工作区**没有被登记**
（`dshm-workspace-claim` 只在注册表为空时登记一次，注册表非空 ⇒ 干净短路，见 `docs/113`）。

### 2.5 为什么"官方等价路线"这次也救不了

官方答复给的平替是「picker 选目录 + `FILE_ACCESS_PERSIST` 持久化授权」。它成立，但**是"新授权"的路线**：

- 它只覆盖**用户重新选一次**的那个目录；
- 它**不会**改写已经登记的工作区路径、也不会改写**已存在会话头里记的 cwd**；
- 老会话的 cwd 仍是 `~/harness` ⇒ 除非让用户逐个重选（= 换工作区，等于把
  用户那 12 条会话的目录藏起来），否则终端与工作区文件**回不来**。

⇒ 这跟 `docs/143` 里 域权限 的判词同构：**官方那条是路径/授权约定，替代不了"全域可达"这件事本身。**

## 3 修法

### 3.1 源码回滚：三条受限权限**全量声明**（`entry/src/main/module.json5`）

| 项 | 改前（`docs/142` §7） | 改后 |
|---|---|---|
| `requestPermissions` | **8 条** | **11 条**（加回 用户文件读写权限 / 全盘访问权限 / 域权限） |
| 位置 | 域权限 单独一条 + 上方一段注释 | 三条连续，`用户文件读写权限(when=inuse)` / `全盘访问权限(always)` / `域权限(always)` |
| 注释 | 写着"另两条**仍撤**、官方等价路线成立" | **改写**：写明三条各自独挡一面、逐条读数、以及"发布档靠签名前摘除" |

`entry/src/main/resources/base/element/string.json` 同步加回两条 `reason`
（`perm_user_file_reason` / `perm_full_disk_reason`，理由与撤除前逐字一致）——不留孤儿引用。

### 3.2 发布链路：**签名之前自动摘除**（`tools/sign-release-hap.ps1` 新增 `[0]` 步）

源码全量声明以后，"直接签发布包"会踩 `docs/142` §1–§2 那条 `PERMISSION_ACL_RULE`（发布 profile
只授权 2 条 ACL）。故在 `[1] 发布签名` 之前插入 `[0]`：

- **`.hap` 输入**：调 `tools/strip-ungranted-acl-perms.mjs` 摘到临时件，签名用摘后件，
  **原文件不动**，签完删临时目录（`[3] 产物` 之后清理）。
- **`.app` 输入**：本脚本**不做容器内改写**（要重打包 `.app` 里的内层 hap），改为**先探测再判红** ——
  读出内层 hap 的声明、跑 `--dry-run`，**摘除数 > 0 就判红**并给出命令；读不出读数也判红。
  即：**绝不静默签出一个装不上的包**（fail-closed）。

工具本身幂等（对着 profile 比）：声明与 profile 齐了它摘 0 条。

### 3.3 装机脚本判据修正（`tools/update-device.ps1` 第 5 步）

`hdc install -r` 会**偶发回空输出**：现场 `(& $hdc install -r $Hap 2>&1 | Out-String)` 得到空串 ⇒
旧判据 `-notmatch 'successfully'` 当场判"安装失败"，可手动重跑同一条命令却 `rc=0` +
`install bundle successfully`（`docs/143` §7 记的就是这一次）。判据改为**三态**：

1. 回文含 `successfully` ⇒ ok；
2. 回文含 `fail` ⇒ fail；
3. **回空**（既非成功也非失败）⇒ 重跑一次；仍空就改用 `bm dump` 的 `updateTime` **正面判定**
   （那是安装/更新时刻的毫秒数，变了就说明这次真装上去了，不是猜）。
