## 1. 先更正我自己的一个错误

`297`/`298` 里我把 `@hms.core.deviceCloudGateway.cloudStorage` 当成了 Drive Kit。**它不是**。

| | `cloudStorage`（我之前用的） | Drive Kit（路线一） |
|---|---|---|
| 定位 | **开发者**云存储，数据归应用 | **用户**云空间，数据归用户 |
| 用户可见 | ❌ 不可见 | ✅ 在云空间 App 里能看到 |
| 前置 | AGC 建 **bucket（存储实例）** | AGC 开 Drive Kit 开关 + 签协议 |
| 鸿蒙 SDK | ✅ 有（`@hms.core.deviceCloudGateway.cloudStorage`） | ❓ **未确认** |

这也解释了为什么它要建 bucket —— **它是应用租的存储空间，不是用户自带的云空间**。

**实测佐证**：云调试里登录成功后，`cloudStorage` 报
`GetDefaultBucket result error` / `Query data row count:0` ⇒ **AGC 侧根本没有这个实例**，
不是代码问题。

## 2. 路线二（端云同步）的技术核对

### 2.1 SDK 事实（本机 `relationalStore` 实读）

| 项 | 事实 |
|---|---|
| `autoSync` | `DistributedConfig.autoSync: boolean`（since 10）—— 表级开关，true 则系统自动触发端云同步 |
| `cloudSync` | `RdbStore.cloudSync(mode, tables[], progress)`（since 10）—— 手动触发 |
| `cloudSyncEx` | `CloudSyncConfig { mode, enablePredicate?, predicate? }`（**since 26.0.0**）—— 26 新增，可按条件同步 |
| `stopCloudSync` | since 26.0.0 |
| 权限 | **`@permission` 零命中** ⇒ 不新增权限条目 ✅ |
| syscap | `SystemCapability.DistributedDataManager.CloudSync.Client` |
| 账号 | 依托系统已登录的华为账号，**应用无需自建登录页** |

⇒ **技术上路线二确实可用，且符合本仓权限铁律。**

### 2.2 但 DSHM 的会话**不是表**

上游 `dsh-session-persistence-jsonl` 的存储形态（源码实读）：

```text
sessions/--<cwd 编码>--/<sessionId>/session.vN.jsonl.zstd
```

**实测数据规模**（本机真实会话）：

```text
文件数     13
总字节     14,744,658  (14.7 MB)
平均       1,134,204   (1.1 MB)
最大       6,982,769   (7.0 MB)
```

⇒ 要把它们塞进关系型表，只有两条路：

| 做法 | 可行性 | 问题 |
|---|---|---|
| **A. 一个会话一行，TEXT 列存整份 zstd** | 勉强 | 单行 1–7 MB；RDB 单字段有上限，且**每次事件追加都要写整行** ⇒ 写放大严重；端云同步按行推送 ⇒ 每轮要传 MB 级 |
| **B. 把 JSONL 拆成事件表**（一行一个事件） | 可行 | **要改写上游持久化格式** ⇒ 违背"不 fork、不魔改 dsh"第一原则 |

**所以路线二不能"直接套用"，必须做适配层。**

## 3. 路线二的**可行改造路径**（这是本文的重点）

### 3.1 核心思路：**把"同步"和"存储"解耦**

不要让 RDB 成为会话的**存储格式**，而是让它成为**同步的信使**。

```text
会话文件（不可变 .jsonl.zstd）        ← 保持上游原样，一个字不动
        │
        ▼  同步代理（新增，Host 侧）
   ┌────────────────────────────┐
   │ 读会话 → 打包成 sync_unit   │
   │ 写进 RDB 表 sync_units      │
   └────────────────────────────┘
        │
        ▼  端云同步（系统负责）
   AGC 云侧表 sync_units
        │
        ▼  另一端拉取 → 还原成文件
```

### 3.2 表设计（最小可行）

```sql
CREATE TABLE sync_units (
  unit_id     TEXT PRIMARY KEY,   -- <workspaceId>/<sessionId>/<version>
  workspace   TEXT NOT NULL,      -- workspaceId（不是 cwd 绝对路径）
  session_id  TEXT NOT NULL,
  version     INTEGER NOT NULL,   -- 代际号（与上游 CANONICAL_LOG_FILENAME 同口径）
  sha256      TEXT NOT NULL,      -- 内容校验
  bytes       INTEGER NOT NULL,
  updated_at  INTEGER NOT NULL,   -- 毫秒时间戳
  payload     BLOB                -- .jsonl.zstd 原样字节
);
```

**关键设计决定**：

| 决定 | 理由 |
|---|---|
| **unit 粒度 = 一代（一个文件）** | 会话代际是**不可变**的 ⇒ 一次写入永不修改 ⇒ 天然适合同步，无写放大 |
| `payload` 用 **BLOB** 存**已压缩**的 zstd | 不再二次压缩；1 个 unit ≈ 一个代际文件 |
| `workspace` 用 **workspaceId** 而不是 cwd | 跨端路径不同（见 docs/301） |
| 带 `sha256` | 恢复前校验，防半截数据 |

### 3.3 为什么这样比"整会话一行"好

| | 整会话一行 | 按代际分 unit |
|---|---|---|
| 追加事件时 | 改一行 ⇒ 重写整个 MB 级字段 | **新增一个 unit** ⇒ 只写增量 |
| 同步传输 | 每次推整会话 | 只推**新代际** |
| 冲突 | 两端都改同一行 ⇒ 必冲突 | 不同代际互不干扰 |
| 与上游兼容 | 要改造 | **完全不改** |

### 3.4 仍有三个必须解决的硬问题

| # | 问题 | 说明 |
|---|---|---|
| 1 | **RDB 单字段/单行大小上限** | 7 MB 的会话在一个代际里可能就超限。**需要真机验证**（见 §5 的 P0） |
| 2 | **AGC 云侧表结构要手工建** | 官方明说「数据类型名称需与本地表名称一致、字段类型要对应」 |
| 3 | **首次全量 vs 后续增量** | 14.7 MB 首同步，之后只传新代际 |

## 6. 我的推荐

**先做第 0 步的 V1–V3（路线二验证），同时提工单问 V4（Drive）。**

理由：

1. **路线二是官方明确推荐给鸿蒙原生的**，且 SDK 权限面干净（零 `@permission`）
2. **路线一在鸿蒙上有平台风险**，在确认前投入是赌博
3. **V1–V3 是小成本高信息量**：两三天就能知道路线二能不能承载 7 MB 的代际文件
4. **已完成的登录 + 清单层两条路线通用**，不会浪费

**如果 V1 显示 RDB 存不下 7 MB 代际**，还有个退路：**把大代际切成多个 unit 分片**（`unit_id` 加 `part` 序号），这不改变架构，只是多一层切片。
