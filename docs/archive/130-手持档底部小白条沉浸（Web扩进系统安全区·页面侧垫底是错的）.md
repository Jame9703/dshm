# 130 · 手持档底部小白条「沉浸」（把 Web 扩进系统安全区；页面侧"垫底"是错的）

> **2026-10-18 后续修订：** 新版 Web 壳的底部使用统计栏改为固定定位后，
> “Web 自身也 expandSafeArea 到屏底”会让小白条压住统计栏。最终改为
> root / Stack / 覆盖层继续扩进安全区画底色，**Web 内容框止于安全区上沿**。
> 详见 `docs/187`；本档的避让读数、分档闸门与底色链仍有效。

> 用户原话：「接着适配一下手机平板端的小白条，你可以先查一下再动手」→（看到第一版截图后）「解决的问题是
> **手机平板端的小白条沉浸**的问题哦」。
> **性质：entry 侧一处功能**（`entry/src/main/ets/pages/WebApp.ets`：读底部避让 + 整条链各自
> `expandSafeArea`）+ 门禁 `tools/check-feature-wiring.mjs` 的一条改名与重钉。
> **无核心树改动 ⇒ `coreVersion` 不动**（仍 `0.2.1-alpha.1+dshm.28`）。
> 真机：手机 `62T0225B18039433`（`const.product.devicetype=phone`）覆盖安装（`hdc install -r`），
> home 指纹 `links=8 size=3440` 装前装后一致。

## 0. 一句话结论

| # | 事 | 结论 |
|---|---|---|
| 1 | 现象 | 手机底部那条手势区（小白条所在）原本**不属于页面**：官方壳的底色在 y=2734 处**硬切**，下面 98px 是窗口底色 `#FFFFFF`。见 §1 |
| 2 | 要的是什么 | **沉浸**：页面铺到屏幕最底，小白条浮在页面自己的底色上（= 系统桌面/原生应用那个观感）。见 §1.2 |
| 3 | 真根因 | Web 组件的框止于**安全区上沿**（`[0,269][1280,2734]`）：窗口内容区默认不含底部避让区，页面视口因此少 98px。**不是**页面不铺，**不是**被谁裁掉。见 §2/§4 |
| 4 | 修法 | 把手势区高度读出来（`max(TYPE_SYSTEM.bottom, TYPE_NAVIGATION_INDICATOR.bottom)` = 98px = 28vp）⇒ 让**整条容器链各自** `expandSafeArea([SYSTEM],[BOTTOM])`（根 Column / Stack / Web / 启动页覆盖层 / 错误覆盖层）⇒ Web 的框变成 `[0,269][1280,2832]`，页面视口 705 → 733 CSS px。见 §5 |
| 5 | 为什么"整条链" | SDK 明文：**`expandSafeArea` 只作用于当前组件、不向父/子传播**，且**设了固定宽高只能扩 TOP/START 且尺寸不变，按百分比定尺寸才可向下扩**。实测：只挂根容器时 Stack/Web 的框纹丝不动（仍 `y2=2734`）。见 §2 |
| 6 | **页面侧一个字都不该碰** | 第一版（错路 B）在页面里给"通高面板"加 `padding-bottom` 垫底 —— 真机实测**反而把壳挤矮 28px**（官方壳自己按 `env(safe-area-inset-bottom)` 预留了那一条），底部又露出窗口白。撤掉页面侧脚本后，侧栏底色一路铺到 y=2830。见 §3.2/§4.2 |
| 7 | 验收 | `uitest dumpLayout`：Web `[0,269][1280,2832]`；像素：侧栏 `#F9FAFC` 从 y=269 **连续**到 **2830**（不再在 2734 硬切）；`diag-bottom-inset`：`armed=true / indicatorBottom=98 / apply bottomPx=98 vp=28`。见 §6 |
| 8 | 待验 | **PC/2in1 回归未做**（无设备；代码路径 `isHandheldForm()` 收口、`bottomInsetVp=0` ⇒ `expandSafeArea([],[])` = API 明文的无效果）、**平板未验**（同一分档，但屏更宽/横屏形态的自测待做）。见 §7 |

## 1. 现象与"要的到底是什么"

### 1.1 真机读数（改前）

手机 `62T0225B18039433`，屏 `1280×2832`px，density 3.5：

| 量 | 值 | 出处 |
|---|---|---|
| 窗口 | `[0,0][1280,2832]`（`origBounds`） | `uitest dumpLayout` 的 `root` 节点 |
| 页面根 | `[0,137][1280,2734]` | 同上（137 = 状态栏） |
| Web | `[0,269][1280,2734]`（269 = 137 + 顶栏 132） | 同上 |
| 底部避让 | `TYPE_SYSTEM.bottom = 0`、`TYPE_NAVIGATION_INDICATOR.bottom = 98` | `win.getWindowAvoidArea()`，落盘 `files/diag-bottom-inset` |
| 页面视口 | `innerHeight = 705` CSS px（= 2467/3.5） | 页面侧回报 |
| 页面底边底色 | 侧栏 `#F9FAFC` 在 **y=2734 硬切**，下接窗口底色 `#FFFFFF` | `snapshot_display` 像素采样 |

**判据（谁在报数）**：底部那一条在**手势导航**下报在 `TYPE_NAVIGATION_INDICATOR`（98），
`TYPE_SYSTEM` 报 0；三键导航时反过来。⇒ 取两者较大者，**不能只听 `TYPE_SYSTEM`**
（只听它这条功能在手机上就是死的）。

### 1.2 「沉浸」= 页面铺到屏底，而不是"补一条同色带子"

第一版做的是"在安全区里补一条与上方内容同色的带子"（ArkTS 侧按页面报回的底色画一条 Row）。
**用户要的不是这个**：带子再准，最底下那一段也还是"应用之外的一条"；原生应用的观感是
**壁纸/页面铺到屏幕最底，小白条浮在上面**。⇒ 必须让**页面自己**占满那 98px。

## 2. 平台事实（`sdk/default/openharmony/ets/component/common.d.ts` 原文，本机 DevEco 自带 SDK）

`expandSafeArea(types?: Array<SafeAreaType>, edges?: Array<SafeAreaEdge>)`（:18071 起）：

1. **「When using expandSafeArea to expand the drawing of a component, avoid setting fixed width and
   height values (except percentages). If fixed width and height values are set (including `auto`),
   the edges for expanding the safe area can only be `[SafeAreaEdge.TOP, SafeAreaEdge.START]`, and the
   size of the component remains unchanged after safe area expansion.」**
   ⇒ 向下扩必须**按百分比定尺寸**（本页根容器/Stack/Web 都是 `'100%'`）。
2. **「The **expandSafeArea** attribute only affects the current component and does not propagate to
   parent or child components. Therefore, all relevant components must be configured individually.」**
   ⇒ 只挂根容器**不够**（§4.1 实测）。
3. **「When **expandSafeArea([],[])** is used with empty arrays, the setting has no effect.」**
   ⇒ PC/2in1 档（`bottomInsetVp = 0`）传空数组 = 与改动前**逐字相同**，这是"不碰 PC"的依据。
4. `SafeAreaType.SYSTEM` = 「Default area of the system, including the status bar and **navigation bar**」
   ⇒ 底部那条归它管（真机也确实按 98px 生效）。
5. 「prerequisites … the settings take effect only if its boundaries overlap with the safe area」
   ⇒ 组件底边本来就压在安全区上沿（`y=2734`），条件天然满足。

## 3. 走过的两条错路（都真机验过，留档避免重走）

### 3.1 错路 A：在安全区里补一条"同色带子"（第一版）

ArkTS 侧按页面报回的**最底一行底色**（`parseBottomRuns`：把页面底部按列切成若干段、各自取色）
画一条 `Row`，`hitTestBehavior(None)` 不吃事件。**能画对颜色，但答的不是用户的问题**：
那一段仍然是"应用之外的一条"，不是沉浸（§1.2）。

### 3.2 错路 B：页面侧"垫底"（`BOTTOM_INSET_SHIM_JS`，第二版）

思路：ArkTS 把避让高度给页面（同步桥 `bottomInsetPx()`），页面给"通高面板"加
`box-sizing:border-box; padding-bottom:28px` —— 底色照旧铺满（padding 属背景盒），内容被垫起来。

**真机实测：反而把壳挤矮了。** 官方壳自己就按 `env(safe-area-inset-bottom)` 预留了那一条
（它的外层容器 733 高、带底色的是内层），我们在 `#root` 上加 `padding-bottom` ⇒ 它的**内容盒**
变成 705 ⇒ 壳的底色又只铺到 705 ⇒ 底部重新露出窗口白（`#FFFFFF`）。
⇒ **页面侧一个字都不该碰**：壳自己把这件事做对了，我们只需要把**窗口/组件**的框给够。

### 3.3 顺带排除：`avoidVisibleViewportBottom(0)` 无必要

`webview.WebviewController.avoidVisibleViewportBottom(h)`（`@ohos.web.webview.d.ts:4834`，`@since 20`）
是"把可见视口上抬 h"的口子。实测把 Web 的框扩到 2832 后，**不调它**页面视口就已经是
`innerHeight = deh = bch = vv = 733`（`meta=width=device-width, initial-scale=1`、`dpr=3.5`）
⇒ 没有"ArkWeb 自己在避让"这回事，**故本轮不留这一句**（也免掉文档里那条
"与可编辑区同用会把键盘避让模式改成 `OVERLAYS_CONTENT`"的副作用）。

## 4. 真机实测：一步一步把"到底哪一段没画出来"钉死

### 4.1 只挂根容器 ⇒ 子组件纹丝不动

给根 `Column` 挂 `expandSafeArea([SYSTEM],[BOTTOM])`（`height('100%')` 是百分比 ⇒ 允许向下扩）：

```
root   [[0,137][1280,2832]]     ← 根容器自己的框确实伸下去了
  Column [[0,137][1280,2832]]
  Stack  [[0,269][1280,2734]]   ← 子组件**一点没动**（SDK 第 2 条）
    Web  [[0,269][1280,2734]]
```
⇒ 印证"不向子组件传播"，须**各自挂**。

### 4.2 品红探针：页面到底画没画到屏底

在页面里插一个 `position:fixed;left:0;right:0;bottom:0;height:40px;background:#FF00FF`（临时探针）：
**屏底 `y=2692..2832` 整段变品红** ⇒ 页面**能**画到屏底，`position:fixed` 的 `bottom:0`
也落在 733 上 ⇒ 页面视口本来就是 733。**排除**"被父容器裁掉""窗口不在全屏""ArkWeb 少画一段"
三种猜测，把矛头指回**我们自己在页面里加的那点样式**（§3.2）。

### 4.3 撤掉页面侧脚本 ⇒ 沉浸达成

```
x=20  : y=2730 #f9fafc  y=2740 #f9fafc  y=2760 #f9fafc  y=2790 #f9fafc  y=2810 #f9fafc  y=2830 #f9fafc
x=640 : y=2730 #ffffff  y=2740 #ffffff  y=2760 #ffffff  y=2790 #ffffff  y=2810 #eaeaea  y=2830 #ffffff
                                                                          ↑ 小白条本体（系统绘制）
```
侧栏底色**一路铺到 2830**（改前在 2734 硬切）；主区白也铺到底；小白条浮在页面之上。
侧栏底部那颗 `...` 图标仍在小白条**上方**（壳自己的 `env()` 预留把内容挡住了手势区）✓。

## 5. 实现（改了哪几行）

`entry/src/main/ets/pages/WebApp.ets`（**纯 ArkTS，无核心树改动**）：

| 处 | 形状 |
|---|---|
| `@State bottomInsetVp` | 底部避让高度（vp）；`0` = 不接管（PC/2in1 或没有避让区） |
| `private bottomInsetArmed` | 分档闸门：只在 `isHandheldForm()` 为真时接管；读数失败即收手 |
| `applyBottomAvoid(win)` | 读数（两个类型取较大者）→ 落地 → `win.on('avoidAreaChange', …)` 订阅 |
| `readBottomAvoidPx(win)` | `max(TYPE_SYSTEM.bottom, TYPE_NAVIGATION_INDICATOR.bottom)`；落盘 `files/diag-bottom-inset` |
| `applyBottomInsetPx(px)` | 幂等（同值不重排）；`px2vp` 后写进 `bottomInsetVp` |
| `bottomSafeAreaTypes()/Edges()` | `bottomInsetVp > 0 ? [SYSTEM] : []` / `? [BOTTOM] : []` |
| `build()` | **5 处各自挂**：根 `Column`、`Stack`、`Web`、启动页覆盖层、错误覆盖层（各自注释写明"整条链"的理由） |

分档口径与既有端侧功能**同源**（`isHandheldForm()`：`const.product.devicetype ∈ {phone, tablet}`），
⇒ PC/2in1 上 `bottomInsetArmed` 恒假、`bottomInsetVp` 恒 0 ⇒ 传空数组 ⇒ 与改动前一致。

## 7. 未做 / 待验

1. **PC/2in1 回归**：无设备。道理上"传空数组 = 无效果"，但**按本项目纪律要真机复验**（用户明确要求
   "别把 PC 端改坏"）⇒ 等 PC 接上后跑一遍 `.\tools\device-acceptance.ps1` + 三端自检。
2. **平板**：与手机同分档，但屏宽/横屏形态的自测未做。
3. **不做**：把页面侧垫底脚本留下来当"兜底" —— 已实测它会**反向**破坏（§3.2），故整条删除，
   不留半开状态；`.ets` 里那 4 处 `token-exempt` 注释随第一版带子一起消失，未新增裸值。
4. **已知边界**：`expandSafeArea` 明文说"非安全区里的点击**可能被系统拦截**" —— 那 98px 里本来就
   只有系统手势（上滑回桌面/切换），归系统优先是**期望行为**，不是缺陷。
