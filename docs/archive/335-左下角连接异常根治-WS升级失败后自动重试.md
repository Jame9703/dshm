## 1. 现象

PC / 手机 / 平板三端冷启动，左下角恒显示「连接异常，刷新重试」（点一下手动重连又能好）。
换云调试**全新未用过的设备**同样复现 ⇒ 不是设备问题。

## 2. 排除过程（全部有实测依据，不是推断）

| 怀疑方向 | 验证方式 | 结论 |
|---|---|---|
| Host 拒绝升级 | 用真实 token + cookie，逐字节照 ArkWeb 的头打 `/api/remote.mux` | ❌ 排除：返回 **`101 Switching Protocols`** |
| 认证 / token | 同上（401 vs 303 对照） | ❌ 排除：token 有效，cookie 224B 正常下发 |
| Origin 校验 | 4 种 Origin（带端口/无端口/ws:// 多值/null）实测 | ❌ 排除：多值补丁生效，任一同源即通过 |
| 权限被删（17→15） | 09:53 的 dshm.98 日志（**权限未删**）同样 ERR_WS_UPGRADE | ❌ 排除：不是权限引起 |
| 1.1.6 → 1.1.7 改坏了 | 解开 1.1.6 包（+dshm.96）与 +dshm.103 逐文件 sha256 对比 | ❌ 排除：**连接代码、前端 dist 94 文件逐字节相同** |
| 会议模式剥离 | 14:32 的 +dshm.102（剥离前）同样 ERR=2 | ❌ 排除：剥离前就有 |

**结论：以上全部排除，是三端共有的一个上游缺陷 + ArkWeb 行为叠加。**

## 3. 真因（毫秒级证据）

日志逐毫秒对照（`com.dshm.dshclient/DSHM-NODELIVE`）：

```
09:11:24.550  ACCEPT #10 127.0.0.1:40010
09:11:24.551  IN-UPGRADE GET /api/remote.mux ... origin=http://127.0.0.1:3120
              URLRequestCanceled error:ERR_WS_UPGRADE(-173)
```

Host 收到升级请求后 **1ms 内**就被取消，`ws.handleUpgrade` 来不及写出 101
⇒ **ArkWeb 网络栈自己 abort**，不是 Host 拒、不是网络、不是 token。

此后**整份日志再无任何 ACCEPT / UPGRADE** —— 关键不在"连不上"，而在**失败后永不重试**。

### 上游缺陷链

```js
// ① maintain() 失败后只置 failure，不排下一次
task.then(() => { this.keepAlive = void 0; });   // ← 到这就停了

// ② 唯一重启入口是 onReconnectRequested，它只在 loop() 的 retry 分支触发
onReconnectRequested: () => this.streams.reconnect()

// ③ 而 loop() 可能永远卡在 offline 分支
if (!this.networkAvailable && !this.immediateRetry) {
  this.emitState("disconnected");           // ← 左下角「连接异常」
  await waitForAbort(retryDelay.signal);    // ← 只有 online 事件能唤醒
}
// 而 setNetworkAvailable() 首行：networkAvailable 初值 true，再报 true 直接 return
```

⇒ **一次 WS 失败 = 永久不再尝试**。

## 4. 修法

`tools/pack-core.mjs` 新增 `patchRemoteStreamSelfHeal()`，改 `dsh-api-gateway/lib/client.browser.js`：

```js
task.then(() => {
  this.keepAlive = void 0;
  this.scheduleSelfHeal();      // ← 新增：失败后自己排下一次，不等 loop()
});

scheduleSelfHeal() {
  if (!this.running || this.disposed) return;
  if (this.socket?.readyState === 1) { this.selfHealAttempt = 0; return; }
  if (this.selfHealTimer !== void 0) return;      // 防重入
  const attempt = ++this.selfHealAttempt;
  const cap = Math.min(10000, 500 * (2 ** (attempt - 1)));
  const delay = cap / 2 + Math.random() * (cap / 2);   // 官方退避口径
  this.selfHealTimer = setTimeout(() => { this.selfHealTimer = void 0; this.maintain(); }, delay);
}
```

- 连上（`opened`）即复位退避并清定时器；
- 新增诊断埋点 `noteCarrier()`：把 ArkWeb 的 `error`/`close` 的 `code`/`reason`/`onLine` 打到
  `[DSHM-WS]` 日志行 —— **下一次如果还失败，这行会直接给出引擎侧原因**。

## 8. 构建环境备注（重要，供后续会话）

本机 Node 默认启动会崩：`Fatal error ... 12 == (*__errno_location())`（12=ENOMEM）。
**根因是内核拒绝 JIT 所需的 `mmap(RWX)`/`mprotect(RX)`**（AGENTS.md 已记录该端侧约束）。

本机可用的完整构建命令：

```bash
export PATH=/data/service/hnp/hmos-clt.org/hmos-clt_1.0.0/node/bin:$PATH
export NODE_OPTIONS="--jitless"
export DEVECO_SDK_HOME=/data/service/hnp/hmos-clt.org/hmos-clt_1.0.0/sdk

node --jitless tools/pack-core.mjs --place-in-app

# 合并三端出包：临时把 phone 的 applyToProducts 改为 ["default"]，
# 出包后**必须还原**（本文件 §6 的包就是这样出的）
/data/service/hnp/hmos-clt.org/hmos-clt_1.0.0/hvigor/bin/hvigorw \
  assembleApp -p product=default -p buildMode=release --no-daemon
```

`pack-core.mjs` 的两处 `node --check` 子进程也已补 `--jitless`
（`SYNTAX_CHECK_FLAGS`），否则语法校验会假红成 V8 崩溃文本。
