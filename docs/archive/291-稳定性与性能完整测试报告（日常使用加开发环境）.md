## 5. 缺陷详析（本报告最重要部分）

### 5.1 🔴 缺陷 1：`__DSHM_BRIDGES__` 高频报错（**9,258 次，且仍在快速增长**）

**现象**（`node-output.log`，全程）：

```text
[ohos_nweb/src/cef_delegate/nweb_handler_delegate.cc:5132]
  native proxy object not found, name:__DSHM_BRIDGES__
```

**统计（含增长率实测）**：

| 项 | 值 |
|---|---|
| 首次统计（19:35） | 6,914 次 |
| **复测（19:38）** | **9,258 次** |
| **3 分钟增量** | **+2,344 次** |
| **实测增长率** | **≈ 780 次/分钟（13 次/秒）** |
| 日志总行数 | 139,971（原 112,005） |
| 占比 | **6.6%** |
| 日志体积 | **22 MB**（原 16.6 MB） |
| 分布 | **全程持续**（按 2 万行分段：1769/1646/638/1194/984/1373/1657/27） |

**⚠️ 严重程度上调**：报告撰写期间实测到 **13 次/秒** 的持续报错，
比 `docs/281` 记录的「18 次/分钟」**高约 43 倍**。这不是偶发噪音，而是**高频轮询式的失败**。

**性质**：NWeb（WebView）桥接层找不到名为 `__DSHM_BRIDGES__` 的原生代理对象。
这是**前端每次都尝试调用一个不存在的桥**，被系统拒绝后继续。

**影响**：
- 功能上：桥调用**静默失败**（若有依赖它的功能，会表现为"没反应"）；
- 性能上：每次失败产生 3 行日志 + 一次跨语言调用开销，6.2% 的日志体量；
- 运维上：**淹没有效日志**，且 16.6 MB 日志持续增长。

**这个问题 `docs/281` 已记录（当时 ~4280 次 / 18 次/分钟），本轮复测已达 9,258 次且实测 780 次/分钟
（13 次/秒）—— 未修复，且量级比当初记录时高约 43 倍。**

### 5.2 🔴 缺陷 2：jitless 下全局 `fetch()` 不可用

**复现**：

```bash
node --jitless -e "console.log(typeof WebAssembly)"
# → undefined

node --jitless --experimental-loader=file://…/undici-loader.mjs -e "
  import('undici').then(u => console.log('导入成功'))
"
# → 导入成功
# → 但实际 fetch 时崩溃：
#   ReferenceError: WebAssembly is not defined
#     at lazyllhttp (node:internal/deps/undici/undici:6340:9)
```

**根因**：垫片**只拦截了模块解析**（`import('undici')` 拿到了替代实现），
但 **Node 内建的 undici 仍被 HTTP 派发路径加载**，它依赖 `WebAssembly`（llhttp），在 jitless 下必崩。

**关键区分（这决定了严重程度）**：

| 路径 | 实测结果 | 影响 |
|---|---|---|
| **产品路径** `dshmFetch`（`fetch-shim.js` → `node:http`） | ✅ **成功**（返回 401，请求真通到宿主） | **产品功能不受影响** |
| **全局 `fetch()`** | ❌ 崩溃 | 影响插件/核心树里直接用全局 fetch 的代码 |

**⇒ 产品主路径是安全的，但"任何直接用全局 fetch 的第三方插件/核心树代码"都会崩。**
这是**能力缺口**，不是当前功能中断。

### 5.3 🔴 缺陷 3：`check-profile-pnpm-bridge` 卡死

**现象**：

```bash
timeout 180 node tools/check-profile-pnpm-bridge.mjs
# ok   A1 假壳缺失 ⇒ shimRunnable() 为假
# ok   A2 假壳存在但跑不起来 ⇒ shimRunnable() 仍为假
# ok   A3 假壳真能跑 ⇒ shimRunnable() 为真
# （此后无输出，直到超时）
# rc=124 (180s) / rc=124 (240s) / rc=124 (300s)
```

**A1-A3 全过，说明假壳判定逻辑正常**；卡在**第 4 项之后**（推测是 `runProfilePnpm` 分叉的实测环节）。

**影响**：插件安装通道的**关键门禁失效** —— 这条链路现在**没有任何自动化保护**。

**已排除**：不是超时设置太短（延长到 300 秒仍然卡死）。

## 10. 总结

**这个 beta 包在日常使用与开发环境的"功能面"是健康的**：

- 组件齐全（bash/python/git/node/sharp/koffi/node-pty 全可用，仅 `rg` 按平台策略禁用）；
- **性能优秀**（bash 52ms、python 98ms、grep 43ms，均远优于阈值）；
- 41 分钟运行零崩溃，事件循环健康，数据无损坏；
- 门禁 81.6% 通过。

**但有 3 个必须处理的缺陷**：

1. **`__DSHM_BRIDGES__` 9,258 次报错，实测 780 次/分钟（13 次/秒）**（6.6% 日志体量，22 MB；
   比 `docs/281` 记录的 18 次/分钟**高约 43 倍**，且仍在增长）——
   这是**唯一的高频稳定性问题**，必须优先解决；
2. **全局 `fetch()` 在 jitless 下崩溃** —— 产品主路径安全，但第三方代码会踩坑；
3. **`check-profile-pnpm-bridge` 卡死** —— 插件安装通道**失去自动化保护**。

**建议下一轮**：优先修 #1 和 #3（前者影响稳定性，后者是保护真空），
并补一次 **>2 小时长跑**以判定内存泄漏趋势（当前 swap 184 MB 是唯一的内存警讯）。
