## 1. 依赖图怎么来的

从核心树的两个 bundle patch 解析出**全部插件行**，再逐个读模块入口，静态提取：

- `inject = [...]`（它需要哪些服务）
- `super(ctx, "name")` / `.provide("name")`（它提供哪些服务）

结果：**182 个插件**，其中 187/213 行有 `name`（其余是纯配置覆盖行）。

## 3. 技术可行性：运行时挂载确实支持

`dsh-app-boot` 导出 `recomposeProfile(ctx, patches, binName)`，其内部 `recompose()`：

```js
await entry.update({ config: { ...includeConfig, patches: prepared } });
await ctx.loader.await();          // ← 真正创建/销毁 loader 条目
```

并且失败会**回滚**（`finally` 里把停掉的 row 塞回并按原顺序重建）。
`hostcore/app/main.js:6900` 又已经持有 `ctx`（`const ctx = result && result.ctx`），
所以二阶段挂载在**接口层面可行**，不需要改 dsh。

配置编辑器（`config-editor.edit`）与插件开关（`plugin-manager`）走的就是这条路径，
说明它不是"给内部用的死代码"。

## 4. 但自动划分不安全 —— 57 个"说不清"的插件

```

```

**其中任何一个被误判为"可延后"，行为就是"模型不回话"或"工具不可用"** ——
正是用户明确要求不能出现的情况。

所以：**分阶段必须手工裁剪，再用真机逐项验收**，不能拿自动结果上线。

## 5. 目前最大的不确定性（为什么先不动手）

本机 profile 装载 10.13 秒里，**3.72 秒是事件循环同步阻塞**（LOOP-GAP 2050+1670ms）。
这比"延后几个插件"的量级更大，而且它的成因**日志里看不出来**：

```
LOOP-GAP-2050ms SYNC-RING        ← 环是空的
```

原因：同步调用环**默认关闭**（`hostcore/app/main.js:23`：
「同步调用环默认关闭…`DSHM_RUNTIME_DIAG=1` 开启」），所以没有栈可归因。

⇒ **先拿到一次带栈的 LOOP-GAP，才能知道该改哪里**，否则分阶段优化可能只是
把一个 3.7 秒的黑洞挪个位置。

## 6. 下一步（要一次冷启动）

用 `DSHM_RUNTIME_DIAG=1` 冷启动一次（只开同步环，不改行为），抓
`node-output.log` / `dshm-host.log`，看 `LOOP-GAP` 后面是否带上调用栈。

拿到之后：
1. 若阻塞在**我们自己的代码**（`spawnSync` 探测等）→ 直接改异步，风险最低；
2. 若阻塞在**插件** → 那个插件正好是阶段二的第一个候选，一举两得；
3. 若阻塞在**上游核心** → 判定为不可改，转去做阶段二。

## 9. 本轮已实施：启动期同步环 + require 耗时榜（只加诊断，不改行为）

按 §6 的第一步落地。**没有动插件装载顺序**，只让"3.7 秒被谁挡住"变成可归因的读数。

### 9.1 改了什么

| 项 | 内容 |
|---|---|
| **启动期同步环** | `DSHM_BOOT_RING != '0'` 时**默认开启**：包装 `fs` 16 个同步入口 + `child_process` 3 个 + `Atomics.wait`，只记账 |
| **就绪后自动卸载** | `runProfile` 返回后调用 `dshmRingStop('after-profile')`：打榜 + **还原全部原函数**，稳态零开销 |
| **require 耗时账本** | 包装 `Module._load`，按被 require 的模块名累计次数/耗时（只记 ≥5ms 的） |
| **汇总榜** | `BOOT-RING-STOP SYNC-COUNT`（同步调用总耗时 + Top12）与 `REQUIRE-COUNT`（模块装载总耗时 + Top15） |

### 9.2 三个开关

| 开关 | 默认 | 语义 |
|---|---|---|
| （不设） | **启动期开环，就绪后卸载** | 拿数据 + 稳态零开销 |
| `DSHM_BOOT_RING=0` | — | 完全回到旧行为（不装环） |
| `DSHM_RUNTIME_DIAG=1` | — | 环按**诊断语义常驻**，本函数只打汇总**不卸载**（不改变现有诊断模式行为） |

### 9.3 自查抓到的两个错误（如实记录）

1. **收尾点放错**：第一版把 `dshmRingStop()` 放进 `writeHostReady()`。而 `writeHostReady()`
   在 `runProfile()` **之前**就会被调用一次（`watchdogAuthUrl` → 早写，日志里那行
   「探针读数已暂存（host-ready.json 仍属于上一次进程 pid=…）」就是它）⇒
   环会在**插件还没开始装载**时被卸掉，等于什么都没测到。
   已挪到 `runProfile` 返回之后、`BOOT_70` 之前。
2. **改了诊断模式语义**：第一版在 `DSHM_RUNTIME_DIAG=1` 时也会卸载环，而那个开关的语义是
   "常驻"。已改为该模式下只打榜、不卸载。

### 9.5 下一步要看的两行日志

冷启动后 `dshm-host.log` 里会出现：

```
BOOT-RING-STOP(after-profile) SYNC-COUNT 同步调用总耗时 NNNms，按耗时 Top12：…
BOOT-RING-STOP(after-profile) REQUIRE-COUNT 被计时的 require 总耗时 NNNms（M 个不同模块），Top15：…
```

- `SYNC-COUNT` 的 Top12 → 那 3.7 秒 LOOP-GAP 的直接责任人；
- `REQUIRE-COUNT` 的 Top15 → profile 装载时最贵的包，**对应插件行的 name** ⇒ 阶段二该先延后谁。

有了这两张榜，Phase 2 的清单就从"我猜"变成"数据指定"。
