## 3. 那么"输入框那圈玻璃"是什么？

**极可能是官方自带的**，与皮肤无关：

`dsh-client-ui-conversation:16832`

```css
._7yHdaG_panel:before {
  z-index: -1;
  background: var(--dsw-specific-menu);              /* #f8f9faf0，94% */
  backdrop-filter: var(--dsw-menu-backdrop-filter);  /* blur(40px) saturate(150%) */
  position: absolute; inset: 0;
}
```

**这是官方实现对"输入框区"的既有设计**，任何时候都存在（不需要皮肤）。
用户在会话区滑动时看到玻璃 → **与皮肤无关，是原生功能**。

> 这也可以解释为什么用户"开启皮肤时"注意到它 —— 开启皮肤这个动作让人**更仔细地看界面**，
> 而不是皮肤带来了玻璃。

## 4. 与观察冲突的几种可能（不排除，待验证）

| # | 可能 | 需要什么证据才能确认/排除 |
|---:|---|---|
| 1 | **输入框玻璃是官方的，本来就有**（§3） | 关闭所有皮肤后滑动，若玻璃仍在 ⇒ 成立 |
| 2 | 市场里的**预览图**被误认为实际效果 | 预览区是独立 DOM，截图可区分 |
| 3 | 皮肤通过**宿主桥在客户端直接注入**，绕过 `cordis.patch.yml` | 页面里应出现 `<style data-plugin=…>` 或 `data-dsh-*skin` 属性 |
| 4 | **应用被重启过**（pid 相同是因为 Host 跑在同一 app 进程） | 查 `host-ready.json` mtime —— 仍是 18:12，**已排除** |
| 5 | 我读的 `cordis.patch.yml` 不是运行时真正生效的那份 | 需要确认 Host 的 patch 合并顺序 |

> **可能 3 是本轮最值得查的**：`dsh-skin-market` 的 `activateSkin` → `runForSkin(skinId,"activate")`
> 是一次**Host 调用**，如果它支持"运行时激活"（不动 cordis 树），就能绕过 §2.2 的判据。

## 5. 下一步取证（需要用户配合一次操作）

**请按顺序操作，每步之间告诉我，我立刻取数：**

| 步 | 操作 | 我要取什么 |
|---|---|---|
| 1 | **关闭所有皮肤**（回到默认） | 页面是否仍有输入框玻璃 |
| 2 | 在会话区上方滑动 | 探针 + 是否存在 `data-dsh-*skin` |
| 3 | **开启皮肤** | 同上 |
| 4 | 再滑动一次 | 玻璃是否**变化**（更强/出现/不变） |

**判据**：

- 若步 1 就有玻璃、步 3 无变化 ⇒ **玻璃是官方的，皮肤与玻璃无关**（§3 成立）；
- 若步 1 无、步 3 有 ⇒ **皮肤确实带来了玻璃**，则 §2.2 的"未加载"判据有漏洞，需查可能 3。

**同时请回答**：开启皮肤时，**侧栏配色**是否真的变了？（你说"两者都有"，
但若配色其实没变，那"皮肤生效"这个前提本身就要重新审视。）
