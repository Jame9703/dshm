# 168 · 平板状态栏归属：手持档**只有全屏 / 最大化**时才由我们设

> 用户报障（附两张同一台平板的对比图）：**"一个是 pad 端 QQ 后台时的状态栏沉浸是黑色的，
> 另一个是 DSHM 在后台时状态栏的沉浸是白色的，同一台设备，看下怎么修。"**
> 同批材料还有一份手机端复测报告（r48，见 §6 的分诊）。

## 1. 现场证据（先把"谁的颜色"钉死）

两张图都是 1920×1262（MatePad Pro 12.2 / 鸿蒙 6.1），用取色而不是肉眼判：

| 图 | 对象 | 顶部状态栏那一条（y≈30） | 状态栏下方 |
|---|---|---|---|
| A | QQ（自由窗口） | `#1E1E1E`（深色，跟着桌面） | 深色桌面带 |
| B | DSHM（自由窗口） | **`#FFFFFF`（整条白）** | 深色桌面带 |

⇒ 同一窗口形态、同一台设备，差异只在"是哪个应用"⇒ **白条是我们自己涂的**：
本仓在两处显式设状态栏属性（`WebApp.applySystemBarTheme()` 与 `EntryAbility.reassertWindowChrome()`），
浅色外观给的就是 `statusBarColor: '#FFFFFF'`。

## 2. 根因

1. **SDK 契约**（`@ohos.window.d.ts` 的 `setWindowSystemBarProperties`，@since 9 当前 API 原文）：
   *"The setting does not take effect when the main window is in non-full-screen or non-maximized mode
   (such as floating windows or split-screen mode). It takes effect once the main window enters
   full-screen or maximized mode."* —— 这套属性**只对"前台且占满屏幕"的窗口有意义**。
2. **真机不守约**：平板自由窗口下它照样把**系统状态栏**涂成 `#FFFFFF`（图 B），而 QQ 什么都不设 ⇒ 深色。
3. **第二条形态（"后台"）**：`onBackground` 那条链（docs/166 §5.1 为"任务卡片顶栏"加的重放）也会设状态栏；
   真机读数证明**那一刻窗口状态仍是 `FULL_SCREEN`**（MINIMIZE 是随后才发生的）
   ⇒ 只看窗口状态判不出"我正在离开前台"，于是离开前台照样把桌面/其它应用的状态栏涂白。

## 3. 修法（三处，全部收在一条判据上）

**判据（纯函数，`platform/src/main/ets/system/WindowChrome.ets`）**：
```ts
statusBarOwnedByApp(handheld, windowStatus)   // 手持档 + FULL_SCREEN(1)/MAXIMIZE(2) ⇒ true
                                              // 其余（MINIMIZE(3)/FLOATING(4)/SPLIT_SCREEN(5)）⇒ false
                                              // 非手持（PC/2in1）恒 true；状态读不到 ⇒ true（维持老行为）
```

1. **页面**（`WebApp.applySystemBarTheme`）：设状态栏之前先问判据（新增 `readWindowStatus()`，
   801 时回 `undefined`）；交还系统时**不锁幂等闸门**，形态变回来能立刻补设。
   顺带修掉一处既有缺陷：`setWindowSystemBarProperties` 返回的是 Promise，
   原先的同步 `try/catch` 抓不到异步拒绝（801 / 1300002 只会变成无人处理的 rejection）⇒ 补 `.catch()`。
2. **能力层**（`EntryAbility.reassertWindowChrome`）：同一条判据 + **语义参数** `foreground`：
   `onBackground` 显式传 `false`（离开前台一律不写系统状态栏），`onForeground` / 形态变化两条链传 `true`
   （回到前台立刻补上）。`readWindowStatusOf(win)` 同样 801 ⇒ `undefined`。
3. **两条重放链都要重判**：窗口状态变化（`refreshDecorCaps` 的 `changed` 分支）与启动发布各调一次
   `reassertWindowChrome(...)` ⇒ 自由窗口 ↔ 最大化之间来回切，状态栏归属跟着切。

**自证读数**：`files/diag-decor-caps` 每行尾部新增 **`sb=app|system`** —— 平板那边只要把这行发回来，
就知道当时走的是"我们设"还是"交还系统"。

## 4. 真机验证（2026-10-16）

**手机 `62T0225B18039433`（手持档 + 全屏，三态逐一读数）**：

| 状态 | `diag-decor-caps` 原文 | 判定 |
|---|---|---|
| 前台 | `… status=1:FULL_SCREEN … sb=app` | 仍由我们设（手机路线不变） |
| **切后台（HOME）** | `refresh H=0 status=3:MINIMIZE … sb=system` | **交还系统**（用户报的"后台白条"这条路被关掉） |
| 回前台 | `refresh H=0 status=1:FULL_SCREEN … sb=app` | 自动补回 |

配套 hilog：`窗口外观重放（background）：手持档 离开前台 ⇒ 状态栏交还系统（底色置透明）`；
前台仍是 `状态栏已跟随外观：dark bg=#151517`（三态切换时浅/深交替出现，属外观跟随，正常）。

**PC `86E0226429000417`（2in1，非手持档 ⇒ 必须逐字不动）**：
`visible=ok set=ok get=H=37 style=ok mode=light status=4:FLOATING -> present=true sb=app`，
且全量 hilog 里 **0 条** "交还系统" ⇒ `handheld=false` 时判据恒 `true`，行为与改动前一致。

**平板本身**：本轮无平板在线，**待平板侧复验**。要的东西就两样：
① 自由窗口下的 `files/diag-decor-caps` 那一行（看 `sb=` 是 `system` —— 期望值）；
② 一张状态栏不再是白条的截图。若 `sb=system` 却仍是白条，说明系统状态栏还记着我们此前写过的白色，
**同日已按 `docs/170` 落地**：交还 = **显式写全透明**（`SYSTEM_BAR_HANDOFF_BG`），不再"什么都不做"。

## 5. 边界与已知限制

- ~~**不主动"复位"**（初版口径，已被 `docs/170` 推翻）~~：交还系统 = **显式写全透明底色**（`SYSTEM_BAR_HANDOFF_BG`），而不是"什么都不做" —— 后者会把前台的色留在系统状态栏上（用户图② 的多任务一条黑就是这么来的）。仍在"不动图标颜色"这条上保持克制：交还之后那格背景不是我们的，图标深浅交给系统 / 启动器（实测它会自己重画）。
- **PC / 2in1 逐字不动**：判据第一行就返回 `true`，门禁有负例钉住。
- 状态读不到（801）⇒ 维持老行为（照旧设）：宁可"按老样子"，也不在信息不足时把状态栏弄丢。
