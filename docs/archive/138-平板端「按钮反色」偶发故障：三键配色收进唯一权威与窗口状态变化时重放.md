## 3. 先排掉的三条（别再来一遍）

1. **ArkWeb 强制反色**：SDK（`web.d.ts` 里 `forceDarkAccess` / `darkMode` 那一族）的语义是"**只在被显式打开时**才强制反色"，
   而本仓当前值是 `forceDarkAccess(false)` 且从不显式打开 ⇒ **ArkWeb 不做强制反色**。
   更关键的是：报告里"反色"连**同一张图里的 App 图标**都翻（白底蓝音符 ↔ 蓝底白音符）——
   ArkWeb 的力**到不了别的应用的图标**，那部分是**系统层**的。
2. **皮肤 CSS 写了 `filter: invert()`**：全仓检索（皮肤 / 垫片 / 宿主 / 已装皮肤包）**零命中**。
3. **三键"重叠 / 重影"**：那是 `docs/133`、`docs/134` 已修的**纵向让位**问题（`present` 判据 + 让位量）。
   报告把"看不见 / 反色"与"重叠"写在同一段里了 —— 两者根因不同、修法不同，**不要混着改**。

## 4. 可归因到本仓的那一半：三键配色"只设一次"

### 4.1 事实链（全部可从代码读出）

- 自绘顶栏自 2026-09-26 起**跟随外观**：深色外观下顶栏底色 `#151517`，三键配色必须是 `COLOR_MODE_DARK`（浅色图标），否则就是**黑底黑键**（2026-10-05 那次真机回归）。
- 而三键（全屏 / 最小化 / 关闭）是**系统画的**装饰：它的配色属于**窗口装饰态**，平台在重建装饰时会把它丢掉。
- 报告里正好有"装饰态在被反复重建"的读数：同一毫秒 3 连发 `refresh`、`present` 在 `FLOATING`/`other` 间翻转、首帧 `style=err`（见 §1 的 1–4）。
- 旧实现里三键配色有**两处**来源，且**都不具备"丢了能补回来"**：
  1. `EntryAbility` 创建窗口时写死 `COLOR_MODE_LIGHT`（那是给当年"恒白底顶栏"配的）；
  2. 页面 `applyDecorButtonMode()`，由 `applySystemBarTheme()`（**主题变化**时）与 `applyTopBarTheme()`（**10 s 一轮**的 DOM 探针兜底）驱动。
  ⇒ **只要平台重建/丢弃了装饰态、而外观又没再变**（外观不变就不会再有通知），两处都不会被再调用
  ⇒ 深色外观下三键退回深色图标 ⇒ 用户看到的就是"三键看不见 / 反色"。
  —— 这正是 2026-10-05「深色外观下黑底黑键」回归的**另一半根因**：那次只修了"主通道也要管三键"这条**漏挂**，没修"**丢了没人补**"。

### 4.2 改动 A · 页面：把"当前生效外观"发布出去，且**不受幂等闸门拦截**

`entry/src/main/ets/pages/WebApp.ets`

- 新增约定键 `const KEY_APPEARANCE_MODE: string = 'dshAppearanceMode';`（与 `KEY_DECOR_KEYS_VISIBLE` 同款：两侧各写一份字面量，门禁钉"同名同值"）。
- `applySystemBarTheme(mode)` 开头（**在幂等闸门之前**）两行：

  ```ts
  AppStorage.setOrCreate<string>(KEY_APPEARANCE_MODE, mode);
  this.applyDecorButtonMode(mode);
  ```

  理由：① 能力层要按"当前外观"重放三键，而它拿不到页面的 `@State` ⇒ 必须有这条跨层约定键；
  ② 闸门只挡"状态栏属性 / 窗口底色"（重复设没有意义），**不许挡三键** —— 三键属于装饰态，平台会丢，被闸门挡住就再没机会补。
  （顺带修掉"窗口未就绪那次调用丢了、同模式的后续通知不重设"的空窗。）

### 4.3 改动 B · 能力层：三键配色收进**唯一**一处，并在窗口状态变化时**重放**

`entry/src/main/ets/entryability/EntryAbility.ets`

- 新增 `private appearanceMode(): string` —— 读那个约定键，**只有 `'dark'` 当深色**，其余一律浅色
  （与官方 boot 的 `color-scheme:light`、页面顶栏初值 `#FFFFFF` 一致 ⇒ 启动瞬间不会"反色闪烁"）。
- 新增 `private reassertDecorButtons(win): string` —— **本文件唯一一处 `setDecorButtonStyle`**，按 `appearanceMode()` 取 `COLOR_MODE_DARK` / `COLOR_MODE_LIGHT`，
  返回 `'ok'` / `err=<code>`（手机全屏、平板某些窗口态抛 801 是**正常回应**，只记不降级）。
- 启动路径：原先塞在 `decorStyleOk` 那段里的 `setDecorButtonStyle` **整块删除**，改成 `const decorStyleRaw: string = this.reassertDecorButtons(win);`。
- `refreshDecorCaps()` 重写为：**先重放三键配色 → 再读高度 → 再读窗口状态 → 算 `present` → 去重（结论 / 状态读数 / 配色三者全都没变才跳过）→ 只在变了时发布 + 落盘**。
- 诊断行补 `mode=`，并把 `status=` 从"只有 `FLOATING` / `other` 两个词"改成 **状态码 + 短名**（新增纯函数 `windowStatusName()`：`UNDEFINED / FULL_SCREEN / MAXIMIZE / MINIMIZE / FLOATING / SPLIT_SCREEN / OTHER`）
  —— 报告里"那个 `other` 到底是 `MAXIMIZE` 还是 `SPLIT_SCREEN`"查不下去，就是缺这一项。

### 4.4 改动 C · 门禁加牙

`tools/check-decor-button-mode.mjs` 第二组 38 → **50** 项（对照臂 A–H → **A–K**）：

- 新增 12 条断言：恰好 1 处 `setDecorButtonStyle` / 取自 `appearanceMode()` / 按外观三元取色 / **不许出现写死的** `COLOR_MODE_LIGHT` /
  两侧 `KEY_APPEARANCE_MODE` 同名同值 / 页面发布 · 能力层读 / 调用在闸门**之前** / 先重放再读状态 / 去重三条 / `if (changed)` 包住发布 / `windowStatusName` 存在。
- 新增三条对照臂：**I**（外观写死 `'light'`）/ **J**（页面不再发布）/ **K**（拿掉去重）。
- 对照臂 A（删调用点）的变异体构造改为按**调用点全删**（现在有两个调用点）。

## 7. 已知边界与未做项（如实登记）

### 7.1 长停顿（`LOOP-GAP` / `statSync` 100 s）本轮**没修**

- 报告的 H1（中高置信度）把"反色"的场景前因指向事件循环长停顿：`LOOP-GAP-1198565ms`、`statSync×1426794=689149ms`、单次最长 `100477 ms`。
- 这是**宿主性能**问题（扫描 `dsh/cores/*/node_modules`、`profiles/ondevice/node_modules` 一类目录），
  与本轮改的 ArkTS 装饰态是**两条独立的路**。本轮**刻意不动**：它要动宿主、可能连带核心树，属**另一次**改动，
  不做"顺手带上"（本仓的回归纪律不允许）。
- 另记一条观察：`LOOP-GAP-1198565ms` ≈ 19 分 59 秒这个量级更像**进程被平台挂起**（平板后台/休眠）而不是纯忙等；
  只有单次 `statSync` 100 s 才像真卡在文件系统上。**待单独排查**。
