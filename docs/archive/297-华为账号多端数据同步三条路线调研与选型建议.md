## 0. 先给结论

> **三条官方面案都不适合直接承载 DSHM 的会话数据。**
> 真正的阻塞点不是"选哪个云"，而是 **DSH 的会话是"按工作区目录分组 + 每会话一个
> `.jsonl.zstd` 追加式日志"的文件形态，而三条路线里没有一条是为"多工作区文件树"设计的**。
>
> 如果要做，正确的是**第四条路**：**华为账号做身份、对象存储做载体、按会话粒度增量同步**。
> 而**最小可验证的第一步**不是接云，而是**先把"同步单元"从文件系统抽象出来**。

## 1. DSHM 的数据到底是什么（这决定选型）

### 1.1 实测：会话是**文件**，不是数据库表

核心树 `@deepseek-ai/dsh-session-persistence-jsonl`（3676 行）的目录布局（源码逐字）：

```text
<sessionRoot>/
  <projectKey(cwd)>/              ← 按工作区 cwd 分组（无 cwd ⇒ _no-cwd/）
    <encodeSegment(sessionId)>/   ← 一个会话一个目录
      <version>.jsonl.zstd        ← 不可变代际日志（SESSION_FORMAT_VERSION）
```

关键事实（源码取证）：

| 事实 | 出处 | 对同步的含义 |
|---|---|---|
| 会话是 **JSONL + zstd 压缩** | `import { zstdCompress } from "node:zlib"` | **不是可映射的行列数据** |
| 每个会话**一个目录** | `sessionDir(root, cwd, id)` | 同步单元天然是"会话" |
| 日志**按格式版本分代**（v0→v1→v2→v3→v4 五个迁移包） | `generationLogFilename(version, compression)` | 跨版本数据**形态会变**，同步要带版本 |
| 目录**按 cwd 分组**（projectKey） | `projectDir(root, cwd)` | **工作区路径是数据的一部分**，跨端路径必然不同 |
| 写入走 **tmp + rename** 原子落位 | `rename` 出现在落位路径 | 增量同步可以按"完整文件"粒度，不用怕写一半 |

### 1.2 会话之外还有这些（`docs/291` 真机读数）

```text
会话 3 个 / 3.7 MB    ← 主体
attachments 365 KB    ← 附件（图片、文档）
storages 131 KB
cache 558 KB          ← 可再生，不该同步
```

⇒ **要同步的数据 ≈ 会话日志 + attachments**，cache 与 cores（350 MB/棵）**绝不能同步**。

### 1.3 一个必须先解决的语义问题

会话目录按 **cwd（工作区绝对路径）** 分组。同一台 PC 与手机的工作区路径天然不同：

```text
PC：  ~/Download/com.dshm.dshclient/我的项目
手机：~/Download/com.dshm.mobileclient/我的项目
```

⇒ **同步时不能原样搬目录结构**，必须建立"跨端路径等价"的映射，否则同一个会话在两端会分成两份。
这是**任何方案都要先解决的问题**，与选哪家云无关。

## 2. 三条路线逐条评估

### 路线一：Drive Kit（云空间）

| 项 | 事实 |
|---|---|
| 定位 | 云端**文件**存储（上传/下载/同步/查看） |
| 账号 | **必须**接华为账号授权拿 Access Token |
| 前置 | AGC 打开 Drive Kit 开关 + 签华为云空间隐私通知与用户协议 |
| 平台 | ⚠️ **官方页面标 Android / Web**；鸿蒙原生（ArkTS）支持**未确认** |
| 适合 DSHM 吗 | **形态最接近**（会话就是文件），但**平台可用性存疑** |

**判断**：如果 Drive Kit 确实支持 HarmonyOS，它是三条里**唯一与"文件形态"匹配**的。
但**平台支持必须先向华为确认**——这是硬前置，不能靠推测动工。

### 路线二：端云数据同步（ArkData 关系型数据库）

| 项 | 事实（本机 SDK 核实） |
|---|---|
| API | `RdbStore.cloudSync(mode, tables[], progress)` / `cloudSyncEx(CloudSyncConfig, progress)`（**26.0.0 新增**）/ `stopCloudSync()` |
| syscap | `SystemCapability.DistributedDataManager.CloudSync.Client`（34 处引用） |
| 权限 | **SDK 声明里没有 `@permission`** ⇒ 不新增权限条目 ✅ 符合本仓权限铁律 |
| 账号 | 依托**系统已登录的华为账号**，无需应用内登录页 |
| 前置 | AGC 云同步服务配置数据类型，**云侧类型名必须与 ArkData 本地表名一致** |

**但这里有结构性不匹配**：

> **DSH 的会话不是关系型表。** 要把 `.jsonl.zstd` 塞进 RDB，只有两种做法：
> ① 一个会话一行、`TEXT` 列存整份 zstd base64 —— 那就等于"用数据库存文件"，
>    且**单行几十 MB** 会撞 RDB 的行体积与同步粒度限制；
> ② 把 JSONL 拆成事件表 —— 要**改写上游持久化格式**，违背本仓「不 fork、不魔改 dsh」的第一原则。

⇒ **路线二对 DSHM 不适用**（不是不好，是形态不合）。

### 路线三：Account Kit 登录 + 云数据库 / 自有服务端

| 项 | 事实 |
|---|---|
| API | `@hms.core.account.LoginComponent`（本机 SDK 存在） |
| 能力 | 华为账号一键登录，拿 **UnionID**（跨应用统一用户标识）+ 手机号 |
| 数据 | 自己写 AGC 云数据库 **或自有服务端** |
| 权限 | 登录组件本身不需要受限权限（待逐条确认 `@permission`） |

**优势**：**完全掌控同步语义**，能按"会话"粒度做增量、能处理 §1.3 的路径映射、
能保留冲突策略。这也正是官方建议里"需要跨端灵活同步"时的选择。

**代价**：你要自己实现服务端或云数据库表设计 + 冲突解决 + 增量算法。

## 3. 我的建议：不选三条中的任何一条，走「第四条路」

### 3.1 为什么

| 需求 | 路线一 | 路线二 | 路线三 | **第四条路** |
|---|---|---|---|---|
| 会话是文件形态 | ✅ 匹配 | ❌ 结构性不匹配 | ➖ 需自建 | ✅ 匹配 |
| 鸿蒙原生可用 | ❓ **未确认** | ✅ | ✅ | ✅ |
| 跨端路径映射 | ➖ 自己做 | ➖ 更麻烦 | ✅ 自己做 | ✅ 自己做 |
| 增量（不重传 3.7 MB） | ❓ 看 API | ➖ | ✅ 可控 | ✅ 可控 |
| 不新增权限 | ➖ 需账号 | ✅ | ✅ | ✅（不新增受限条目） |
| 改动上游 | 否 | 否 | 否 | **否** |

### 3.2 第四条路的具体形态

```text
身份层：Account Kit（LoginComponent）→ UnionID
          ↓
同步单元：一个会话 = 一个可寻址对象（sessionId + 版本代际 + 内容哈希）
          ↓
载体层：Drive Kit（若鸿蒙可用）
        或 AGC 云数据库（只存"索引 + 元数据 + 指针"，不存日志体）
        或自有对象存储（OSS/COS/MinIO，最自由）
          ↓
端侧：在 DSH 之外做一个"同步代理"
      · 监听 <sessionRoot> 的文件变更（新增/追加）
      · 按会话粒度打包上传（zstd 已压缩，不再二次压缩）
      · 拉取时写回对应 projectKey（经路径映射）
```

**关键设计决定（无论选哪个载体都成立）**：

1. **同步单元 = 会话目录**，不是文件、不是行。一个会话的所有代际日志一起走。
2. **索引与内容分离**：云上存一份"会话清单"（id / 标题 / 工作区 / 更新时间 / 哈希），
   正文另存。这样"列出会话"很快，"打开会话"才拉正文。
3. **路径映射表是必需品**：`本地 cwd ↔ 云端 workspaceId`，首次同步时让用户确认一次。
4. **cache 与 cores 永不参与同步**。
5. **冲突策略先定死**：会话日志是**追加式不可变**的 ⇒ 同会话两端都写时，
   正确做法是**按代际合并**（保留双方日志，新代际重放），而不是"最后写入者赢"。

## 4. 分阶段规划（每阶段都可独立停下）

### 阶段 0：可行性验证（**不动产品代码**，1–2 天）

| 要回答的问题 | 怎么验 | 阻塞后续什么 |
|---|---|---|
| **Drive Kit 是否支持 HarmonyOS 原生** | 向华为提工单 / 查开发者联盟 | 决定载体层选 Drive 还是自建 |
| Account Kit 登录是否需额外权限/审核 | 逐条读 `@permission` + AGC 配置 | 决定身份层能否零权限接入 |
| AGC 云数据库对个人开发者的开通条件 | AGC 控制台确认 | 决定是否需要企业认证 |
| 同一会话在两个工作区路径下的表现 | 本地构造两个 cwd 跑一遍 | 验证 §1.3 的路径映射设计 |

**产出**：一份"能不能做、怎么做载体"的结论。**这一步不通过就不该往下走。**

### 阶段 1：把"同步单元"抽象出来（**纯端侧，可离线验证**，2–3 天）

不改任何网络逻辑，只在 DSH 之外加一层**只读的会话快照/清单生成**：

```text
SessionSyncScope（platform 层，纯逻辑）
  · 扫描 <sessionRoot> → 会话清单（id / cwd / 代际 / 字节数 / 哈希）
  · 排除规则：cache、cores、临时 .tmp
  · 输出稳定的 manifest.json（可 diff、可测试）
```

**为什么先做这个**：它是三条路线**共同**的前置（不管云选哪家都要先知道"要同步什么"），
而且**纯离线可验证**，能用门禁钉住（判据：清单稳定、排除规则生效、哈希可复算）。

### 阶段 2：单机闭环（**不上云**，3–5 天）

同一台设备上的"导出 → 导入"：

- 导出：manifest + 会话打包成 `.dshmsync` 归档；
- 导入：按路径映射写回，冲突按代际合并。

**价值**：把**最难的语义部分**（路径映射、冲突合并）在没有网络、没有账号的前提下验完。

### 阶段 3：接入载体（依赖阶段 0 结论，5–10 天）

- 若 Drive Kit 支持鸿蒙 → 直接上/下载归档；
- 否则 → Account Kit 登录取 UnionID + 对象存储。

### 阶段 4：双向同步与冲突（5–10 天）

真正的"多端同时改"，需要后台调度、断点续传、冲突提示 UI。

| # | 问题 | 为什么必须你定 |

## 6. 风险登记

| 风险 | 说明 | 应对 |
|---|---|---|
| **Drive Kit 鸿蒙支持不明** | 官方页面只标 Android/Web | **阶段 0 必须先问清**，不能假设 |
| 会话格式会变 | v0→v4 已有五代迁移 | 同步必须带 `version`，且**不跨大版本强合并** |
| 数据量增长 | 现在 3.7 MB，但长会话理论无上限 | 分会话粒度 + 增量，避免整包重传 |
| 隐私与合规 | 会话里有用户对话内容 | 上云前需要**用户显式同意**+隐私政策更新（AGC 上架会查） |
| 端云加密 | RDB 有 `isEncrypt`，文件载体没有 | 若走文件载体，**必须自己做端到端加密** |
| 与现有 Host 冲突 | 同步代理与 DSH 同时写会话目录 | 同机必须**串行化**（锁文件），否则会踩 §1.1 的原子写 |

## 7. 一句话交接

**三条官方面案都不适合直接承载 DSHM 的会话**：会话是"按工作区分组的 `.jsonl.zstd` 文件树"
（路线二的结构性不匹配），而路线一的**鸿蒙原生支持未确认**、路线三要自建后端。
**建议走第四条路**：Account Kit 做身份 + 对象存储做载体 + 按会话粒度增量同步；
**但无论走哪条，第一步都是阶段 1 的"会话清单抽象"**——它纯离线、可门禁、三条路线共用。
**在阶段 0 的四个问题问清之前，不建议动任何联网代码。**
