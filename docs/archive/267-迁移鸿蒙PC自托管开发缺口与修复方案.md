## 2. P0 级：必须最先修

### P0-1 私钥与凭证会被提交进 Git

**症状（实测）**：
```
git check-ignore .env                    → NOT-IGN（rc=1）
git check-ignore .certs/release1012/dshm.p12 → NOT-IGN
git ls-files --others --exclude-standard -- .env .certs
  → .env 及 .certs 下 22 个文件全部会被 add
```
涉及 `.certs/debug-local/xiaobai.p12`、`.certs/release1012/dshm.p12`（**AGC 发布
私钥**）、各 debug/release profile、material 目录，以及 `.env`（AGC OAuth 配置）。

**叠加问题（文档与现实不符）**：`docs/249` §6 写着「AGC 凭证只落本地 `.env`，
该文件已加入 `.gitignore`，不得入库」——**实测它不在 `.gitignore` 里**。说明
当时改过又被还原，或从未真正改。这类"文档说了、配置没做"的偏差必须连同修复一起订正。

**为什么是最高级**：`AGENTS.md` 记载私钥"没有第二份"（2026-10-04 事故）；
一旦 `git add -A`，密钥进入历史，`filter-repo` 重写会毁掉所有已发布分支的哈希。

**修复方案**（按仓库已有的 `signing/` 内层忽略范式做——该目录用
`.gitignore`（`*` + `!.gitignore` + `!README.md`）实现了"目录在库、物料不在"）：

1. 在根 `.gitignore` 追加（放在「机器绑定物料」注释块旁边，与 `/build-profile.json5` 同段）：
   ```gitignore
   # 【签名物料·同 signing/ 内层忽略范式】.certs/ 只留 README/校验和可入库，密钥永不入库
   /.certs/*
   !/.certs/README.md
   # AGC 凭证（docs/249 §6 的口径，本轮实测此前的声明未生效）
   /.env
   ```
2. （可选）给 `.certs/` 补一份 `README.md` + `SHA256SUMS.txt`（对齐 `signing/` 的做法），
   供异机核对物料完整性。
3. 订正 `docs/249` §6：加一行"2026-10-28 复核发现该忽略曾失效，已重新落地"。

**验收判据**：
```
git check-ignore .env .certs/release1012/dshm.p12   # 两条均 rc=0
git ls-files --others --exclude-standard -- .env .certs | wc -l   # = 0
git status --short | grep -c '?? .certs'            # = 0
```

### P0-2 沙箱 `bin/node` 包装器失效 + Codex `CODEX_HOME` 缺创建

**症状（实测）**：
```
$ node --version
Error loading shared library libc++_shared.so: (needed by .../files/bin/node-cli)   rc=127
```
任何经 PATH spawn `node` 的路径（含 Agent 的 bash 工具、部分插件安装链）拿到的
都是这个坏包装器。

**根因（本轮逐层定位）**：
- 包装器把 `LD_LIBRARY_PATH` 指向 `/data/storage/el1/bundle/libs/arm64`，那里
  `libc++_shared.so` **存在且可读**（可 `cp` 出来），但**不可被映射加载**
  （`dlopen` 返回 `Permission denied`——ELF 的 exec 映射被拒，与 `host-ready.json`
  里 `sandbox-dlopen: ok:false` 是同一族系统约束）；
- 把该文件复制到应用沙箱后 `dlopen` 仍被拒（应用数据区 ELF 同样受限于该进程域）；
- `/system/lib64/libc++_shared.so` 可 `dlopen`，但包装器没把它放进搜索路径，
  且实测 `node-cli` 的 DT_NEEDED 解析仍不认。
- 与此对照：`node-brew`（完整 Node 26.12.1 二进制，位于用户可见目录）**完全可用**，
  且 `node-runtime-provision.cjs` 已经在用它给插件供运行时（`host-ready.json`
  的 `nodeCli.ready=true, file=node-brew`）。

**修复方案**：
1. `bin/node` 包装器改为**优先委托 `node-brew`**：存在且可执行时直接
   `exec "$NODE_BREW" "$@"`；找不到再走现有 libnode 路线（PC 档保底）。
   这样 PATH 上的一切 `node` 调用方立即恢复。
2. **伴生缺口（Codex 子智能体）**：`dsh-subagent-codex` 已安装且补丁正确落位
   （argv 换 `codex-brew`、CA 注入都在），但 `$HOME/.codex` 无人创建——
   Codex 自报 `CODEX_HOME points to "...", but that path does not exist`，
   登录态/CA/历史全部落空。修法二选一：
   - 在 `patchCodexSubagentForExternalCodex()` 注入的 `dshmCodexSpawnEnv()` 里补
     `mkdirSync(env.CODEX_HOME, { recursive: true, mode: 0o700 })`（自愈，推荐）；
   - 或装机后跑一次 `node tools/setup-codex-for-dshm.mjs`（会连凭据一起同步）。
   > 本轮排查时已手动 `mkdir` 了一个空 `.codex`（会话库 0 条）救急；开发端落地
   > 上述修复后该目录会被正常重建，无需保留人工痕迹。

**验收判据**：
```
node --version          # 全新 shell 里返回 v26.12.1，rc=0
# Codex 侧：全新装一次 subagent-codex 后
codex-brew --version    # 不再出现 "CODEX_HOME ... does not exist" WARNING
```

## 3. P1 级：迁移开发的真实阻塞

### P1-1 双端一致性门禁判红：6587 处漂移

**症状（实测，真实 exit code=1）**：
```
node tools/check-two-project-parity.mjs
❌ 不一致 6587 处（这些不是设计差异，是漂移）：
  只在 PC 工程有：hostcore/app/dshm-compat.js …
  只在 PC 工程有：connection/Index.ets …（另有 6507 处）
```

**根因**：`docs/214` 双端分离（2026-10-21）后，PC 工程一路演进到
`rc.3+dshm.96 / 1.1.6 / hostruntime HSP / 17+9 权限`，而 `DSHM-mobile` 停在
分离基线（`rc.2+dshm.78` 时代）。门禁当时的"两端同源"前提已不成立。
（附带实测：手机工程目录对本应用上下文不可 `ls`（EPERM），但 Node 门禁能读——
不影响判定，只影响人工检查。）

> **2026-10-28 订正（评审后实测）**：本节初稿把 `check-two-project-parity` 的
> **exit 1 / 6587 处漂移**当成"手机工程落后 PC 工程"的真漂移 —— **这个结论是错的**。
> 复测显示：对端工程 `DSHM-mobile` 在本机应用域是 **`stat` 通、`listdir` EPERM**，
> 而门禁旧实现 `inventory()` 把 `readdirSync` 的异常**静默吞掉**（`catch { return out }`）
> ⇒ 对端清单恒为空 ⇒ 每个 PC 文件都被报成"只在 PC 工程有"。
> **6587 是取证失败造成的假红，不是漂移。**
>
> 已修（同日）：`ENOENT` 仍按真缺失处理，其余错误记入 `unreadable` 并 **exit 2（无法判定）**；
> 自检改为两条臂（臂 1 注入漂移判红 / 对端不可写时如实 skip；臂 2 **跑真门禁子进程**断言
> 对端不可枚举 ⇒ exit 2）。复跑实证：`rc=2`，精确列出 12 个 EPERM 目录。
>
> ⇒ **本节的 A/B/C 三选项仍然成立，但当前没有"6587 处待处理"这回事**：
> 要判断是否真有漂移，得先把手机工程放到**应用域可枚举**的位置（或给
> `DSHM_MOBILE_ROOT` 指一个可读副本）再跑一次。

**这不是"修个文件"能解决的，需要先拍板**，三选一：

| 选项 | 动作 | 代价 |
|---|---|---|
| A. 手机侧追平 | 按 PC 侧同批次改动同步 `DSHM-mobile`（hostcore/HAR/ets/resfile） | 大；但保住"两端共用源码"的产品承诺 |
| B. 承认分叉 | 把 6587 处登记进门禁的 ALLOWED 清单（注明理由），门禁退化为"新增漂移才红" | 小；但放弃同源承诺，今后每轮都要维护清单 |
| C. 暂停手机线 | 移动端冻结在 1.1.6 发布版，门禁加 `--mobile-frozen` 旁路 | 中；产品决策而非技术决策 |

**验收判据**： whichever 选项落地后 `check-two-project-parity` exit 0（或带
显式 ALLOWED 清单的豁免口径），并写入 `docs/README.md` 基线表。
