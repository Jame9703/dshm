## 1. 先更正我自己：全局 `fetch()` 那一项判错了

### 1.1 我在 `docs/292` §4.1 写过"本机实测不成立"

当时的依据是：用**不可达端口**（`127.0.0.1:1`、`127.0.0.1:59999`）调 `fetch`，拿到的都是
`connect ECONNREFUSED`，没有出现 `WebAssembly is not defined`，于是判"报告不成立"。

### 1.2 为什么那个实验是**假阴性**

连接在**建立阶段**就失败了 —— 根本没走到 undici 的 HTTP 解析器，自然不会碰 WASM llhttp。
用"连不上"去证明"解析不会崩"，是无效对照。

### 1.3 换一个**真的在监听**的 server，结论立刻翻转

```text
$ node-brew --jitless --experimental-loader=.../undici-loader.mjs -e "fetch('http://127.0.0.1:18092/')…"
ERR fetch failed
CAUSE WebAssembly is not supported in this environment, but is required for HTTP/1 parsing
```

⇒ **294 的"仍崩"是对的，我上一轮的"不成立"是错的。**

### 1.4 但这不等于"产品不可用"——要分清两层

| 路径 | jitless 下的表现 | 结论 |
|---|---|---|
| **裸 Node 的 `globalThis.fetch`**（不经宿主启动链） | ❌ `WebAssembly is required for HTTP/1 parsing` | 291/294 报的就是这一层 |
| **宿主启动链覆盖后的 `globalThis.fetch`** | ✅ 实连取得响应体 `PRODUCT-OK` | 产品路径可用 |

证据（`--jitless` 下）：

```text
[diag] jitless fetch 垫片已安装（基于 node:http/https；原生 fetch 不可用）
installed: true
typeof globalThis.fetch: async function dshmFetch(input, init = {}, options = {}) { … }
fetch('http://127.0.0.1:18094/') → GLOBAL FETCH OK: PRODUCT-OK
```

**口径（写进这里，避免再被误读）**：

- `hostcore/app/main.js:962` 的 `jitlessEnv.installJitlessFetch()` 会把 `globalThis.fetch`
  **替换**成纯 JS 的 `dshmFetch` ⇒ **产品内全局 fetch 是可用的**；
- 294 §5.2 复现的是**裸 Node + loader**（不执行 `main.js`）的情形 —— 那条路径上
  loader 只拦 `import('undici')`，**不替换 `globalThis.fetch`**；
- 所以：**在宿主进程里跑的第三方插件不会踩这个坑**；只有在宿主之外单起 `node --jitless`
  跑脚本时才会（例如设备上直接验证用的临时命令）。

⇒ 这一项的**严重度应从"中"下调为"低（调试/脚本场景）"**，产品不需要为此改代码。
如果将来要在宿主外提供 fetch，正确做法是让那个场景也走 `installJitlessFetch()`，
而不是去改 undici 的解析器。

## 2. `__DSHM_BRIDGES__`：420 次/分钟的剩余泄漏点已定位并补强

### 2.1 294 提供的新线索

```text
CheckIsInJsPermission: permission map is empty or no object_id(1) key
```

报告据此判断"是**授权**问题不是注册问题"。这个方向是对的，但它指向的**不是**
"桥没注册"——`methodList` 与垫片调用已经逐条对齐（`check-bridge-methodlist` 绿）。

### 2.2 真正的剩余泄漏点：**调用抛异常时没有退避**

`applyHandheld()` 在 `docs/292` 里已经加了指数退避，但**只覆盖"方法不存在"**这一种：

```js
if (b === null || typeof b.platformForm !== 'function') { …退避… }
try { form = b.platformForm(); } catch (e) { return; }   // ← 这里直接 return，不进退避
```

当桥对象存在、方法也在 methodList 里，但**每次调用都抛**（正是 `permission map is empty`
的形态）时，`catch` 只"这一拍不做事"，**下一拍照样再调** —— 300ms 一拍，全变成
ArkWeb 侧的 `native proxy object not found` 日志。这与复测的 420 次/分钟（≈7 次/秒）吻合。

### 2.3 修法

把"调用抛异常"并进同一套退避（entry / phone 两处同步）：

```js
try { form = b.platformForm(); } catch (e) {
  bridgeMiss = Math.min(bridgeMiss + 1, 4);
  bridgeRetryAt = now + Math.pow(2, bridgeMiss) * 500;
  return;
}
```

`platformPcMode()` 同理。**只改探测节奏，不改任何形态判定**：桥一旦能正常应答，
下一拍即清零恢复全速。

### 2.4 预期与判据

- 若 420 次/分钟**全部**来自这条路径 ⇒ 退避后应降到 **≤ 4 次/分钟**（1s→2s→4s→8s 封顶）；
- 真机判据：重启后放 10 分钟，
  `grep -c "native proxy object not found, name:__DSHM_BRIDGES__" node-output.log` **零增量或个位数**；
- 若仍高速增长 ⇒ 说明还有**第三个**泄漏点（不在 `applyHandheld` 上），需按同样方法逐垫片排查。

## 3. 本轮新增的门禁：`check-cli-shim-semantics`

上一轮我在 `docs/292` 里**撤掉**过这条门禁（当时测试脚手架调不通，没验证成立的测试不该入库）。
本轮把它**真正做成**了：19 条判据 + 3 个对照臂，全部实跑通过。

### 3.1 为什么必须"真跑"

假壳是生成的 shell 脚本，两条缺陷全在执行语义里：

- 失败分支 `echo "[]"` 在 `exit` 之前 ⇒ **退出码被 `echo` 覆盖成 0**；
- `dir=$(pwd)` 无条件当 profile ⇒ 在 `/tmp` 下 404 却说"端点不可达"；
- 裸 `config` 什么都不打印却 rc=0。

正则判不出这些。门禁从 `main.js` 抽出**真实的 `CLI_SHIM_LINES`**，重建脚本后在假 HOME 下真跑。

### 3.2 判据（19 条）

| 组 | 判据 |
|---|---|
| A | list：pwd 是包目录 ⇒ rc=0、返回依赖树、path 就是 pwd、不打回落提示 |
| B | list：pwd 无 package.json ⇒ 回落 profile 且 stderr 点明 |
| C | list：端点 404 ⇒ **rc=1**、文案指向"不是包目录"、stdout 仍 `[]` |
| D | list：Host 连不上 ⇒ **rc=1**、文案"连不上 Host" |
| E | list：成功 ⇒ rc=0 且 stdout 是端点原文 |
| F | config 裸 / list / --json ⇒ 打印 registry、rc=0、stderr 有边界说明 |
| G | config get registry ⇒ 真值；其它键 ⇒ 空串 rc=0（上游口径不变） |
| H | config set / delete ⇒ **拒绝 rc=1** |
| I | 未知子命令 ⇒ 明确提示 rc=1 |

### 3.3 三个对照臂（都必须判红）

| 变异 | 结果 |
|---|---|
| list 失败分支把 `exit 1` 改成 `exit 0`（rc 被吞） | ✅ 判红（2 条） |
| config 列表分支退回静默空输出 | ✅ 判红（3 条） |
| list 去掉 profile 回落（退回无条件 pwd） | ✅ 判红（1 条） |

### 3.4 这条门禁踩过的三个坑（已写进文件头注）

1. **不能 `spawnSync`**：它阻塞本进程事件循环，而同进程的模拟 Host 就永远响应不了 ⇒
   门禁整体挂死。这正是上一轮"跑到 A 就没动静"的真因。必须 `spawn` + `await`。
2. **不能依赖本机 `/bin/wget`**：本机是 luckybox 变体，连 200 都不回正文。改为注入
   与 busybox wget 三态语义一致的假 wget。
3. 假 wget 直接 `exec` 到 node 代理，不经中转文件 —— 中转文件会引入"`$$` 可用性 /
   重定向顺序"两个与判据无关的失败面。

另：第一个对照臂最初设计成"删掉 `exit 1`"，结果**变异生效但判据不红**——因为脚本末尾
还有一条 `exit 1` 兜底。改成 `exit 0` 后才真正钉住"失败分支必须显式退出"。
