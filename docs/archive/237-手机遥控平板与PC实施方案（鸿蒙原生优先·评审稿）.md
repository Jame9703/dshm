# 237 · 手机遥控平板与 PC 实施方案（鸿蒙原生优先 · 评审稿）

> 日期：2026-10-24
>
> 状态：已对照本机 HarmonyOS SDK 和开发者官网智能体方案复核，**尚未实现**。
> 本轮 r6 不能声称已经具备远程控制。
>
> 用户目标：手机发现并遥控平板或 PC，创建、查看、追加、审批和停止 DSHM
> 会话，执行发生在被控设备。

## 1. 最终选型

采用“原生控制面 + DSHM 既有数据面”的混合方案：

| 层 | 方案 |
|---|---|
| 设备发现 | `distributedDeviceManager.getAvailableDeviceList()` |
| 可信连接与配对 | `abilityConnectionManager` |
| 小体积控制/配对消息 | `sendMessage()` / `sendData()` |
| DSHM 会话与文件数据 | 继续复用现有 Host HTTP RPC、`/api/remote.mux` 和事件流 |
| 非敏感临时 UI 状态 | 可选 `distributedDataObject`，不作为权限或正文传输通道 |
| 跨公网 | 被控端主动外连 WSS 中继；系统分布式能力只覆盖可信组网 |

不能把“分布式数据对象”当远程控制总线。官方一致性是最终一致，SDK 也明确其
不解析内容且不适合敏感数据；DSHM 的会话正文、审批、文件内容和 token 都不能
放进去。

也不能把 `abilityConnectionManager` 当成完整 HTTP/WebSocket 隧道：
`sendMessage()` 单条文本上限为 **1 KB**。它适合发现设备、批准配对、交换短期
连接信息和发送小块控制命令；完整会话流仍走 DSHM 已有协议。

## 2. SDK 核实结果

本机 SDK：

- `@ohos.distributedsched.abilityConnectionManager.d.ts`：API 18 起；
- `@ohos.distributedDeviceManager.d.ts`：API 10 起；
- `@ohos.application.DistributedExtensionAbility.d.ts`：API 20 起；
- `@ohos.data.distributedDataObject.d.ts`：API 9 起。

API 18 低于当前最低兼容 API 23，因此系统版本不是首版阻断项。真正的设备条件
是 `SystemCapability.DistributedSched.AppCollaboration` 和可信组网。

### 2.1 权限

`createAbilityConnectionSession()` 的 SDK 声明要求：

```text
ohos.permission.INTERNET
ohos.permission.GET_NETWORK_INFO
ohos.permission.SET_NETWORK_INFO
ohos.permission.DISTRIBUTED_DATASYNC
```

当前三端只有前两条，新增两条会扩大权限面：

| 权限 | SDK 等级 | 授权方式 | 是否需 ACL |
|---|---|---|---|
| `SET_NETWORK_INFO` | normal | system_grant | 否 |
| `DISTRIBUTED_DATASYNC` | normal | user_grant | 否 |

`DISTRIBUTED_DATASYNC` 必须在用户点击“允许本机被遥控”或首次发现设备时做运行时
授权。拒绝时整个原生设备列表与连接入口都明确显示“未授权”，不能逐次弹框。

### 2.2 官方示例中的五处偏差

开发者官网智能体给出的方向正确，但示例不能原样落地：

1. `PeerInfo.deviceId` 应取 `DeviceBasicInfo.deviceId`，不是 `networkId`；
2. `CollaborateResult` 只有 `ACCEPT = 0` 和 `REJECT = 1`，示例里的
   `COLLABORATE_START` 不存在；
3. 当前三个 `EntryAbility` 都是 `launchType: specified`，而官方 d.ts 明说
   `onCollaborate` **不支持 specified 模式**；不能为了遥控破坏现有多窗口入口；
4. `sendMessage` 只支持 1 KB，不能承载聊天正文或文件；
5. 三端 moduleName 不同，PC 对 `entry`、平板对 `tablet`、手机对 `phone`，
   不能三端都写 `entry`。

另外，`onCollaborate` 的 `wantParam` 只承诺支持
`ohos.extra.param.key.supportCollaborateIndex`。内部参数优先使用 SDK
`CollaborationKeys.PEER_INFO / CONNECT_OPTIONS`，不要依赖未进入 d.ts 的自由
字符串。

## 3. 被控端 Ability 设计

不要在现有 `EntryAbility` 上直接加 `onCollaborate`。新增独立
`CollaborationAbility`：

```text
entry 模块：moduleName = entry
tablet 模块：moduleName = tablet
phone 模块：moduleName = phone
launchType = singleton
```

它只负责：

1. 接收官方协作请求；
2. 创建并接受 `abilityConnectionManager` 会话；
3. 校验请求方设备、DSHM 版本和配对票据；
4. 向主应用 Host 进程转交“开始/停止/发送消息”事件；
5. 会话断开时释放资源。

这样保留 `EntryAbility(launchType=specified)` 的多会话、多窗口行为。

`DistributedExtensionAbility` 也提供 `onCollaborate`，但
`createAbilityConnectionSession` 的公开文档描述是拉起对端 **UIAbility**。
在真机证明 extension 能作为该 API 的对端前，不把“无界面”写成已确定能力。
若 `CollaborationAbility` 会强制被控端前台，首版必须如实接受这一交互；不能
为了后台而宣称不弹窗。

## 4. 原生握手

### 4.1 手机端

1. 请求 `DISTRIBUTED_DATASYNC` 运行时授权；
2. `createDeviceManager(bundleName)`；
3. `getAvailableDeviceList()`；
4. 只显示可信且在线的 DSHM 设备；
5. 用户选设备后，用其 `deviceId` 构造 `PeerInfo`；
6. 通过 `createAbilityConnectionSession()` 和 `connect()` 发起连接；
7. 接收被控端返回的短期配对结果与 Host 地址。

### 4.2 平板 / PC 端

1. `onCollaborate()` 校验协作 token；
2. `acceptConnect()`；
3. 只在用户已开启“允许被遥控”时接受；
4. 生成一次性会话票据；
5. 通知 Host 准备远程入口；
6. 返回 `AbilityConstant.CollaborateResult.ACCEPT`。

短消息格式保持小于 1 KB：

```json
{
  "v": 1,
  "type": "pair.request",
  "requestId": "…",
  "deviceId": "…",
  "clientVersion": "1.1.6"
}
```

敏感 token 不放在设备名、分布式数据对象、日志或通知里；只经已建立的原生会话
发送，并在手机端写入现有 `SecretStore`。

## 5. 数据面

### 5.1 局域网

原生握手完成后，被控端打开**单个私网地址**的 Host 入口：

- 不使用 `0.0.0.0`；
- 继续保留 token/cookie 和 `/api/remote.mux`；
- 手机加载目标 Host Web UI；
- 页面常显“远程设备：xxx”；
- 关闭遥控或断开原生会话后重新绑定 `127.0.0.1`。

网络地址通过 `connection.getDefaultNet()` 与
`getConnectionProperties().linkAddresses` 获取。不能用原生设备 ID 代替 IP。

### 5.2 公网

系统分布式能力要求可信组网，不是公网遥控方案。跨公网仍应：

```text
手机 ──TLS/WSS──> DSHM Relay <──TLS/WSS── 平板/PC
```

被控端主动外连，不开放入站端口。中继只转发加密帧，设备绑定、短期 ticket、
撤销和审计仍由账号服务承担。

## 6. 分阶段落地

### P0：原生能力真机探针

在手机与 PC/平板同一可信组网中验证：

- 权限申请成功；
- 设备列表能读到 PC/平板；
- `PeerInfo` 能拉起独立 `CollaborationAbility`；
- `connect/acceptConnect` 成功；
- 双向 `sendMessage` 和 `sendData` 成功；
- 断网、拒绝、关闭遥控后的错误码可读。

P0 未通过前不改业务 UI，也不宣称已支持遥控。

### P1：系统设备选择器

- 手机设置页显示可信 DSHM 设备；
- 未授权、无设备、能力裁剪三种空态分开；
- 设备选择后进入配对；
- 不接触 DSHM 会话数据。

### P2：原生握手 + 局域网 Host

- 被控端显式开关；
- 独立 CollaborationAbility 接系统协作；
- 原生通道交换一次性票据和私网地址；
- 手机 WebView 加载目标 Host；
- 会话、审批、停止和文件预览直接复用现有协议。

### P3：公网中继

- 账号绑定设备；
- 双向 WSS 与端到端密钥；
- 设备撤销和短期 ticket；
- 中继不解析正文。

## 7. 代码改造清单

| 层 | 改动 |
|---|---|
| 三端 `module.json5` | 申请 `SET_NETWORK_INFO`、`DISTRIBUTED_DATASYNC`，声明独立 CollaborationAbility |
| `platform` | 运行时权限、可信设备列表、网络地址、配对票据加密保存 |
| `entry/tablet/phone` | `CollaborationAbility` 与 onCollaborate 接线 |
| `hostruntime` | 显式远程开关；私网 Host 参数；关闭后回 loopback |
| `WebApp` | 本地/远程目标切换与设备标识 |
| `connection/appstate` | 复用现有连接、认证、事件流与远程设备状态 |
| 云端 | Relay、账号绑定、短期 ticket、审计 |

## 8. 安全与验收

红线：

- 默认关闭；
- 不进 `distributedDataObject` 的敏感内容；
- 不关闭 DSHM 审批；
- 不使用 `0.0.0.0`；
- 不在日志、通知、设备名中泄露 token；
- 不因系统连接成功就跳过 DSHM 自身鉴权；
- 原生会话断开后立即撤销远程 Host 入口。

最小验收：

1. 手机首次使用只弹一次分布式授权；
2. 设备列表只含可信设备；
3. PC/平板拒绝协作时不启动远程 Host；
4. 手机新建一轮，PC 出现用户消息和流式输出；
5. 手机审批/拒绝/停止与 PC 同步；
6. 文件预览和“文件管理”入口在远程模式下仍受用户目录范围限制；
7. 断开原生会话后，局域网地址立即不可用；
8. 重启被控端后旧票据失效；
9. 日志、通知与分布式对象中无会话正文或 token。
