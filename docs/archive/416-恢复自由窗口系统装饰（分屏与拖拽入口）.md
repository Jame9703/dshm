# 416 恢复「手持形态 + 自由窗口」的系统装饰（分屏与拖拽入口）

**状态更正（2026-11-12）：仅 FLOATING 恢复装饰的代码已落地，真机未闭环。** 下文“标题栏是分屏唯一入口”“隐藏装饰就是全部根因”“分屏也已覆盖”的表述撤回：官方有手势/Dock 等入口；当前条件没有 SPLIT_SCREEN；系统 PC 分类及 Tablet 悬浮窗限制是独立问题。详见[故障调查报告](../outputs/DSHM-故障调查报告-20261112.md)。

**现象**：平板用户反馈分屏、自由窗口入口不可用。以下窗口诊断来自用户粘贴的平板反馈，并非市场 r23 文档本体：

- `diag-decor-top`：`handheld=true rawType=tablet show=false`；
- `diag-decor-caps`：`present=false`、`status=1:FULL_SCREEN`，窗口状态历史里只有 `FULL_SCREEN` / `MINIMIZE`，从未出现 `SPLIT_SCREEN`；
- `module.json` 没有 `supportWindowMode` 字段（缺省即 `["fullscreen","split","floating"]`），代码也没有调用 `setSupportedWindowModes`。

**根因：`docs/391` §3 把 `pcMode` 改成恒 `false`**

原逻辑是 `pcMode = isHandheldForm() && statusPre === FLOATING`：平板一进自由窗口就保留系统装饰，换来四边缩放边框。11-07 以「移动端 APP 没有顶栏、平板不要 PC 灰条」为由改成：

```ts
const pcMode: boolean = false;
win.setWindowDecorVisible(false);
```

当时**只登记了一个代价**（失去四边缩放边框），漏登记了第二个、也是更致命的：**系统标题栏同时是平板分屏的唯一入口**（三键菜单里的「分屏」，或把窗口拖到屏幕边缘）。自绘顶栏又没有实现 `startMoving()`，拖拽一并消失。

而且它形成自锁环：没有装饰 ⇒ 进不了 `FLOATING` ⇒ `refreshDecorCaps()` 里「进入自由窗口恢复装饰」那段永远没有执行机会 ⇒ 一启动就锁死在全屏无装饰状态。

**修法（用户 2026-11-12 裁决「A」）**

| 位置 | 改动 |
|---|---|
| `EntryAbility.afterWindowStageReady()` | 恢复 `pcMode = isHandheldForm() && statusPre === FLOATING`（启动时先读一次窗口状态）；`pcMode` 为真时 `setWindowDecorVisible(true)` 并调用新增的 `showTitleButtons()` 把三键拉回来，否则维持隐藏 |
| `EntryAbility.refreshDecorCaps()` | 恢复「自由窗口 ⇄ 最大化/全屏」跟随：进 `FLOATING` ⇒ 显示装饰 + 三键（`decorHiddenOk=false`）；离开 ⇒ 重新隐藏。三键策略与装饰策略在同一处按 `pcMode` 决定 |
| `EntryAbility.showTitleButtons()` | 新增：`setWindowTitleButtonVisible(true,true,true)`，失败只记诊断 |

**取舍（明确登记）**：自由窗口 / 分屏里会多出一条系统标题栏，状态栏也交还系统——这正是 11-07 否决过的观感。换来的是**分屏与窗口拖拽可用**。全屏（含手机全屏）仍然隐藏装饰、保持沉浸；PC / 2in1 走 `isHandheldForm()===false`，不受影响。

**门禁**：`tools/check-decor-button-mode.mjs`（第一组 9/0、第二组 99/0，对照臂 A–R 全绿）、`tools/check-window-mode.mjs`（27/0，仍钉住 `platformForm` 不得因 `pcMode` 改答 desktop）。

**边界**：本机无 hdc，真机需复核——平板右上角三键出现、能从三键菜单进入分屏、能把窗口拖成自由窗口；手机全屏仍无标题栏。
