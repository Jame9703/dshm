## 3 性能与内存（含一条订正）

### 3.1 PC 2in1：1.2 GB 是 guest VM 的常驻成本，不是泄漏

主进程 pid 51978 三轮采样（`%TEMP%\dshm-pc-memtrend-*.txt`）：
`1,149,848 kB → 1,198,176 kB → 867,688 kB → 848,312 kB`；线程数 86→87 稳定。

- 1.15–1.20 GB 的**平台段**与 `docs/120` 记的 VmRSS ≈1.22 GB 对得上（随包 guest VM）。
- 中途 330 MB 级下跌是 V8 回收造成的锯齿，不是"漏了又收"。
- ⇒ 判定：**常驻取舍**，非异常占用、非泄漏。

### 3.2 手机：订正上一轮"VM 未常驻"的读法

上一轮只看 VmRSS 小（≈360 MB）就写了"VM 未常驻"，**这是错的**。本机实读：

| 读数 | 值 |
|---|---:|
| `VmRSS` | 363,640 kB |
| `RssAnon` | 105,796 kB |
| `VmSwap` | **880,332 kB** |
| `Threads` | 105 |
| `/proc/<pid>/stat` vsize | 52,266,291,200 B（TCG 代码缓存 + guest 映射） |

决定性证据三条：① `/proc/net/unix` 里 `qga_socket` / `qmp_socket` / `term1` 全是 LISTEN，
且 `qga_socket` 有一条已连（QEMU 与宿主客户端）；② `vm/rootfs.qcow2` 55,508,992 B、
`serial.log` 16,965 B、`tmp/*` 5 个 socket 都在；③ 同进程 vsize 52 GB。

⇒ **VM 是常驻的，只是被系统换出到 swap**：手机档同样承担约 1.2 GB 的 guest 成本，
只是账记在 swap 上。终端冷启动 **10.6 s**（`00:27:09 → 00:27:20`，与 `docs/119` 的 11.8 s 同级）。

### 3.3 前台正常、后台被系统冻结（本轮新增定性）

- **前台段**（`00:26–00:35`，含冷启动与首启解包）：事件循环停顿 1.6–3.5 s，符合冷启动预期。
- **退到后台后**：`node-output.log` 共 14 次 `LOOP-GAP`，最大 **2,033,077 ms（33.9 分钟）**；
  其后续出现 5 次**规整的 86.2–86.3 s 停顿**（间隔约 91 s 一轮）。
- 判据：这 5 次停顿期间进程 CPU 只涨 **5–8 jiffies（50–80 ms）**、内核 `state=S`、
  同步调用合计最多 1694 ms（远不足以解释 86 s）⇒ **进程根本没被调度**，不是自旋、不是死锁、
  也不是换页抖动（换页的内核时间会记在进程 stime 上）。
- ⇒ 判定：这是**系统对后台应用的冻结/配额调度**（~91 s 周期给 ~5 s 运行窗口），
  与 `docs/158` 那次"设备侧 OOM 风暴 + 系统冻结"同族，**不是应用缺陷**；
  期间 hdc 侧读取、进程存活（pid 48264 未变）都正常。

**决定性实证（本轮复读）**：同一次读取里 `/proc/48264/cgroup` =
`1:freezer:/Frozen` —— 进程**当时就在冻结组里**；同一时刻
`VmRSS 114,160 kB / VmSwap 982,160 kB / Threads 105`（RSS 掉到 114 MB 是**换出**，
不是"内存漏了又吐"，与 §3.2 那次 363 MB 的采样差值全部记在 swap 上）。

**归因边界（如实声明）**：屏幕 / 电源状态在本轮读不到 ⇒ 无法区分
"熄屏休眠"与"后台冻结策略"，只能确认"进程没被调度"这一层；不据此推断策略细节。

### 3.4 与历次"内存又炸了"的关系

## 5 4 条 P1 残余风险（登记，本轮不改）

不改的理由统一是：这些都动核心树或宿主插件 ⇒ `coreVersion` 变更 ⇒ 侧载件与送审件**必须重出
并重跑真机验收**，超出本轮"只审"的范围。全部**如实登记**，供下一轮排期。

### P1-1 guest VM 没有优雅停机（唯一有数据完整性含义的一条）

- 证据：插件导出了收尾口 `hostcore/plugins/dshm-vm-bash/lib/index.js:317-320` 的 `shutdown()`，
  但宿主 `hostcore/app/main.js` 里 **0 处引用**（全仓 grep 无命中）；停机链只有
  `requestStop()`（`main.js:5257-5278`）→ `dsh` 的 `shutdown()` → 1.5 s 后 `process.exit(0)`；
  而插件卸载钩子（`index.js:304-308`）**显式不** `stop()`（注释写明"停机交给宿主退出"）。
- 加剧因素：镜像盘是 `cache=writeback`（`vm.js:441` 的 `-drive …`）⇒ 强杀可能留下半写 qcow2。
- **爆炸半径（这条决定了它为什么登记而不紧急）**：qcow2 里只有 **guest OS 与 apk 装进 guest 的包**；
  用户工作区走 9p 共享、落在**宿主侧**（`vm.js:330`）。最坏情形是 guest 需要重灌
  （删 `rootfs.qcow2` 后由 `vm.js:463-471` 从 resfile 重拷），**不丢用户会话 / 插件 / 工作区**。
- 修法（下次动核心树时）：宿主退出前 `await` VM 的 `shutdown()`，并对 QEMU 走 QMP `quit`（`vm.js:1037-1058` 已有实现）。

### P1-2 每命令的脚本 / stdin / spill 写入是 fire-and-forget

`handle.js:72-78, 122, 136, 201-211`：`createWriteStream().end(buffer)` 不等 `finish`、无 `error` 监听。
影响面限于**单条命令的临时脚本/输入**没落全 ⇒ 该条命令报错，不污染持久数据。

### P1-3 终端输出没有背压

`terminal.js:309` 的 `new PassThrough()` + `337-343` 的 `output.write(chunk)` 忽略返回值 ⇒
下游消费慢时缓冲无界增长。触发面：在终端里打印超大输出（例如 cat 一个大文件）。
本轮真机实测输出量小，未观测到增长；按"未复现但成立"登记。

### P1-4 `/dshm-shot` 预览图代理的两个小口子

`main.js:3963-3977`：丢弃被拒响应体时不 `cancel()`；10 MB 上限对 `chunked`（无 content-length）
响应无效。触发面限于"市场缩略图代理"，且 URL 走 https 白名单 + 仅 127.0.0.1。
