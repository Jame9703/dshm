## 1. 侧栏浏览器卡死（P0：端口偏移导致扩展永不回连）

### 1.1 现象

侧边栏内置浏览器输入地址回车 ⇒ 界面一直"正在打开…"，不出现页面、也不报错。

### 1.2 完整调用链（逐段取证）

```text
侧栏 UI（官方插件 dsh-client-ui-sidebar-browser）
  └─→ navigate 工具（hostcore/plugins/dshm-tool-browser/lib/index.js）
       └─→ invokeTool(): statusClients() 为空 ⇒ ensureClient(target)
            ├─ ① 请求 /dshm-open-link（Host HTTP）→ 写 open-link/<id>.req 文件队列
            ├─ ② entry/.../OpenLinkBridge.ets 轮询取到 ⇒ startAbility(com.haitai.htbrowser)
            ├─ ③ 写 <id>.done {ok:true,detail:"startAbility(...)"}  ⇒ Host 答 ok=true
            └─ ④ 轮询等扩展回连 WS（LAUNCH_CONNECT_BUDGET_MS = 15000ms）
                 └─→ 扩展 background.js 连的是 ws://127.0.0.1:19390/browser-bridge
                     ← 宿主实际监听 ws://127.0.0.1:19391/browser-bridge
                     ⇒ 15s 预算耗尽 ⇒ UI 侧"正在打开…"无限转
```

### 1.3 根因（两处端口不一致，坐实）

| 侧 | 端口 | 出处（可复查锚点） |
|---|---|---|
| **扩展**（写死，不可跟随） | `19390` | `hostcore/browser-extension/background.js:5`<br>`const BRIDGE = 'ws://127.0.0.1:19390/browser-bridge?token=dshm-browser-beta';` |
| **宿主**（运行期计算） | `19391` | `hostruntime/.../runtime/RuntimePort.ets:209`<br>`DSHM_BROWSER_PORT=${BROWSER_BRIDGE_DEFAULT_PORT + (port - HOST_DEFAULT_PORT)}` |

**算术**（`RuntimePort.ets:116/118`）：`BROWSER_BRIDGE_DEFAULT_PORT=19390`、`HOST_DEFAULT_PORT=3120`，
beta 包主端口 = `3121` ⇒ `19390 + (3121 - 3120) = 19391`。

**宿主侧实读**（本次真机日志）：

```text
2026-10-29T07:24:01.728Z browser-bridge: listening ws://127.0.0.1:19391/browser-bridge
```

**已部署扩展副本同样写死 19390**（不是"部署了旧版"）：

```text
~/Download/com.dshm.dshmbeta/dshm-browser-ext-v11/background.js:5
  → ws://127.0.0.1:19390/browser-bridge
```

⇒ **只要跑的是 beta 包（或任何非正式包），浏览器桥必然连不上**。正式包（主端口 3120）刚好对得上，
所以这个问题**在正式包上不会暴露**，只在 beta / 其它包名上出现 —— 这正是它拖到现在的原因。

### 1.4 现场佐证（本次实测读数）

| 判据 | 读数 | 含义 |
|---|---|---|
| `GET /dshm-browser/status` | `{"ok":true,"port":19391,"clients":[]}` | 宿主桥活着，**零客户端** |
| `GET /dshm-browser/invoke?tool=navigate&…` | `{"ok":false,"error":"没有已连接的浏览器扩展（请在目标浏览器中加载并启用 DSHM Browser Bridge 扩展）"}` | 宿主明确判定"无扩展" |
| `open-link-bridge-heartbeat` | `07:37:32.994Z startAbility ok id=… bundle=com.haitai.htbrowser` | **拉起是成功的**，浏览器确实被叫起来了 |
| 拉起后浏览器进程 | 无 `haitai` 进程存活 | 起来后又被系统/自身回收，或起来即退 |
| `node-output.log` | `browser-autoclose: armed url=…/dshm-browser/start` | 拉起链走通了，只差回连 |

> 结论：**不是浏览器没装、不是 `openLink` 不通、也不是扩展没加载** —— 是**端口对不上**。
> 用户"加载了扩展却永远连不上"的体感，与 `docs/176`（`background.js:9-19` 那段 alarms 自愈注释）
> 描述的"宿主重启后扩展静默离线"是**同一类症状、不同根因**，排查时不要混为一谈。

### 1.5 建议修法（三选一，推荐 B）

**A. 扩展侧改成"候选端口扫描"（改动最小，但仍是枚举）**

`background.js` 的 `BRIDGE` 由常量改为候选列表，依次尝试 `19390…19399`
（与主端口偏移区间同宽），首个连上即停，失败按既有退避重试：

```js
const BRIDGE_PORTS = [19390, 19391, 19392, 19393, 19394];   // 正式 3120 ⇒ 19390
function bridgeUrl(port) { return `ws://127.0.0.1:${port}/browser-bridge`; }
```

- 优点：**只改扩展一处**，老宿主、新宿主都兼容；
- 缺点：端口是枚举出来的，多个 DSHM 实例并存时可能连到"另一个"桥上。

**B. 扩展启动页参数下发（推荐）**

扩展被 `startAbility` 拉起时，URL 里带真实端口；扩展从 `location` 兜底读取：

```text
http://127.0.0.1:19391/dshm-browser/start?port=19391
```

`background.js` 优先用 `chrome.tabs` 当前页 URL 的 `port` 参数，取不到再回落 `19390`。

- 优点：**端口是宿主告诉它的，不是猜的**；多实例也能连对；
- 代价：需要 `tabs` 权限（manifest 已声明）；`/dshm-browser/start` 要带上 `port`。

**C. 扩展改从宿主 HTTP 端口推导（最稳，改动稍大）**

扩展先 `GET http://127.0.0.1:<任意已监听端口>/dshm-browser/status` 拿 `port` 字段再连 WS
（`status` 已经返回了 `port`：`{"ok":true,"port":19391,…}`）。仍需一个"探测哪些 HTTP 端口在听"的入口，
故通常与 A 组合。

**无论选哪个，都必须同步做**：

1. `hostcore/browser-extension/` 与已部署副本 `~/Download/com.dshm.dshmbeta/dshm-browser-ext-v11/`
   **两处一起改**（后者是用户实际加载的那份，只改仓库不生效）；
2. 版本号从 `0.11.1` 升一位（`manifest.json`），否则浏览器不会重载扩展、用户无法判断是否换了新版；
3. 更新 `check-browser-*` 类门禁里对 `19390` 的断言（见 §5）。

### 1.6 验收判据

```bash
# 1) 宿主桥自报端口应与扩展实际连接端口一致
curl -s http://127.0.0.1:19391/dshm-browser/status   # port 字段
# 2) 扩展加载并启用后，clients 必须非空
curl -s http://127.0.0.1:19391/dshm-browser/status   # 期望 {"ok":true,"port":19391,"clients":[{...}]}
# 3) 侧栏输入地址回车 ⇒ 页面出现（不再"正在打开…"）
```

## 2. 可观测性缺陷（P1：`startAbility` 假成功）

### 2.1 事实

`entry/src/main/ets/system/OpenLinkBridge.ets:236-251`：

```ts
async function startBrowserBundle(bundle: string, url: string,
  abilityCtx: common.UIAbilityContext): Promise<boolean> {
  try {
    const want: Want = { bundleName: bundle, action: 'ohos.want.action.viewData',
      entities: ['entity.system.browsable'], uri: url };
    await abilityCtx.startAbility(want);
    return true;                    // ← 只要没抛异常就报成功
  } catch (e) {
    hilog.warn(...); return false;
  }
}
```

**`startAbility` resolve 只代表"系统受理了这个 Want"，不代表目标应用真的起来了。**
心跳据此写 `done id=… ok=true`，Host 据此答 `launched`，而 `ensureClient()` 的
`launched: launch.ok === true` 于是变成**不可信的成功口径**，UI 侧无从区分"起来了但没回连"
与"根本没起来"，只能落到同一个 15s 超时。

### 2.2 本次对照实验（证明该口径不可信）

| 传入 bundle | 心跳记录 | 结论 |
|---|---|---|
| `com.haitai.htbrowser`（真实存在） | `startAbility ok` | 报成功 |
| `com.this.browser.does.not.exist`（**不存在**） | `startAbility 失败 …… 回退 openLink`，随后 `done ok=true` | **同样报 ok** |

⇒ 两条完全不同的路径都报 `ok=true`，**该字段对"浏览器是否真的起来"零信息量**。

### 2.3 建议修法

1. `startBrowserBundle()` 之后**做一次存在性确认**（任一即可）：
   - 等 `clients` 非空（现有 15s 预算已经做了，但要把它变成**判定依据**而不是事后超时）；
   - 或查目标 bundle 是否在运行（`bundleManager` 能查到"运行中进程"即可）；
2. `done` 载荷增加 `pending: true` 语义：**"已受理、尚未确认"** 与 **"已确认可达"** 分开；
3. Host 侧 `ensureClient()` 把 `launched` 与 `connected` **分别**呈现给 UI，
   UI 才能说"浏览器没起来，请检查默认浏览器"而不是无限"正在打开…"；
4. `docs/275` 的 `check-open-link-bridge` 建议加一条对照臂：
   **把 `return true` 改成基于实际状态的判定，故意让状态为假 ⇒ 判据必须能报出"未就绪"**。

### 2.4 验收判据

- 浏览器未安装/未起来时，侧栏应**在 15s 内给出明确文案**（而不是一直转圈）；
- 心跳里能区分 `startAbility 受理` 与 `扩展已回连` 两件事。

## 3. 沉浸光感"看不出效果"（P2：符合预期，不是没接入）

### 3.1 先确认：材质**确实已接入并在运行**

| 判据 | 读数 |
|---|---|
| 应用级开关 `ohos.arkui.UIMaterial.state` | `entry/src/main/module.json5:36-41` = `enable` |
| 共享工具 | `platform/src/main/ets/ui/ImmersiveMaterialKit.ets`，含 API<26 判定 + try/catch 双兜底 |
| 弹窗挂载 | entry 4 处 / phone 3 处 `dialogMaterial()`（THICK） |
| 顶栏挂载 | `WebApp.ets:3538` `topBarShellMaterial = shellMaterial()`（THIN）；`:6133-6134` 让位 `Color.Transparent` + `.systemMaterial(...)` |
| 设备 API | `const.ohos.apiversion` = **26**（满足 `< 26 ⇒ undefined` 的闸门） |
| 设备件 vs 交付包 | `entry.hap` 77/77、`hostruntime.hsp` 133/133 条目**逐字节一致** |
| 运行期异常 | `diag-web-console` 无 `ImmersiveStyle`/材质相关报错、无闪退 |

### 3.2 为什么"看不出来"——四个原因叠加（都不是缺陷）

**① Web 画布本身就是纯白，THIN 取色后还是白**

官方 UI 底色 token 链（`@deepseek-ai/dsh-client-ui-theme`）：

```text
--dsw-alias-bg-base → --dsw-static-neutral-00: #fff
```

THIN 材质的本质是"背景模糊 + 取色"。**背景是纯白，取出来的仍是白**，毛玻璃在白底上几乎不可辨。

**② 顶栏只挂了一条 THIN 条带**

按 `docs/196` 的染蓝教训（`ImmersiveMaterialKit.ets:56-62` 注释），`shellMaterial()` 取 **THIN**
且**只挂条带、不铺大面** —— 面积小 + 档位最薄 ⇒ 视觉增量本就很小。

**③ 材质只覆盖原生浮层，不作用于 Web 画布**

`docs/parity-matrix.md` 的既定口径："材质只覆盖**原生浮层**（Dialog/Menu/Sheet/文本选择菜单），
渲染面是 Web 画布 ⇒ 不给 Web 界面换皮"。所以你日常看的聊天区、侧栏，**本来就不该变化**。

**④ 系统「沉浸光感」设置可整体调弱**

官方原文：同一材质效果会受系统设置「沉浸光感」配置项影响。若系统侧调低，应用侧挂得再对也会变淡。

### 3.3 想看出来的正确验证路径（按证明力排序）

| 顺序 | 动作 | 为什么能看出来 |
|---|---|---|
| **1** | 点一条 Markdown 外链 ⇒ 确认框 | 走 `dialogMaterial()` = **THICK 最厚档**，背景模糊 + 取色最明显 |
| **2** | 系统切到**深色**模式再看顶栏 | THIN 在深底上反差才显出来；白底是它的最差展示条件 |
| **3** | 滚动页面时盯顶栏下缘 | 内容从下缘透出模糊；静态时几乎无差 |
| 4 | 会议面板按钮（`MeetingPanel`） | `controlMaterial()` = REGULAR + interactive，按压有光感 |

> 若**深色 + 弹窗确认框**都毫无变化，才需要怀疑未生效；那时的第一步检查是
> `topBarShellMaterial` 是否为 `undefined`（即被 `sdkApiVersion` 判定或 try/catch 兜底吞掉了）。

### 3.4 可选增强（**需先拍板，不属缺陷**）

| 方案 | 改动 | 风险 |
|---|---|---|
| 顶栏 THIN → REGULAR | 改 `shellMaterial()` 一档 | 更明显，但 `docs/196` 的染蓝风险随之上升 |
| 深色主题下才挂顶栏材质 | 加 `colorMode` 判据 | 只在能看出来的场景生效，白底下退回纯色（**推荐**） |
| 顶栏材质加 `feature` 开关 | 加 env / 桥方法 | 用户可 A/B 对比，出问题秒回退 |

## 4. 顺带发现（P2）

### 4.1 `native proxy object not found` 仍在刷（277 未竟）

| 判据 | 本次读数 | `docs/277` 声称 |
|---|---|---|
| 该行出现次数 | **4280 次 / 本档 70896 行** = 6.0% | "全链 124,648 次 / 占 60%" |
| 速率 | 约 **18 次/分钟**（14 分钟窗口） | 约 3720 次/小时 |
| `platformPcMode` 调用 | **2141 次，全部成功** | 曾每拍报错 |

⇒ **277 的修复确实生效**（`platformPcMode` 不再报错），但**报错源没有归零**：
`__DSHM_BRIDGES__` 这一层代理查找仍在失败。`docs/277` §5 "增速应归零"的验收判据**未达成**，
需要单独定位（粗看与"原生侧未注册 `__DSHM_BRIDGES__` 这个对象本身"有关，
而非具体方法名 —— 方法已在 `methodList` 里）。

**建议**：`check-bridge-methodlist.mjs` 目前只判"垫片调用的方法 ⊆ methodList ⊆ 定义"，
建议加一条**运行期**判据或把本项登记为独立待办 —— 静态名单无法覆盖"对象级未注册"。

### 4.2 `check-immersive-material` 的"零就地 new"只扫 `WebApp.ets`

`entry` / `phone` 的 `MeetingPanel.ets:750` 各有一处 `new uiMaterial.ImmersiveMaterial(opts)`，
门禁未覆盖。**该处自带完整双兜底**（`sdkApiVersion < 26` 判定 + try/catch，见 `:739-754`），
**功能无缺陷**，只是"兜底纪律单源"的目标未达 100%。

建议：门禁扫描面从"只 WebApp"扩到 `entry`/`phone`/`platform` 全部 `.ets`，
并把 `MeetingPanel` 的本地 `materialOf()` 收编到 `ImmersiveMaterialKit`（消除双实现）。
