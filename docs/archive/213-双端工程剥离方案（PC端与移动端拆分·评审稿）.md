## 0. 结论摘要

**一句话**：当前代码库不是一个「可以被一刀切成两半」的工程，而是一个**用运行时形态判据把三端装进同一个包**的工程。拆分可行，但拆分的正确边界不是 UI，而是「**入口壳 + 能力面 + 权限清单**」；UI 与核心必须保持单一真源。

三条必须先讲清的结论：

1. **UI 不能复制**。`entry` 的界面代码 25,728 行（`pages/` + `view/`）里，PC 与手持共用同一套三形态响应式布局，形态判定 100% 在运行时完成（`platform/src/main/ets/system/DeviceFacts.ets`），不存在编译期分支。把它按端复制成两份，等于制造两份会立刻漂移的 2.5 万行代码。
2. **「不同权限」的实际差额只有 1 条**。8 条权限里，真正只在 PC 侧有使用点的只有 `PREPARE_APP_TERMINATE`（托盘 / 任务栏真退出收尾）。`ALLOW_EXTERNAL_NATIVE_CODE` 与 `FILE_ACCESS_PERSIST` 被本地核心与目录授权共同依赖，移动端摘不掉——除非移动端**不跑本地核心**。所以「为权限而拆」的收益上限，取决于 §9-D3 那个产品级选择。
3. **包体不会因为拆工程而变小**。当前 HAP 439 MB 的构成是 libnode（126.8 MB）、核心树 zip（95 MB）、guest VM（65 MB）、toolchain（35 MB）、QEMU（34.8 MB）、Python（23 MB）等**运行方式资产**。它们的取舍由「移动端跑什么」决定，与工程是否拆分无关。

因此本方案推荐的顺序是：**先把能力面显式化并冻结（P1）→ 再把源码重排成 core / kit / shell 三层（P2）→ 最后复制出第二个工程壳（P3）**。每一步都以「产出与基线逐项等价」为验收门，任何一步不等价就停在那一步。

### 1.2 形态判定机制：运行时，不是编译期

```
deviceInfo.deviceType ──► FormFactor { PHONE, TABLET, DESKTOP, UNKNOWN }
        │                        ▲
        └─ QXS-* / MatePad Edge ─┘ 强制 DESKTOP（isEdgePcSeries）
```

- 归一化与强制桌面：`platform/src/main/ets/system/DeviceFacts.ets`（`isEdgePcSeries`、`formOf`）
- 手持档判据：`platform/src/main/ets/system/FilePicker.ets` 的 `isHandheldForm()` = PHONE ∪ TABLET
- 直板机判据：同文件 `isPhoneForm()` = PHONE 且非折叠屏
- 顶栏 / 三键让位 / 底部安全区 / 返回手势 / 抽屉侧栏 / 首启自愈，全部读这两个判据

**结论**：代码里没有任何 `#if PC` 式的编译期分支。同一个 HAP 装到三端，行为由设备事实决定。这是拆分方案必须保住的性质——一旦把判据换成编译期常量，就等于把「一套已验证的真机行为」拆成「两套各自未验证的行为」。

### 1.4 权限面：谁在用，能不能摘

| # | 权限                           | 级/授予                   | 使用点                                                              | 移动端可否摘                     |
| - | ---------------------------- | ---------------------- | ---------------------------------------------------------------- | -------------------------- |
| 1 | `INTERNET`                   | normal / system_grant  | Host 回环 + 远程 Host                                                | 否（核心必需）                    |
| 2 | `GET_NETWORK_INFO`           | normal / system_grant  | 连接诊断、网络切换重连                                                      | 否                          |
| 3 | `KEEP_BACKGROUND_RUNNING`    | normal / system_grant  | `EntryAbility.maybeAcquireHandheldKeepAlive()`（**手持档也在用**）+ 长时任务 | **否**（除非移动端放弃后台续跑）         |
| 4 | `PREPARE_APP_TERMINATE`      | normal / system_grant  | 仅 `onPrepareToTerminate`：托盘右键退出 / 任务栏退出收尾                        | **可以**（移动端三键关闭即官方退出，不走该回调） |
| 5 | `ALLOW_EXTERNAL_NATIVE_CODE` | **system_basic / ACL** | 加载应用数据区的原生件（koffi / node-pty / python 桥 / 插件原生模块）                | **否**（本地核心必需）              |
| 6 | `FILE_ACCESS_PERSIST`        | **normal / ACL**       | `persistPermission` 记住目录授权、跨启动 `activatePermission`              | **否**（工作区目录授权必需）           |
| 7 | `STORE_PERSISTENT_DATA`      | normal / system_grant  | 偏好 / 凭据 / 主题持久化                                                  | 否                          |
| 8 | `MICROPHONE`                 | normal / user_grant    | Web 语音输入 + 会议录音                                                  | 否（移动端语音输入是主路径）             |

**结论**：**8 → 7**，差额只有第 4 条。这条结论直接决定 §9-D3 的取舍：如果不接受「移动端只少一条权限」，那么"不同权限"这个拆分理由不成立，拆分应改按「**独立发版 + 包体 + 审核节奏**」来论证。

同时注意：本仓的权限铁律（`AGENTS.md`「权限面铁律」）写的是「**本包**恒 8 条，第 9 条永不写」。拆成两个包后，这条必须改写成「**每包各自恒等且不超基线**」，并让 `tools/check-permission-surface.mjs` 从单值硬编码改成**按包读清单**。这是 P1 的必做项，否则拆完门禁立刻误报。

## 2. 六个决定性发现

### F1 界面层不可按端复制

证据：`entry/pages` + `entry/view` 共 25,728 行，`Index.ets`(4,465) 声明「单栏 / 双栏 / 三栏按**窗口宽度**切换」，`WebApp.ets`(6,085) 是唯一 `loadContent` 的页面（`EntryAbility` 第 1307 行）。两端各存一份 = 两份必须永远同步的 2.5 万行。

### F2 「不同权限」的差额只有 1 条

见 §1.4。剩下 7 条被本地核心与目录授权共同依赖。**除非移动端不再本地跑核心**，权限差不可能拉开。

### F3 平板是跨界设备，按 deviceType 切会切错

平板（`deviceType=tablet`）当前走**手持档**全套规则（抽屉、返回手势、底部避让），但**横屏要显示顶栏**；而 MatePad Edge（`QXS-*` / 市场名命中）被**强制识别为 desktop**（`isEdgePcSeries`）。于是：

- 若「移动端 = 手机 + 平板」：MatePad Edge 会装到移动包，却要求 desktop 行为 ⇒ 移动工程必须保留全部 PC 分支 ⇒ 拆分不产生任何隔离。
- 若「移动端 = 手机」「PC 端 = 平板 + 2in1」：MatePad Edge 自然落在 PC 侧，语义自洽。

**这是本方案里最容易被忽略、但会直接决定成败的一条。** 推荐后者。

### F4 两个工程 = 必须两个包名 = 必有一端数据断裂

HarmonyOS 一个 `bundleName` 对应一个应用身份、一套 el2 数据、一条发布版本流。因此：

- 要「两个独立工程、各自独立发版」⇒ 必须 `com.dshm.dshclient.pc` / `...mobile` 之类两个包名；
- 其中一端改名后，**该端已装机用户的数据（会话 / 工作区 / 插件 / 凭据）不会跟随**，跨 bundle 读不到对方 el2（沙箱隔离），只能靠「应用内导出 → picker 选文件 → 新包导入」的一次性迁移功能承接；
- 若坚持「同包名、一次上架、数据连续」⇒ 只能一个 `.app` 里放两个 entry HAP（按 deviceTypes 分发），**无法独立发版**。

> ⚠️ `[需核实]` 「同一 bundleName 在 AGC 只有单一版本流」这一条按当前 AGC 发布模型表述；执行前应在 AGC 侧确认是否存在「按设备类型分版本」通道。若存在，本发现降级为「发版耦合度」问题而非「必须改名」。

### F5 拆分不复制 400 MB 资产

资产不在 git，由脚本现场放置（`.gitignore` 第 33–55 行）。所以「两个工程」的磁盘成本 = 两套生成物（各约 400 MB），可用「一份源、两个放置目标」共用，不必两份源。

### F6 工作树在飞，必须先冻结

见 §1.6。306 项未提交改动横跨迁移与适配两条线。

## 3. 拆分边界设计（目标结构）

### 3.1 分层原则

拆的是**壳**，不是**肉**：

```
┌─────────────────────────────────────────────┐
│ apps/<端>/entry        壳：30–200 行         │  module.json5 / 权限 / deviceTypes /
│                        能力开关 / override    │  Ability 子类 / 页面包装
├─────────────────────────────────────────────┤
│ kit/（HAR，单一真源）                        │  connection / dshcompat / appstate /
│  · appshell：DshmEntryAbility 基类            │  platform / ui
│  · ui：DshmWebApp 组件 + view/*              │  ← 25,728 行 UI 只此一份
├─────────────────────────────────────────────┤
│ core/（单一真源）                            │  hostcore / hostruntime / recipe / assets
└─────────────────────────────────────────────┘
```

### 3.2 目标目录

```text
DSHM/                                  # 一个仓库（推荐，见 §9-D1）
├── core/
│   ├── hostcore/                      # 原 hostcore/（Host JS + 插件 + profile + 浏览器扩展）
│   ├── hostruntime/                   # 原 hostruntime/（HAR）
│   ├── recipe/                        # core-recipe*.json（核心版本唯一钉点）
│   └── assets/                        # 生成物：libs/ resfile/ node-headers/（不入库）
├── kit/
│   ├── connection/  dshcompat/  appstate/
│   ├── platform/                      # 原 platform/（机制层，PC/手持两套判据仍在内部）
│   ├── appshell/                      # 【新增】DshmEntryAbility 基类 + 生命周期骨架
│   └── ui/                            # 原 entry/ets/pages + view（改为 HAR 组件库）
├── apps/
│   ├── dshm-pc/                       # DevEco 工程（deviceTypes: 2in1, tablet）
│   └── dshm-mobile/                   # DevEco 工程（deviceTypes: phone）
├── tools/  docs/  third_party/  spec/
└── .github/workflows/gates.yml        # 双工程矩阵
```

### 3.4 三处必须新增的抽象（这是拆分的真实工作量）

1. **`DshmEntryAbility` 基类**（`kit/appshell`）：把 2,512 行里与端无关的 95% 提出来，端差异只留 3 个 override —— `onSetupDesktopChrome()`（托盘 / `windowWillClose`）、`onSetupKeepAlive()`、`onCloseBehavior()`。**不做这一步，两个工程就要各存一份 2,512 行，必然漂移。**
2. **页面包装**：`apps/*/entry/src/main/ets/pages/WebApp.ets` 变成 20 行包装，body 只有 `<DshmWebApp />`。`main_pages.json` 仍指向本模块路径，绕开 HAR 不能直接注册为入口页的限制。
3. **能力清单（capability manifest）**：`capabilities/pc.json` / `capabilities/mobile.json`，逐项声明「该端是否具备：托盘 / 多窗 / 浏览器自动化 / 原生终端 / 会议 / VM 档位」。清单是**门禁的唯一裁判**，代码注册点必须与清单一致（新增 `tools/check-capability-surface.mjs`）。

## 6. 权限面裁剪：实测计划

### 6.1 候选与判据

| 候选                                 | 摘除理由                                                        | 证伪条件（出现即回退）                                                        |
| ---------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------ |
| `PREPARE_APP_TERMINATE`（移动端）       | 移动端三键关闭 = 官方退出，不经过 `onPrepareToTerminate`；该回调只服务托盘 / 任务栏真退出 | 真机上出现「退出时核心未停 / 托盘残留 / 通知未撤」；或日志显示 `onPrepareToTerminate` 被调用且有副作用 |
| （可选）`KEEP_BACKGROUND_RUNNING`（移动端） | 仅当产品决定移动端**不做后台续跑**（切后台即暂停任务）                               | 切后台后任务中断、回前台不续 ⇒ 产品决定不成立，回退                                        |

### 6.2 方法（与仓库既有文化一致：不猜，量）

1. 用现有 `tools/strip-ungranted-acl-perms.mjs` 的同族思路，产出「移动端 7 权限」实验包（不删源码声明，只在构建期摘除，便于回退）。
2. 真机覆盖安装（**只允许 `hdc install -r`**），采集：`diag-tray`（应完全无输出）、`diag-window-close`、核心启动日志、`bm dump` 的 `requestPermissions`。
3. 跑 10 项冒烟：启动 / 会话 / 工作区授权与重启恢复 / 插件安装 / 终端（guest）/ 语音输入 / 卡片 / 覆盖安装后数据仍在 / 切后台回前台 / 退出。
4. 读数写入 `dist/acceptance/`，结论写进新的编号文档；失败即回退并记录失败形态。

### 6.3 OQ1（若走路线 B 必做）

单工程双 entry、同 bundleName 时，**模块级 `requestPermissions` 是否只对实际安装的那个 HAP 生效**？验证方法：造一个两 entry 的测试包，装到手机后 `bm dump` 看 `requestPermissions` 是否只剩移动端那 7 条。若答案是"两端权限被合并"，路线 B 的权限隔离收益归零，必须改走 A。
