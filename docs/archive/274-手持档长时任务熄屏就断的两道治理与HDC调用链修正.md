## 1. 根因（两条，都有代码级证据）

### ① 申请判据太窄：只看"界面投影"，熄屏那一刻判成"没事"

手持档的保活只在 `onBackground` 申请，且要求（`EntryAbility.maybeAcquireHandheldKeepAlive`）：

```ts
busy = snap.running === true || snap.pending.length > 0;   // ← 只有两条
```

而 `running` / `pending` 是**界面投影**：Host 侧明明还在跑模型、还有待发队列，投影可能仍是
idle 或晚一拍 ⇒ 熄屏那一刻判成"没事" ⇒ **不申请长时任务** ⇒ 进程被冻 ⇒ 任务断。

### ② 被系统取消后无人补救（10 分钟规则）

手持档只能用 `DATA_TRANSFER`，官方契约是**首次进度超过 10 分钟未更新即被取消**
（`docs/209` 已抓到 603s 现场）。原实现的取消监听只记原因：

```ts
this.active = false;
this.cancelReason = `reason=${info.reason} id=${info.id}`;
if (USER_CANCEL…) { this.userStopped = true; }
```

**没有任何续期**（`userStopped` 只用于"用户停过就不再申请"）⇒ 长任务 10 分钟后必断。

## 2. 修法（两道，都不碰权限面）

### 2.1 判据扩到"在途事实"（`EntryAbility.maybeAcquireHandheldKeepAlive`）

```ts
busy = snap.running === true || snap.pending.length > 0
  || snap.activeStreams > 0 || snap.outbox > 0;      // ← 新增两条在途事实
needNote = `running=… pending=… streams=… outbox=…`;
this.keepAlive.noteBackground(busy);                 // 告知"本后台周期想不想保活"
this.keepAlive.recordNeed(`${needNote} ⇒ busy=${busy}`);   // 四项读数落 diag
```

`activeStreams` = 控制流 + follow 逻辑流仍开着（Host 正在推事件）；`outbox` = 还有待发队列。
四项读数进 `files/diag-keepalive` ⇒ 真机反馈可直接逐项对账"判据是不是又判错了"。

### 2.2 系统取消 ⇒ 退避续期（`KeepAlive`）

- 新增 `noteBackground(wanted)` / `recordNeed(note)`；`refs` 归零时连带清掉续期与后台期许；
- 取消监听里，**非用户主动停** + 仍想保活 + 还有人要 ⇒ `scheduleRenew()`：
  退避 `10s × (n+1)`，单周期最多 3 次，连续失败只留一行诊断（不无限重试）；
- `renewNow()` **不动引用计数**，沿用**上次成功申请的类型**（手持档恒 `DATA_TRANSFER`，
  不越权换 `TASK_KEEPING`）；
- 官方接入规范只禁止"**用户主动停止**后立即再申请"，系统侧取消不受此限 ⇒ 续期合规。

> ⇒ 效果：把"10 分钟必断"变成"每 10 分钟续一次，最多连续续 3 次"；
> **根治**仍需 `KEEP_BACKGROUND_RUNNING_SYSTEM`（ACL 审批后把手持档改成优先 `TASK_KEEPING`、失败降级）。

## 3. HDC 调用链修正（`tools/lib/hdc-client.mjs`）

### 3.1 现象与定性

本机（应用域）实测：`hdc list targets` **rc=0、stdout 空、stderr 空**；`/data/local/tmp`
不可访问、看不到 hdc 服务端进程 ⇒ hdc 自身不可用。而旧实现把"完全无输出"与真·`[Empty]`
混为一谈 ⇒ 装机/验收工具显示「没有设备（`hdc list targets = [Empty]`）。接上设备后重跑」，
**把"这台机器的应用域调不动 hdc"说成了"你没插设备"**。

### 3.2 修法

- 新增 `probeHdc(hdc)`：返回 `{available, targets, port, raw, stderr, silent, note}`；
- **本机回环场景**（`docs/260` 口径）封进来：`param get persist.hdc.port` → `tconn
  127.0.0.1:<port>` → 重列一次；桌面平台没有 `param` ⇒ 该路自动不参与；
- 区分三种"空"：`[Empty]`（真·无设备）/ **沉默**（hdc 不可用）/ 其它异常，各给人话；
- `listTargets()` 保留签名，内部改走 `probeHdc().targets`（既有调用方自动受益）。

### 3.3 调用方同步

- `tools/update-device.mjs`：设备检查改报「hdc 不可用（**不是**"没有设备"）」+ 下一步
  （桌面终端 / DevEco 侧运行，或设 `DSHM_HDC`）；实跑读数 rc=3、报文准确 ✓；
- `tools/device-code-fingerprint.mjs`：**修掉上次移植里写错的设备段** ——
  `runHdc` 的真实签名是 `(hdc, target, args, opts)`，原代码按 `(args, opts)` 调；
  `listTargets` 还被当成 Promise。⇒ 该工具的**设备路径从未真正跑过**（当时只跑了不碰 hdc 的
  `--self-test`）。现改用 `probeHdc()` 并按真实签名调用，无设备时如实 rc=2「未验证」。

## 4. 门禁补判据（`tools/check-memory-guard.mjs`）

新增 **E7–E9**：⑦系统取消后必须退避续期（钉**调用形态** `this.scheduleRenew();`，而不是
"函数定义存在"——定义还在时删掉调用点必须判红）；⑧手持档 busy 判据必须含在途事实
（`snap.activeStreams` / `snap.outbox`）+ 判据读数落 diag；⑨续期沿用上次成功类型
（`await this.requestMode(this.lastMode, this.lastModeLabel)`）。

新增 **3 组对照臂**：M11 去掉系统取消后的续期 / M12 判据退回只看界面投影 / M13 续期越权换
`TASK_KEEPING`。实跑：**正例 0 失败，M1–M13 全部判红**。

## 6. 真机复验清单

1. **熄屏（不是锁屏不熄屏）后**让 Agent 跑一个长任务（>10 分钟），观察是否仍被断；
2. 看 `files/diag-keepalive`：应出现 `need running=… pending=… streams=… outbox=… ⇒ busy=true`、
   以及被取消后的 `renew 计划第 N 次，…ms 后（DATA_TRANSFER）` / `renew 成功`；
3. 若仍断在 10 分钟附近：说明续期也没接上（拿 `diag-keepalive` 的 `cancel reason=` 与我核对），
   或已触到"连续 3 次放弃"上限 —— 那就是 `KEEP_BACKGROUND_RUNNING_SYSTEM` 的活儿（ACL 后续）。

> HDC 侧（若要在本机跑装机/验收）：应用域调不动 hdc 属环境边界，工具现在会**如实**说
> 「hdc 不可用（不是没有设备）」；请在桌面终端 / DevEco 侧运行，或设 `DSHM_HDC` 指向可用的 hdc。
