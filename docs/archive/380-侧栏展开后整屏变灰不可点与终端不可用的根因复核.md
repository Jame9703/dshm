## 4. 两条互相独立的根因

### 根因 A（手机/窄屏）：我们的侧栏被官方遮罩压在下面

我们的 `.dshm-sbcol{z-index:40}` **低于**官方 `drawerMask{z-index:70}`。
抽屉一展开 ⇒ 遮罩铺满、`pointer-events:auto` ⇒ 侧栏虽然画出来了，但**被半透明+模糊的遮罩盖住（看起来就是"灰的"），且所有点击被遮罩吃掉**。

0.2.1-rc.5 没有 `drawerMask`（`inert`/`drawer` 计数均为 0），所以 `z-index:40` 当时完全正确 —— 这正是「0.2.1 没这个问题」的原因。

> 顺带说明：上一轮我把 `inert` 整页清掉是对的（它确实会冻结主区），但**它不是主因**。清掉 inert 之后遮罩还在，所以现象没变。

### 根因 B（平板）：状态被 opener 污染

`entry` 壳的 `findToggle()` **没有跳过 `data-sidebar-opener`**：

```ts
for (var i = 0; i < buttons.length; i++) {
  if (buttons[i].id === FAB_ID) { continue; }        // ← 只有这一条跳过
  var label = buttons[i].getAttribute('aria-label');
  if (label !== null && (has(COLLAPSE_LABELS, label) || has(OPEN_LABELS, label))) { return buttons[i]; }
}
```

opener 的 `aria-label` **恒为「打开侧边栏」** ⇒ `stateOf()` 永远返回 `'collapsed'` ⇒ 我们的 CSS 把侧栏轨道压成 0、⊞ 常驻，且所有 `[data-dshm-sidebar=…]` 样式与官方真实状态**整体错位**。

## 5. 修复方案（不再打补丁，改为「把抽屉交还官方」）

### 5.1 状态源换掉（两壳都改）

- 唯一状态源：`frame[data-sidebar-collapsed]` / `frame[data-sidebar-drawer]`（**JSX 字符串字面量，压缩不改名**，比 aria-label 稳）。
- `aria-label` 只作兜底；`data-sidebar-opener` 永不参与状态。
- 收益：平板档的「恒 collapsed」立刻消失；手机档不再依赖「侧栏里还有一颗 toggle」这个脆弱假设。

### 5.2 抽屉几何交还官方（手机 <768）

- **删掉**我们自绘的 `#backdrop`（z-35）与 `.dshm-sbcol{z-index:40}` 那套覆盖式几何。
- 官方 `drawerMask` + `sidebarCol(z-71)` 本身就是标准移动端抽屉：面板全高、点外部关闭、主区不可点（这是**正确**语义，不是 bug）。
- 我们只保留三件事：① 手机档隐藏 `[data-sidebar-opener]` 保持「只有一颗 ⊞」；② ⊞ 点击直接点 opener（drawer 态下它就是唯一开关）；③ 状态同步到 `<html data-dshm-sidebar>` 供 CSS 用。

### 5.3 窄带 768–1023（分屏/自由窗口）保留我们的覆盖式侧栏

- 这一段官方只给「图标轨 + narrowExpanded」，形态不是移动端该有的。
- 保留现有覆盖式 CSS，但 **z-index 抬到 80**（>71），并且**不再自绘 backdrop**（改用官方 mask，避免两套遮罩打架）。
- 用 `@media (min-width:768px) and (max-width:1023.98px)` 精确限定，杜绝再压到 <768。

### 5.4 平板默认展开

- 进页面后若 `!data-sidebar-collapsed` 则什么都不做；若是 collapsed，**主动 click 一次 opener**（仅一次，带 6s 有界重试），实现「默认左侧边栏打开」。

### 5.5 `inert` 处理保留

- 作为防御层保留（整页清 + MutationObserver），但它不再是唯一手段。

### 5.6 终端

- 侧栏修好后，若仍无请求：加一条「终端打开探针」—— 点终端时先打 `[dshm-terminal] 请求进入 spawnTerminal`，把「没点进来」和「点进来但 VM 起不来」彻底分开。
- `dshm-vm-bash` 的 VM 启动日志目前一条不打（只在接管时打 4 行），建议把 `VM boot start / 耗时 / 失败原因` 补进 hilog，下次日志能直接定位。

### 5.7 云同步（不猜）

- 代码侧能做的只有「把事实打出来」：把 `cloudSyncState` 的 `code` / `schedule` / `message` 原文写进 hilog，并在界面上让错误文案可长按复制。
- 需要你确认 AGC 三项：①「数据类型名称」是否合法字母数字（如 `dshmsyncunits`）；②「**本地表名称**」是否填 `sync_units`；③是否「实施变更到生产环境」+ 退出华为账号重新登录。
- 这台设备系统侧已经在喊 `offCloudSync,please register` / `User is not logged in` ⇒ **账号态本身可能就是拦路虎**，与代码无关。

### 8.2 报文对应到代码

用户看到：`端侧VM 不可用：guest 命令超时（30000 ms）`

```
vm.js:1620  catch(error) → return { ok:false, error: message }
index.js:282  throw new Error(`端侧 VM 不可用：${outcome.error}`)
qga.js:588   const error = new Error('guest 命令超时（' + timeoutMs + ' ms）')
```

`30000` 不是终端命令的超时（`handle.js` 的兜底是 3,600,000 ms，`qga.call` 默认 20,000 ms），
它**精确等于 `vm.js:99` 的 `PROVISION_PROBE_MS = 30000`** —— 即 **provision 探测段**：

> 探测段 30 s（只挂载 + 判 `/bin/bash`），安装段 600 s（首装是分钟级）

也就是说：**VM 本身已经起来了（QGA 已就绪），卡在「挂共享目录 + 探测 /bin/bash」这一步**。
一旦这一段抛超时，整个 VM 被判 `failed`，终端就拿不到会话 ⇒ 报「端侧 VM 不可用」。

### 8.3 为什么云调试上特别容易踩

- 云调试的"手机"本身跑在虚拟化环境里，应用内的 guest 只能退到 **TCG 软件模拟**（日志档位 `tcg=64MiB`，`guest=256MiB` economy）。
- TCG 下 guest 的 I/O 与 CPU 都慢一个数量级，**30 s 探测预算在真机够、在这里不够**。
- 而它是**一次判死**：超时即 `phase='failed'`，没有分级重试。

### 8.4 终端修复方案

1. **探测段改分级重试，不再一次判死**：`30s → 60s → 120s`（仅对 `DSHM_VM_TIMEOUT` 这类超时重试；guest 返回非零退出码等语义失败**不重试**，避免把真错误拖成三倍等待）。
2. **新增覆盖开关** `DSHM_VM_PROVISION_PROBE_MS`，云调试/慢机型可临时调大。
3. **失败后闸门要放开**：现在靠 `reviveIfAlive()` 兜底，改成显式允许下一次重试，杜绝「必须重启应用才能再试」。
4. **终端首启给进度而不是红字**：显示「首次启动虚拟机，约需 1–2 分钟」，期间不判失败。
5. **错误文案带证据**：`阶段 + 耗时 + 串口尾部（serialTail 已有）` 一起进报文与 hilog，下次一眼看出是"慢"还是"死"。
6. （可选）识别模拟器/云调试环境，自动把预算 ×3。

### 8.5 需要补的日志

请重抓一次**包含 Info 级**的日志（云调试里选「全部日志」，或 `hdc hilog`），至少覆盖「点终端 → 报错」全过程。
过滤关键字：`DSHM-NODELIVE`、`dshm-vm-bash`、`DSHM-NodeRuntime`。
有这三类行，才能确认是「探测慢」还是「9p 挂载/串口卡死」——两者的修法不同（前者调预算，后者换挂载方式）。
