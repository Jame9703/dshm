## 2. 资产归属（依据代码与平台能力表）

> **修正（2026-11-11 23:32，用户指出）**：普通平板（tablet）的 bash 由 **guest VM** 支撑，
> 与手机同属 VM 侧；只有 2in1 / PC / Edge 这类"桌面档"才走原生终端工具链。
> 因此归属轴不是「PC vs 手机」，而是 **原生终端档 vs VM 档**。

| 资产 | 2in1 / PC（原生终端） | 平板 tablet（VM） | 手机 phone（VM） | 依据 |
|---|:---:|:---:|:---:|---|
| core zip + libnode + koffi/pty/dshhost | 需要 | 需要 | 需要 | 三端 Host 都跑 Node |
| `resfile/toolchain/*`（bash/git/python/npm/pnpm/tmux/gh） | **需要** | **不需要** | **不需要** | 只有桌面档用原生终端；平板/手机走 guest |
| `libs/libpython*` | **需要** | **不需要** | **不需要** | Python 工具只在桌面档提供 |
| `resfile/vm/*`（qcow2/kernel/guestpkgs） | **不需要** | **需要** | **需要** | 平板与手机的 bash 都靠 QEMU + 9p |
| `libs/` QEMU 闭包 | **不需要** | **需要** | **需要** | 同上 |
| sharp/vips/rsvg 图像闭包 | 需要 | 需要 | 需要 | 插件通用，按公共处理 |

**关键结构约束**：`entry` 这一个 HAP 同时声明 `tablet` 与 `2in1`，也就是说
**同一个安装模块里既有 VM 档设备、又有原生终端档设备** ⇒ entry 依赖的 HSP 必须同时带两套资产，
无法只靠"拆 HSP"让 2in1 瘦下来。

**预期体积**（HSP 单份，按不同形态真正需要的并集）：

| 形态 | 现在 | 只拆 HSP 后 | 降幅 |
|---|---:|---:|---:|
| 手机 | 486.6 MB | **约 406 MB** | -16.5% |
| 平板（tablet） | 486.6 MB | 486.6 MB | 0（entry 仍带两套） |
| 2in1 / PC | 486.6 MB | 486.6 MB | 0（entry 仍带两套） |

> 想让 2in1 真正瘦，必须把 `entry` 按 `tablet` / `2in1` 拆成两个 HAP（见 §7 的数据风险）。

## 3. 三种可选落地方式（按风险从低到高）

### A. 只拆手机 HSP（安全，建议先做）

- 新增 `hostruntime-phone`（deviceTypes 仅 `phone`）：只带公共 + VM 资产；`phone` 依赖它。
- `entry` 继续用现有 `hostruntime` 全量包 —— 平板与 2in1 共用一个 HAP，无法只瘦其中一端。
- 收益：手机 **-79.2 MB**；平板 / 2in1 不变。数据零风险（phone 模块名与数据目录都不变）。

### B. 把 entry 按设备类型拆成两个 HAP（收益最大，但动数据目录）

- `entry-tablet`（tablet，VM）+ `hostruntime-vm`；`entry-pc`（2in1，原生终端）+ `hostruntime-native`。
- 收益：2in1 **-128 MB**、平板 **-79.2 MB**、手机 **-79.2 MB**。
- 代价：entry 模块被拆 ⇒ 数据目录从 `haps/entry/files` 变成 `haps/entry-*/files`，旧数据会"看不见"，
  必须做迁移（见 §4），且要升 versionCode。

### C. 只给测试出「PC 专用裁剪包」（不改正式结构）

- 用同一份 manifest 在构建期裁剪，产出只含 2in1 所需资产的 Beta 侧载包；AGC 仍为全量单包。
- 收益：PC 侧载立刻 **-128 MB**；零数据风险、零模块变更。
- 代价：只解决测试侧载，不是正式瘦身。

## 4. 两个 HSP 会不会丢数据 / 能否无损升级

1. **HSP 里没有用户数据**。HSP 只装代码与资源；DSHM 的会话、工作区、插件、凭据都在
   `/data/storage/el2/base/haps/<module>/files/...`（entry 或 phone），HSP 自身没有数据目录。
2. **只"多一个 HSP"、模块名与 HAP 模块名都不变** ⇒ 数据路径不变，覆盖升级不会丢数据。
   卸载/覆盖安装只替换代码包，el2 数据保留；既有门禁 `check-user-data-preserved` 仍然适用。
3. **真正的风险是把 entry HAP 拆开**：`filesDir` 与模块名绑定，拆完新模块读到的是新目录，
   旧 `haps/entry/files` 里的 `dsh/home` 会"看不见"。同应用同 uid 下理论上可按绝对路径读旧目录做迁移，
   但 dsh/home 可能有几 GB～几十 GB，首启复制耗时长，失败会表现得像丢数据。
4. **版本号**：结构变更必须升 versionCode（1010015 → 1010016），否则同版本覆盖安装可能被系统拒绝。
5. **回滚**：若走 B，"旧路径兜底读"至少要保留一个版本，确认迁移成功后再清理。

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 手机误删工具链后插件报错 | 手机本就不用 PC 工具链；裁剪后跑 `check-vm-bash` + 插件安装/运行用例 |
| 平板被误裁 VM 资产 | 平板继续用全量 `hostruntime`，不进裁剪通道 |
| 图像闭包归属判断错 | 按公共保留，真机用例确认后再裁 |
| 签名/Profile 与新模块不匹配 | 复用同一 release Profile（8 条 ACL），逐模块验签 |
| 结构变更导致同版本覆盖失败 | 若走 B 必须升 versionCode；A/C 不改结构，无此问题 |
