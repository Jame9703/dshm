## 2. 验证页做了什么

### 入口

```text
顶栏「应用」→「端云同步验证」
```

### 前置步骤（自动）

| 步 | 内容 |
|---|---|
| 建库 | `dshm_sync_probe.db`，`securityLevel: S1`（与会话数据等级一致，不用低等级糊弄） |
| 建表 | `sync_probe`，字段见 §3 |

### V3：表结构自检

```
PRAGMA table_info(sync_probe)
```

把本地表的**字段名 + 类型**打印出来 —— 这串就是要拿去 AGC 建云侧表对照的。

### V1：容量验证

依次写入 **1 / 3 / 5 / 7 / 10 MB** 的 BLOB，**写完再读回逐字节比对**。

> 【为什么必须读回】只写成功不算数：RDB 可能接受写入但读回截断。
> 判据是**读回字节数与原数据一致、且内容逐字节相同**。

写的数据是有规律的（每字节 = 下标 & 0xFF），所以能真正逐字节校验，不是只看长度。

### V2：端云同步

```ts
setDistributedTables(['sync_probe'], DISTRIBUTED_CLOUD, { autoSync: true })
cloudSync(SYNC_MODE_PUSH, ['sync_probe'], progress)
```

两步：
1. **声明云端分布式表**（`DISTRIBUTED_CLOUD = 1`，不是 `DISTRIBUTED_DEVICE`）
2. **手动推一次** —— `autoSync` 的时机由系统决定，验证时等不到，手动推能立刻拿到成败

### 收尾

自动删除 V1 写入的大 BLOB（1–10 MB 纯粹测上限，没有同步价值，留着会把云侧撑爆）。
另有「删除测试表」按钮可整表清场。

## 3. 表结构（AGC 云侧要按这个建）

```sql
CREATE TABLE sync_probe (
  unit_id     TEXT PRIMARY KEY,
  workspace   TEXT NOT NULL,
  session_id  TEXT NOT NULL,
  version     INTEGER NOT NULL,
  sha256      TEXT NOT NULL,
  bytes       INTEGER NOT NULL,
  updated_at  INTEGER NOT NULL,
  payload     BLOB
);
```

**字段类型对应关系**（官方口径：云侧字段类型要与本地对应）：

| 本地 | 云侧 |
|---|---|
| `TEXT` | String |
| `INTEGER` | Long / Integer |
| `BLOB` | — **需确认云侧是否支持二进制** |

> ⚠️ **`BLOB` 这一列是最大风险点**。如果 AGC 云侧不支持 BLOB，就得改成
> 把字节转成 Base64 存 TEXT（体积 +33%）。这也是 V2 要看的东西之一。

## 5. 三种结果对应的架构决策

### 结果 A：V1 全绿 + V2 通

✅ **按 `docs/304` §3 的原设计落地**：

```text
会话代际（不可变 .jsonl.zstd）
    → 一个代际 = 一条 sync_units
    → RDB（DISTRIBUTED_CLOUD + autoSync）
    → 云端 → 另一端拉取还原
```

### 结果 B：V1 在某档失败

在 `unit_id`/`version` 之外加 `part` 序号，把大代际切片：

```sql
unit_id = '<workspace>/<session>/<version>/<part>'
```

**架构不变**，只多一层切片与重组。

### 结果 C：V2 不通

回到路线一（Drive），但**先提工单确认鸿蒙支持**。

## 9. 2026-10-29 23:43 修正（依官方端云同步配置说明）

用户提供官方配置路径后，修了三处，其中两处是**真 bug**：

| # | 问题 | 原实现 | 修正 |
|---|---|---|---|
| 1 | **`app.json5` 缺应用级开关** | 无 | `"cloudStructuredDataSyncEnabled": true` |
| 2 | **`SYNC_MODE` 用错** | `SYNC_MODE_PUSH`（syscap = RelationalStore.**Core**，设备间） | `SYNC_MODE_NATIVE_FIRST` / `SYNC_MODE_CLOUD_FIRST`（syscap = CloudSync.**Client**） |
| 3 | **表字段带 `NOT NULL`** | 全部 NOT NULL | 全部去掉（官方硬约束） |

### 9.1 云调试日志证据（23:32 那份）

  ← 缺 cloudStructuredDataSyncEnabled，系统不建同步通道

  message = Parameter error. The mode must be a SyncMode of cloud.

  ← 首次建库的正常提示，可忽略

### 9.2 一处与官方示例不一致（以 SDK 为准）

官方示例把 `autoSync` 写在 `StoreConfig` 里：

```ts
const storeConfig = { name:'note.db', ..., autoSync: true };
```

但**本机 SDK（apiVersion=26）的 `StoreConfig` 里没有 `autoSync`** —— 逐行查 d.ts，它只存在于：

```ts
interface DistributedConfig { autoSync: boolean; }   // since 10
```

因此实现为：

```ts
await store.setDistributedTables([PROBE_TABLE],
  relationalStore.DistributedType.DISTRIBUTED_CLOUD,
  { autoSync: true });
```
