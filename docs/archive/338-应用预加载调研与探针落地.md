## 1. 调研结论：华为的「预加载」有五个不同技术，只有两类适用我们

| 技术 | 归属 | 适用 | 判断依据 |
|---|---|---|---|
| **应用预加载 App Preload** | Ability Kit（系统级） | ✅ 能受益，但要改结构 | 系统按用户习惯自动做，**开发者不写接入代码**；但可用 `getAppPreloadType()` 感知并据此调整 |
| **AppStartup 启动框架** | Ability Kit | ✅✅ 最对症 | `startupTasks` 支持 `schedulerPhase: preAbilityStageLoad` + `runOnThread: taskPool`，可并行化初始化 |
| ArkWeb `precompileJavaScript` | ArkWeb | ✅ 有价值 | 生成 JS 字节码缓存；`CacheOptions.responseHeaders` **由我们自报 ETag**，不依赖服务端 |
| ArkWeb `prefetchPage` | ArkWeb | ⚠️ 收益有限 | 本地回环资源本来就快；且要求 controller 已挂 Web 组件 |
| ArkWeb `prepareForPageLoad`（预连接） | ArkWeb | ❌ 基本无用 | `127.0.0.1` 无 DNS 解析、TCP 握手亚毫秒级 |
| ArkWeb `prefetchResource` | ArkWeb | ❌ 不适用 | SDK 明确只支持 **POST + `application/x-www-form-urlencoded`**；我们 API 走 JSON POST |
| 组件级预加载（Tabs/Swiper `preloadItems`） | ArkUI | ❌ 不适用 | 首页不是这类容器 |
| Cloud Foundation 数据预加载 | 云服务 | ❌ 不适用 | 需开通预加载服务；我们资源全在本地 |
| Preview Kit 文件预加载 | Preview Kit | ❌ 不适用 | 文件预览场景 |

### 1.1 关键 API（本机 SDK 实证，`@ohos.app.ability.application.d.ts`）

```ts
export enum AppPreloadType {   // since 22
  UNSPECIFIED = 0,                   // 未预加载
  TYPE_CREATE_PROCESS = 1,           // 预加载到「进程创建完成」
  TYPE_CREATE_ABILITY_STAGE = 2,     // 预加载到「AbilityStage 创建完成」
  TYPE_CREATE_WINDOW_STAGE = 3,      // 预加载到「WindowStage 创建完成」
}
export function getAppPreloadType(): AppPreloadType;
```

**官方约束（SDK 原文）**：只有在 `AbilityStage.onCreate` 首次执行**之前**调用才拿得到真实值；
AbilityStage 创建完成后预加载数据被清除，之后再调恒返回 `UNSPECIFIED`。
⇒ **`AbilityStage.onCreate` 是全应用唯一能读到它的地方。**

### 1.2 为什么这三档深度决定我们能不能拿到收益

| 我们的重活放在哪 | 什么时候跑 |
|---|---|
| `UIAbility.onCreate` / `onWindowStageCreate` 之后（**现状**） | **等用户点击才跑** |
| `AbilityStage.onCreate` | **预加载阶段就会跑掉** |

若真机读数常见 `2` / `3`，把 `installBundled()` 与 `host.start()` 前移即可显著缩短
"点开 → 可用"的等待；若恒为 `0`，则 App Preload 这条路**无收益**，
资源应全押到 AppStartup 的并行解包（与系统是否预加载无关的确定性收益）。

### 1.3 AppStartup 的能力边界（本机 SDK `appStartup.json` schema 实证）

- `startupTasks[]`：`runOnThread: mainThread | taskPool`、`waitOnMainThread: boolean`、
  `dependencies`、`excludeFromAutoStart`、`schedulerPhase: preAbilityStageLoad | postAbilityStageLoad`
- `appPreloadHintStartupTasks[]`：**so 预加载**（API 18+），**只能 `taskPool`**，不支持系统 so
- `systemPreloadHintStartupTasks[]`：带 `ohmurl`（系统 so 名）
- 已知坑：任务类必须 `@Sendable`；**循环依赖会让所有任务静默不执行**；
  taskPool 里不能碰 UI；`waitOnMainThread` 设错会让首页取不到数据而崩；
  `module.json5` 字段名是 `appStartup`（全小写）

## 2. 本轮落地：预加载类型探针（只加日志，不改行为）

### 2.1 改动

`entry` / `phone` 两壳的 `AppAbilityStage.ets`：

```ts
onCreate(): void {
  super.onCreate();
  rememberAppPreloadType(probeAppPreloadType());   // ← 唯一新增
  ...（原有 appRecovery 逻辑一字未动）
}
```

- `probeAppPreloadType()`：读 `application.getAppPreloadType()`，打一行 `DSHM-PRELOAD` 日志，
  **整个调用包在 try/catch 里**——设备系统低于 API 22 时符号不存在，
  抛异常会打死 AbilityStage ⇒ 应用起不来。「探针失败」绝不升级成「启动失败」。
- `rememberAppPreloadType()`：写 `AppStorage`（键 `dshAppPreloadType`），**同样包 try/catch**。

> **为什么 AppStorage 也要包**：`AppStorage` 是 ArkUI 全局态，**本工程既有代码从未在
> AbilityStage 层用过**（其余调用点都在 EntryAbility 及之后，即 UI 上下文起来后）。
> AbilityStage.onCreate 可能早于 ArkUI 运行时初始化 ⇒ 直接写有抛异常风险。
> 这条信息只用于后续决策，**存不下也没关系**。

### 2.2 刻意没做的事

- **没有**移动任何初始化、没有改启动顺序、没有加 AppStartup 配置。
- 本轮产物与上一版 `.105` 的行为**逐字相同**，只多两行日志。

## 4. 需要你做的（一次冷启动即可）

装包后**冷启动 2–3 次**（最好包含「从桌面图标点开」和「隔一段时间再点开」两种），
然后抓日志，搜 `DSHM-PRELOAD` 这一行：

```
DSHM-PRELOAD 本进程预加载类型=N（…）
```

| 读数 | 含义 | 下一步 |
|---|---|---|
| `0` 未预加载 | 系统没预加载我们 | App Preload 无收益 → 全押 AppStartup 并行解包 |
| `1` 进程 | 只建了进程 | 收益有限 |
| `2` AbilityStage | 连 AbilityStage 都建好了 | **前移初始化，预期省 6–8 秒** |
| `3` WindowStage | 连窗口都建好了 | **前移初始化 + 可直接预载 Web，最大收益** |

> 这一行是后面所有优化方向的**分岔点**：读数决定是走"前移初始化"还是走"并行解包"。
