# 361 · DSH 核心同步评估：最新可运行版本仍是 rc.5（0.2.2 被 Node 引擎卡住）

> 日期：2026-11-05 ｜ 触发：用户要求「同步最新的 DSH 核心」

---

## 0. 结论

**无法同步到 `0.2.2-rc.1`**：它的 `engines.node` 要求 **>= 24.9.0**，而 DSHM 宿主内嵌的
`libnode.so.137` 是 **v24.2.0**（`host-ready.json` 的 `runtime.nodeVersion` 实测）。
上游 `latest` 通道仍是 **0.2.1-rc.5** —— 也就是我们当前的基线，**已经是最新可运行版本**。

本轮因此没有"换基线"，而是把 rc.5 基线**重打了一遍**（`+dshm.111`），把本仓的端侧补丁
与本轮修复全部带进容器（sha256 `ab76a5ac…`）。

## 2. 为什么引擎不满足就不能硬升

1. **不是"警告而已"**：`engines` 在 npm 安装时默认只告警，但运行时若用了 24.9+ 才有的 API
   （Node 24.x 的 minor 版本会带 V8/内置模块行为变化），失败会出现在**运行期**而不是安装期 ——
   表现为宿主启动即崩、或某些插件加载时抛 `TypeError`，比安装失败更难定位。
2. 我们的宿主是 **libnode 静态嵌入**（`libdshhost.so` 链 `libnode.so.137`），
   升级 Node 不是 `npm i`，而是**换一份 OpenHarmony 的 libnode 构建**：仓库里没有该产物，
   需要上游/移植方提供 arm64 OHOS musl 版，属于**运行时分发物换代**。
3. 本仓在 rc.5 上叠了 **31 个补丁函数 / 54 处 `join(STAGE, …)` 注入点**（pack-core）。
   换到 0.2.2 后这些锚点大概率要重写一轮，还要跑全量门禁与三端复测。

## 3. 三个选项（含代价）

| 选项 | 动作 | 代价/风险 | 建议 |
|---|---|---|---|
| **A. 留在 rc.5（当前）** | 已重打 `+dshm.111`，修复全部在内 | 0 | ✅ 推荐 |
| B. 先升 libnode 到 ≥24.9 | 找/构建 OHOS arm64 musl libnode（126 MB 级），替换 `hostruntime/libs/arm64-v8a/libnode.so.137`，重签，再升 0.2.2 | 运行时换代 + 31 个补丁迁移 + 三端全量回归；没有现成产物 | 需要上游能给出候选 libnode 才立项 |
| C. 只改 `engines` 绕过 | 改 package.json 骗过 npm | **不可取**：运行期缺 API 照样炸，且把问题藏到设备上 | 禁止 |

## 4. 本轮实际做了什么（"同步"的可行部分）

```text
coreVersion : 0.2.1-rc.5 → 0.2.1-rc.5+dshm.111（基线不变，补丁与修复全量重打）
容器        : dsh-core-0.2.1-rc.5+dshm.111-openharmony-arm64.zip
sha256      : ab76a5aca6d4b8c1f5a772f66a36f47186af927fe2e404309833b236ab56d0a6
体积        : 94.6 MB / 39,375 条目
```

已核验：

- 容器内 `dshm-vm-bash/lib/vm.js` 含本轮新增的 `backgroundWorkloadActive`（后台放行）；
- `check-resfile-core-zip` 通过（resfile 只有 1 份容器，与配方/本次产出一致）；
- 测试包 1010013 内 HSP 的核心容器就是这个 `.111`。

> 重打时 pack-core 报 `找不到 binary-sign-tool（或 JDK）：跳过自签名`，
> 产物仍是「47 通过 / 1 未检出」。这不影响 rc.5 的既有签名，但**如果将来要动核心树里的
> rg/git 等 ELF，得先补签名工具**，否则 exec 域仍会拒。

## 5. 真要升 0.2.2 的检查清单（等 libnode ≥24.9 到位再执行）

1. 新 libnode 先过 `tools/check-libnode-io-uring.mjs`（本项目对 io_uring 做过中性化）；
2. 改 `hostcore/core-recipe.json` 的 `coreVersion` 到 `0.2.2-rc.1+dshm.1`；
3. `node tools/pack-core.mjs --place-in-app` —— 按第一个 `die` 的锚点逐个迁移（31 个补丁函数）；
4. 全量门禁：`check-core-openharmony-patches` / `assert-core-entrypoints` / `check-plugin-toggle` /
   `check-parity` / `check-node-cli` 等；
5. 三端复测：PC（v10 五项）、手机（六目录 + guest）、平板（沉浸状态栏 + 后台）。

---

## 6. 一句话

**"最新 DSH 核心"对当前运行时来说就是 rc.5，我们已经在上面并且刚重打过；0.2.2 不是不做，
是被 libnode 24.2 < 24.9 卡在运行时分发物这一层 —— 需要先有新版 libnode，才谈得上迁移补丁。**
