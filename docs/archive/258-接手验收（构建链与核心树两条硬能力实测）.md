## 4. 路上修掉的 4 个缺陷（都是"不修就接不了手"）

### 4.1 `tools/pack-core.mjs`：npm 路径被无条件加引号 ⇒ POSIX 上恒 ENOENT

**症状**：`✗ npm install 失败（exit=null）`。手动执行**同一条** npm install 却成功
（610 包 / 53 s）。

**根因**：旧代码

```js
const npmForShell = `"${npm.replace(/"/g, '\\"')}"`;          // 无条件加引号
spawnSync(npmForShell, args, { shell: process.platform === 'win32' });
```

在 Windows 上这是对的（`shell:true` 时要防 `D:\Program Files` 被拆词）。
但在 POSIX 上 `shell:false`，spawn 去找的是一个**名字里带双引号**的可执行文件 ⇒ ENOENT、
`status` 为 **null**。报错文案只说 `exit=null`，完全看不出是引号问题。

复现与判定：

```text
spawnSync('"/…/npm"', ['--version']) → status=null  error=ENOENT
spawnSync('/…/npm',   ['--version']) → status=0
```

**修法**：引号跟着 `shell` 一起用；并把 `r.error` 一并打进报错（`exit=null` 多半不是退出码，
而是根本没起来）。

### 4.2 `tools/check-dead-handlers.mjs`：带返回类型注解的回调默认值被误判成死按钮

**症状**：`MeetingPanel.ets` 报了 4 处「调用处空实现（点了没反应）」。

**实测这 4 处全是误报**：它们是**组件回调 prop 的默认值**，父组件 `WebApp.ets`
的 `MeetingPanel({ onClose, onMinimize, onTick, onInsertTranscript })` 注入了真实现，
且子组件里确实在调 `this.onMinimize()`（:282）、`this.onTick(...)`（:940）、
`this.onClose()`（:1264/:1285）、`this.onInsertTranscript(...)`（:1315）。

**根因**：`isPropDefault()` 的正则写死了 `= () =>`（无冒号），而 ArkTS 标准写法是

```ts
onClose: () => void = (): void => {
};
```

带返回类型注解 `(): void` ⇒ 匹配不上 ⇒ 落到"调用处空实现"分支。

**修法**：参数括号与返回类型注解都放宽成可选/任意。

**负控制（必须能抓真死按钮）**：注入

```ts
buildDeadProbe() {
  this.onClose = (): void => {
  };
}
```

⇒ 门禁报 `发现 1 处空实现 … MeetingPanel.ets:129 [调用处空实现]`；还原后回到"未发现空实现"。
**误报长期挂着等于门禁失效**——真死按钮会被淹没在 4 条噪音里，这正是要修的理由。

### 4.3 `tools/check-custom-api-save.mjs`：本机 hmfs 恒 660 ⇒ 凭据插件拒载 ⇒ 门禁恒红

**症状**：`FAIL ② 写入密钥 credentials/set — credential/rejected: … readable beyond its owner (mode 660)`。

**根因**：`@deepseek-ai/dsh-credentials-local` 的 `assertOwnerOnly()` 要求凭据文件无
group/other 位（600）。但鸿蒙 `hmfs` **强制 660 且 `chmod` 无效**：

```text
chmod 600 ~/.dsh/.credentials.yaml → rc=0，stat 仍 660
node fs.chmodSync(…, 0o600)        → 存入后 stat 仍 660
/tmp（tmpfs）chmod 600             → 生效（600）
```

⇒ 不是缺 unix 权限实现，是 hmfs 策略。而**插件自带这个豁免**（源码原文：
`DSHM_CREDENTIALS_MODE_EXEMPT: hmfs 强制 660 ⇒ 该检查在鸿蒙永远不可能通过（E127）`），
只要 `DSHM_PLATFORM=ohos` 就跳过——端侧本来就走这条路。

**修法**：门禁起 Host 时声明 `DSHM_PLATFORM: 'ohos'`（与端侧同款）。修后
`✅ 通过：创建/编辑/存密钥/重启存活/删除 全链路成立`。

### 4.4 `tools/check-compat-exemption.cjs`：上游改字段名 + hmfs 660，两条判据双双失效

**症状**：`RESULT: 47 passed, 2 failed`（历史基线是 48 passed / 0 failed）。

**B2 基线红**：断言 `before.peers` 非空，而上游 `0.2.1-rc.3` 已把字段名改成
**`requirements`**：

```js
return { name, version, runtimeVersion, requirements, exempted }   // 无 peers
```

这正是该文件 :277-280 注释自己警告过的同族问题——"判据错了但看起来像在测东西"。
而且 B2 是 B8 翻转对比的**基线**：基线恒红 ⇒ 后面"翻转"失去意义。

**修法**：两种字段名都认（`requirements ?? peers`），仍要求非空。

**B6 红**：断言 `mode === 0600`，但 §4.3 已证明 hmfs 恒 660 且 chmod 无效。
**修法**：现场探测 `chmod` 是否真生效；hmfs 上按"平台不具备"**显式记名跳过**
（进 `skipNotes`，不当通过也不当失败），其它文件系统仍严格判 0600。

修后：`RESULT: 48 passed, 0 failed`——回到历史基线。

### 4.5 附带：resfile 里还是旧核心（`.95`），构建会打出旧核

发现 `recipe` 已是 `.96` 而 `hostruntime/src/main/resources/resfile/` 里还是 `.95` 时，
构建是**成功**的，只是 HSP 里带的是旧核心——"构建绿了但产物不对"。
已用 `pack-core --skip-install --place-in-app` 换新，并用 `check-resfile-core-zip` 加验。

## 5. 关于两次 sha256 不同（774eb3bb → 1c6fdd2c）

`pack-core` 跑了两遍：一次不带、一次带 `--place-in-app`。两次的 zip sha256 不同
（`774eb3bb…` vs `1c6fdd2c…`），**这是预期的**：重打包会重写 zip 时间戳等元数据。
`check-resfile-core-zip` 的判据是"resfile 那份 == dist 那份 == 配方声明那份"，
换新后三者一致即通过（实测 99,355,896 B / `1c6fdd2c…`）。
⇒ **不要把 zip 的 sha256 当"内容是否一致"的判据**，除非是同一次产出。

### 6.3 接手时要知道的 3 件事

1. **`DSHM_PLATFORM=ohos`**：任何在本机起真实 Host 的场合都要带（凭据 660 豁免）。
   已固化进 `check-custom-api-save.mjs`；以后新写同类脚本照抄。
2. **核心树改动必须走 `--place-in-app`**：否则 `dist/core` 更新了、HSP 里还是旧的，
   而构建**照样成功**（这是最安静的一类失败）。出包后跑 `check-resfile-core-zip`。
3. **`chmod` 在仓库根（hmfs）无效**：涉及"权限位"的判据一律要探测，
   不能假定 `chmod 600` 生效。
