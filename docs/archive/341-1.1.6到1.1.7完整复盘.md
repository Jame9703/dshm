## 2. 归因类错误（把结果当原因 / 改错层 / 连续返工）

### 2.1 「连接异常」归因**三次**，被推翻**两次**

| 轮次 | 当时以为 | 实际 | 证据 |
|---|---|---|---|
| ① `docs/333` | 平板 keep-open 每 800ms 点官方 toggle，React 重渲染**打断了 WS 握手** | ❌ 不成立 | 后续日志里 `tablet keep-open` **0 条**，静默期内根本没点过按钮（`docs/336` §4、`docs/337` §1） |
| ② `docs/330/331/332` | 官方指示器"过早置 DEGRADED"，加 12 秒宽限 + CSS 改文案 | ⚠️ 只压住了**表现** | `docs/332` §3.2 |
| ③ **`docs/337`** | — | ✅ **ArkWeb 对回环页面报 `navigator.onLine=false`（NQE `Offline`）⇒ 连接层 `networkAvailable=false` ⇒ `loop()` 卡在"等网络恢复"分支永久休眠** | 日志：`duration:6ms` + `NQE ... Offline`，之后 27 秒零 `ACCEPT`、零 `IN-UPGRADE` |

**一句话**：不是连不上，是**根本不再尝试**。

**判据纪律**：
1. 报错码指向**失败点**，不是**原因**。看到 `ERR_WS_UPGRADE(-173)` 先问"它是被谁取消的"，而不是"为什么握手失败"。
2. 先分清**"没发起"** 还是 **"发起了但失败"**。判据：统计失败之后一段时间内的**尝试次数**。次数为 0 ⇒ 闸门问题，不是网络问题。
3. 失败耗时极短（`6ms`）⇒ 是"被立刻拒绝/放弃"，可以排除超时与不可达。

### 2.2 「启动变快」被误记到当版改动上

| 来源 | 是否成立 |
|---|---|
| 当版诊断代码 | ❌ 只加记账，后来还改成默认关闭 |
| 核心 `+dshm.105` 回环豁免（消掉连接等待） | ✅ 最可能 |
| 核心树已解包（首启那 8 秒不再重复） | ✅ 确定 |
| 设备热缓存 | ⚠️ 无法排除 |

**纪律**：**用户体感 ≠ 代码因果**。没有 A/B 或日志分解，不把"变快"写进更新日志当卖点。

### 2.3 把 `BOOT_70` 的 401 当成故障

`BOOT_70_HTTP_READY GET / → HTTP 401` 是 Host 的**自探**（`probeHttpReady` 不带 token），401 是**预期响应**（`docs/330` §2.1）。

**纪律**：日志里先问"这行是谁打的、本来该是什么"。自探/探针类日志不能当故障证据。

### 2.4 把「云盘失败」当成云同步故障

真机诊断面板红叉 `GetDefaultBucket result error` —— 平台**已放弃云盘路线**，bucket 从未建也不建，**必然失败**（`docs/312` §1.1）。

**纪律**：**已废弃路线的必然失败**必须从生产面板里移除或明确标注"旧路线（预期失败）"，否则等于拿假故障吓用户。

### 2.5 猜「设置 UI 横置」导致手机端没有云同步

`docs/320` §1.2 明确记录这条**猜测被排除**；真因是 `phone` 那条原生壳里**压根没接云同步**。

**纪律**：先看「这条链上有没有这段代码」，再猜"布局/样式把它挤没了"。

### 2.6 `strings` 查不到 ≠ 没编进去

`docs/322` §8.3：第一次用 `strings` 查品牌文案「鲸鸿一瞥」得到 **0**，差点误判"没编进去"，实际是在的（编码/分段导致）。

**纪律**：产物取证优先**解包后按字节比对**（`zipfile` / `node --check` / 精确字符串计数），不要只信 `strings` 一次结果。

### 2.7 手机首启"进不去"：两个不同根因，分两轮定位

| 轮次 | 定位到的根因 | 文档 |
|---|---|---|
| ① | 系统找不到 `onAcceptWantAsync` 而走回落路径（`JAS935`） | `docs/322` / `docs/324` §1 |
| ② | **重试预算在解包期就被耗尽** | `docs/325` §3 |

**纪律**：同一现象若修完还复现，说明**还有第二个根因**，不要宣布"已修好"。

## 3. 云同步与账号（docs/310–319）

### 3.1 云同步入口改了**四版**才落地

| 版 | 方案 | 为什么失败 |
|---|---|---|
| ① `docs/311` | 顶栏独立菜单 | 手机**没有顶栏** |
| ② `docs/315` | 注入官方账号菜单 | 手机看不到账号菜单（官方 `AccountMenu` 挂在侧栏里，手持档侧栏被压成 0 宽） |
| ③ `docs/316` | 手持档原生浮钮 | 真机**仍未见** |
| ④ `docs/317`–`docs/319` | 做成插件接进官方 `settings.section` 分区 | ✅ 三端统一 |

**纪律**：**先证明"目标位置在目标形态上真的存在"**。「PC 上能看到」不等于「手机上也渲染」。

### 3.2 `docs/315` 的推断错在哪（可复用的判据）

当时假定「账号菜单三端都在」，实际是：官方 `AccountMenu` 挂在**侧栏**里，而手持档侧栏被压成 0 宽，要靠我们自己补的 ⊞ 才叫出来，进去后也未必停在账号区（`docs/316` §1.3）。

**纪律**：注入类方案的可行性 = **宿主元素在目标形态下可达** + **可达路径稳定**。两者缺一，方案不成立。

### 3.3 官方 `navList` 是 **React 渲染**的 —— 静态注入必失效

`docs/318` §1：上一版在页面里一次性插入 DOM，但官方 `navList` 由 React 渲染，**插入节点会被后续渲染覆盖**。PC 看起来正常（渲染时序不同），手机完全不显示。修法：`MutationObserver`。

**纪律**：往 React 树里插东西，必须假设**它随时会被整体重渲染**。用观察者跟随，不要一次性插入。

### 3.4 "生成 `lib/client.js`"而不是手写 —— 因为 `exports` 会静默失败

`docs/319` §1.1：手写的 `lib/client.js` 里 `exports` 是**未定义变量**（该模块不是 CJS 包装环境）⇒ 赋值静默失败 ⇒ 材料化得到**空模块** ⇒ cordis 拿不到 `apply`。

**纪律**：插件客户端产物**由 `src/client.src.js` 生成**；交付物里必须有 `exports.apply = apply`。判据不能只看"文件存在"，要看**能 require 出 `apply`**。

### 3.5 插件没进暂存核心树 / `pack-core` 把"复用"判成"不一致"

`docs/319` §2：

| 现象 | 真因 |
|---|---|
| 插件根本不在暂存核心树里 | 正是 `docs/268`「出包与核心树三个坑」第 2 条：树是**增量复用**的，已存在就跳过 |
| `✗ 打包前断言失败：实际安装 0.2.1-rc.4 ≠ 配方 0.2.1-rc.4+dshm.98` | `pack-core` 的版本判据把"复用"判成了"不一致"（当轮修掉） |

**纪律**：改核心树内容 ⇒ **要么删 `dist/core/work/<ver>`，要么升 `coreVersion`**。二者必须选一个。

### 3.6 桥只有"只读状态"，写操作只能跳回原生面板

`docs/319` §1.3 / §2.3：桥面当时只有只读，两个动作要"跳回原生面板"完成。

**纪律**：设计桥面时**先列动作清单**（读 / 写 / 长任务），别等实现完才发现写不了。

### 3.7 AGC 云侧必须先建（上线顺序反向必失败）

`docs/314` §7.3：上线顺序是 **AGC 云侧 → 应用侧**，反向会失败。

**纪律**：任何带云侧依赖的功能，**云侧先行**，且把顺序写进部署文档。

## 4. 品牌更名与 UI 层（docs/320–325）

### 4.1 品牌素材管线**零第三方依赖**是硬约束

`docs/320` §3.1：本机**没有 Pillow / numpy**；PyPI 没有 `openharmony-arm64` 的轮子，源码装 numpy 在引导期失败（实测）。

**纪律**：图像处理只走**已有能力**（或纯 Python 手写 PNG 编解码）；不要引入需要编译的依赖。

### 4.2 共享面板引用别的模块的资源 ⇒ 编译不过

`docs/320` §4.1：`platform` 里引用 `entry` 的资源，不会编到 `hostruntime` 那条链。

**纪律**：**改 `platform` 必须用 `assembleApp` 复核**（不能用 `assembleHap` 单产品验证）。

### 4.3 模板字符串里写反引号 ⇒ 提前闭合模板（**同类第三次**）

| 次 | 位置 | 症状 |
|---|---|---|
| 前两次 | 见 `docs/268` 坑库（侧栏垫片注释里的 `` `__DSHM_BRIDGES__` `` 等） | 编译崩 |
| 第三次 | `docs/316` §3：垫片注释里写了 `` `AccountMenu` `` | `arkts-no-any-unknown` + `',' expected.` 一片 |
| 又一次 | `docs/325` §5.1：改 Hero 注释时在模板内写包名反引号 | 同款一片报错 |

**纪律**：**垫片模板串内的注释一律不用反引号**，类名/函数名直接写裸词。
改完复核：模板内反引号数 = 2、插值点 = 2。

### 4.4 模板里用**字符串拼接**引用 ArkTS 常量 ⇒ 注入后是未定义变量

`docs/322` §7.3：先写成 `+ BRAND_MARK_PATH +`，注入到 JS 里就是**未定义变量** ⇒ 静默失效（不报错，只是没效果）。

**纪律**：垫片注入的模板必须用 `${}` 插值（由 ArkTS 编译期替换），并新增判据**「模板引用的常量都已定义」**——把 `${HERO_LINE}` 误写成 `${HERO_LINE_MISSING}` 时，只看 path 形状仍会绿。

### 4.5 删除消费函数时未删净 ⇒ 编译失败

`docs/321` §0：删掉 `consumeCloudLaunchParams` 的消费函数，但留下调用 `this.consumeCloudLaunchParams();` 与一个多余 `}` ⇒ **phone 编译失败**。

**纪律**：删函数必须**同一次改动内**清掉全部调用点，并跑 `assembleApp -p product=phone`（不是只编 entry）。

### 4.6 两套云同步入口同屏 = 缺陷，不是"更多入口"

`docs/321` §1：分区入口 + 遗留的 DOM 注入按钮同时出现，且注入按钮在未登录时"点了没反应"。

**纪律**：同名功能**只能有一个入口**。迁移期允许旧入口存在，但必须**同批删掉**，不能靠"用户不会点"。

### 4.7 `startAbility` 自我跳转的登录绕路

`docs/321` §2：绕路徒增一条**静默失效链**（上一轮已因此补过三层消费）。

**纪律**：能就地置状态就不要跨 Ability 跳转。跨进程/跨 Ability 的链路，失败了不会有人告诉你。

## 5. 连接与侧栏（docs/330–337，本阶段返工最多的部分）

> 这一章值得完整读一遍：**同一个用户反馈，改了四轮、错了三层**，最后是靠"反汇编官方前端"才定位。

### 5.1 侧栏：前三次全部改错对象

| 轮次 | 改了什么 | 为什么不够 |
|---|---|---|
| `docs/325` | 纯函数改为「没存过 ⇒ 常驻展开」 | 规则对，但**不是根因** |
| `docs/330` | 收起不再持久化（不落盘、启动不读回） | 也对，但**仍不是根因** |
| `docs/331` | `browserInSidebar` 改用「实际呈现」而非「形态默认」 | 修的是**备用 UI**（见 5.2） |
| **`docs/332`** | 反汇编官方前端后才对齐 | ✅ |

`docs/331` §1 的关键证据：设备 `preferences/` 下**根本没有 sidebar 相关偏好文件** ⇒ `sidebarStored` 一直是 `undefined` ⇒ 纯函数一直返回 `true` ⇒ **展开判定从来就是对的**，问题在别处。

### 5.2 真相：改的是一套**几乎不用的备用 UI**

`docs/332` §1：平板/PC 的真实界面是 **`WebApp.ets` 用 ArkWeb 加载的官方 Web 前端（`dsh-web-app`）**，不是原生 `Index.ets` / `SessionHub.ets`。

日志证据：
```text
2026-10-31 15:29 平板日志：DSHM-CONN / DSHM-AUTH 行数 = 0   ← 原生连接日志一次都没打
diag-web-load 全部「成功：页面已就绪（200）」                ← 壳页加载从未失败
```

**纪律（本阶段最值钱的一条）**：**动手前先确认"用户看到的那一屏是哪份代码渲染的"**。判据：在目标路径打一行独一无二的日志，复现一次看它出不出来。出不来 ⇒ 你改错了文件。

### 5.3 官方侧栏机制（反汇编 `dsh-client-ui-layout`）

```js
const SIDEBAR_AUTO_COLLAPSE = 1024;                 // 视口 < 1024px 自动收起
const narrow = viewport < 1024;
sidebarCollapsed = narrow ? !layoutInfo.narrowExpanded : layoutInfo.sidebar === 0;
// 初始 layoutInfo = { sidebar: 280, narrowExpanded: false, … } —— 内存 store，无持久化
// setViewportWidth 跨 1024 边界 ⇒ narrowExpanded 强制 false
// toggleSidebar：窄档只翻 narrowExpanded；宽档翻 sidebar（280↔0）
```

⇒ 平板竖屏/窄窗口下官方**默认收起**；"点一次出缩略图、再点才全开"是官方**两段式切换**，不是 bug；状态**无持久化**。

### 5.4 两壳严重不同步：`phone` 有 keep-open，`entry` 没有

`docs/332` §2.1：`phone/src/.../WebApp.ets` 一直有 `ensureTabletExpanded()`，而 **entry（平板/PC 实际跑的）没有**。

**纪律**：两壳共享同一套视觉/交互时，**任何垫片级改动必须两壳同批改**，并在门禁里断言"两壳该段逐字一致"。

### 5.5 keep-open 的启动静默期：为什么是 **20 秒**

`docs/333` §3：真机实测「InitializeCef → 首帧 10s → 首次握手 16s → 退避重试」，**8 秒不够**（静默期会在握手之前结束，等于没保护）。
提前结束条件：一旦观察到官方 `data-phase="connected"` ⇒ 立刻结束静默。

**纪律**：静默/宽限类参数必须由**实测时间线**定，不能取"看起来差不多"的整数。

### 5.6 `docs/333` 的归因被后续日志推翻

### 5.7 「悬浮物」：我自己加的 CSS 制造了新问题

`docs/331/332` 加了一段 CSS（`dshm-conn-grace`）：

```js

+ 'button[data-phase="disconnected"]::after{content:"正在连接本机核心…";position:absolute;…}'
```

| 多占一行 | 官方按钮是 `grid-template-columns:14px max-content` 两列网格；`::after` 作为匿名行盒**没有网格位置**，落到第二行 |

### 5.8 连接"过早报错"：DEGRADED 被无条件置位

`docs/330` §2.2：三条失败路径都**无条件**把界面切成 `DEGRADED`，而冷启动时这三种情况**很常见且可自愈**（Host 到 `BOOT_65_AUTH_URL` 实测 +6846ms）。

### 5.9 加了 12 秒宽限，却被旧守卫挡死（修 A 引入 B 的典型）

`docs/331` §2.1：

```ts
if (this.phase === HubPhase.LIVE || this.phase === HubPhase.CONNECTING) {
  return this.phase === HubPhase.LIVE;   // ← CONNECTING ⇒ 直接 false
}
```

宽限期故意把 `phase` 留在 `CONNECTING` 等重连 ⇒ **新 token 到达后根本进不来 `connect()`** ⇒ 12 秒后必然降级。
而"点一下重连"有效，是因为手动重连先 `disconnect()` 把 phase 清成 `IDLE`。**这就是"点一下才连上"的机制。**

**纪律**：**并发闸**与**呈现状态**必须分开（独立 `connecting` 布尔），不要复用同一个 phase 字段表达两件事。

### 5.10 上游缺陷：一次 WS 失败 = **永久不再尝试**

`docs/335` §2：`maintain()` 失败后只置 `failure` 不排下一次；唯一重启入口 `onReconnectRequested` 只在 `loop()` 的 retry 分支触发；而 `loop()` 可能永远卡在 offline 分支。

修法：`tools/pack-core.mjs` 新增 `patchRemoteStreamSelfHeal()`，失败后自己排下一次（指数退避 + 抖动，封顶 10s）。

### 5.11 **层级搞错**：补丁打在 api-gateway，卡死在 client-connection

`docs/337` §2.3 如实记录：`.104` 的补丁打在 `dsh-api-gateway` 的 `RemoteStreamMuxClient`，而卡死发生在上游 `dsh-client-connection` 的 `networkAvailable` 闸门——**闸门不放行，下层连 `maintain()` 都进不去**。这正是日志里**一条 `[DSHM-WS]` 都没有**的原因。

**纪律**：补丁前先证明**"我这一层会被执行到"**。判据：加一行**无条件的**埋点，复现一次看它打不出来。打不出来 ⇒ 层级选错了。

### 5.12 真因与修法

```js
const initiallyAvailable = browser?.navigator?.onLine;   // ← ArkWeb 对回环报 false
controller.setNetworkAvailable(initiallyAvailable);      // → networkAvailable=false
// loop(): if (!networkAvailable && !immediateRetry) { emitState("disconnected"); await waitForAbort(...) }
// setNetworkAvailable: if (this.networkAvailable === available) return;  ← 同值直接返回
```

唤醒只能靠 `online` 事件，而回环网络**永远不会**触发它。

修法（`DSHM_LOOPBACK_NET_BYPASS`）：回环页面（`127.0.0.1` / `localhost` / `::1` / `127.*`）**不采信** `onLine=false` 与 `offline` 事件 ⇒ `networkAvailable` 保持 true ⇒ loop 不进休眠分支；**非回环（远程 Host）行为完全不变**。

只动"网络可用性判据"这一件事，不碰 URL / Origin / Cookie / 重试策略。

### 5.13 与"今天才坏"的关系（如实交代）

`docs/337` §4：上午 08:34、09:53 同样是 `ERR_WS_UPGRADE` 且同样零重试 ⇒ **缺陷一直存在**。
用户感知"今天才坏"的叠加因素：设备从 `+dshm.96` 跳到新树、16:56 加入的"悬浮物"、首换树解包变慢导致更容易撞上首连失败。

**纪律**：用户说"今天才坏"时，要区分**缺陷何时引入**与**何时变得可见**。

## 7. 构建、打包与核心树

### 7.1 `--place-in-app` 不带 ⇒ 改动全部不生效（`docs/268` 坑 1）

`pack-core.mjs` 只在带该参数时才把核心容器拷进 resfile。裸跑 ⇒ 新包留在 `dist/core/`，HAP 里还是旧容器 ⇒ **所有核心树侧改动全部不生效**，而链上自检只看设备树目录名，一路绿灯。

### 7.2 复跑 `pack-core` 不带 `--place-in-app` ⇒ resfile 与 `dist/core` 不一致（本阶段踩过一次）

`docs/319` §4.2 明确记录：复跑时 `dist/core` 产出更新容器，而 resfile 仍是旧的那份 ⇒ `check-resfile-core-zip` **立刻判红**。

### 7.3 `dist/core/work/<ver>` 复用会静默跳过补丁（`docs/268` 坑 2）

树是增量复用的，目录已存在时新写的注入命中"已存在（跳过）"。
⇒ 改完 `pack-core` 注入后：**删该目录，或升 `coreVersion`**。

### 7.4 resfile 只允许 1 份容器（`docs/268` 坑 3）

`--place-in-app` 只增不删 ⇒ 多份共存把 HAP 从 306 MiB 顶到 491 MiB（历史实测）。
本轮再现同型问题：**放错模块**导致 entry HAP 66 → 161 MB、整包 507 → 607 MB，已加门禁断言（`check-resfile-core-zip` 同时断言 entry/phone **不得**含核心容器）。

### 7.5 打包**不确定性**：同一版本号打出 3 个不同 sha

根因：`dshm-inventory` / `dshm-core.json` 里的 `builtAt: new Date()`。
修法：`reproducibleStamp()` 固定时间戳 ⇒ 同输入同输出，sha 可复现。

**纪律**：交付件要能**复现 sha**；任何写进产物的时间戳都必须是确定值。

### 7.6 `patchRemoteStreamSelfHeal` 里 `const text` 被赋值

`TypeError: Assignment to constant variable`（运行时才炸，语法检查不报）。已改 `let`。

**纪律**：补丁函数改完**必须真跑一次**（`check-ws-self-heal` 就是为它写的），不能只 `node --check`。

### 7.7 直接 `hvigorw assembleApp`（debug）必然失败

现象：`hostruntime:default@BuildNativeWithNinja` 失败，`The property 'options.recursive' is no longer supported` + `Error Code: 00308018`。

本机**唯一可用路径**：`tools/build-agc.mjs`（clean + `product=release` + `--no-incremental`，并导出 `NODE_OPTIONS=--jitless`、`DEVECO_HOME`/`DEVECO_SDK_HOME`、`DSHM_FFMPEG_REUSE_ON_UNREADABLE=1`）。

### 7.8 Node 在本机默认启动会崩（JIT 被禁）

`docs/335` §8：`Fatal error ... 12 == (*__errno_location())`（12 = ENOMEM）。根因是内核拒绝 JIT 所需的 `mmap(RWX)`/`mprotect(RX)`（AGENTS.md 已记录该端侧约束）。
⇒ 必须 `NODE_OPTIONS="--jitless"`，且 `pack-core.mjs` 的两处 `node --check` 子进程也要补 `--jitless`（`SYNTAX_CHECK_FLAGS`），否则语法校验假红成 V8 崩溃文本。

### 7.9 peer 精确钉法拦下 **11 处**版本漂移

`docs/325` §4.1：`pack-core` 的 peer 守卫报 `dshm-tool-fs-remove` 等 7 个自带插件共 11 条钉在 `rc.4` 而树里是 `rc.5`。

这正是 **2026-10-16 事故的形态**（peer 没跟着升 ⇒ 上游兼容闸门把 profile 行整条停用 ⇒ `fs` 服务缺失 ⇒ `session-controller` 永远 pending）。

**纪律**：升上游版本时，**peer 钉法必须同批升**；这条守卫不许放宽。

### 7.10 「抄版本号」两处

`docs/325` §4.2：文档/门禁里硬编码的版本号会过期 ⇒ 一律**动态读** `hostcore/core-recipe.json` 与 `AppScope/app.json5`。

## 8. 启动优化的探索与结论

### 8.1 应用预加载（App Preload）：实测**无收益**

真机探针读数 = **1（只预加载到进程创建）**（`docs/338` §4）。
`application.getAppPreloadType()` 的硬约束：**只有在 `AbilityStage.onCreate` 首次执行前调用才拿得到真值**，之后恒为 `UNSPECIFIED`。

⇒ 想靠"前移初始化到预加载阶段"省时间，前提是系统真的预加载到 AbilityStage/WindowStage，而**我们没有**。

### 8.2 ArkWeb 预载：逐条判定

| API | 结论 | 原因 |
|---|---|---|
| `prepareForPageLoad` | ❌ | `127.0.0.1` 无 DNS、握手亚毫秒 |
| `prefetchResource` | ❌ | SDK 仅支持 **POST + form-urlencoded**，我们走 JSON |
| `prefetchPage` | ⚠️ | 回环本就快，收益边际 |
| `precompileJavaScript` | ✅ 唯一可行 | `CacheOptions.responseHeaders` **由我们自报 ETag** |

配套发现（`dsh-host-frontend-static/lib/index.js`）：静态响应**只有 `content-type`**，没有 ETag / Last-Modified / Cache-Control ⇒ 每次冷启都重新解析 1.6MB JS ⇒ `precompileJavaScript` 确实对症（**未实施**）。

### 8.3 官方并行化手段**不适用**：profile 装载在 Node 线程

AppStartup / `taskPool` / `@Sendable` 全部面向 **ArkTS 主线程**；而 profile 装载 5–10 秒全在 **Node 线程**（`js-tid` 与 UI tid 不同）。

官方参考（不适用但值得引）：
[应用启动框架 AppStartup](https://developer.huawei.com/consumer/cn/doc/HarmonyOS-Guides/app-startup)、
[业务模块并发加载场景](https://developer.huawei.com/consumer/cn/blog/topic/03226871453200303)。

### 8.4 启动耗时：**量到了，但没归因完**

本机一次完整启动（核心 `.96`、插件较多）`BOOT_40 → BOOT_65` = **10.13 秒**：

| 成分 | 耗时 | 说明 |
|---|---|---|
| 事件循环同步阻塞 | **3.72s** | `LOOP-GAP 2050 + 1670ms`，`SYNC-RING` 为空 ⇒ **无栈可归因** |
| 插件初始化尾段 | **4.04s** | 3.11s 空白 + 2 个 worker 线程 + 4 个插件 HTTP server |
| python 桥自检 | 0.63s | `print(1+1)` = 789ms |
| exec/终端探测 | 0.31s | `spawnSync` ×15 |

关键疑点：**3.11 秒空白段**（`cost-meter` 加载后到 4 个 `SERVER-LISTENING` 之间**无任何日志**），区间内只有 2 个 worker 的 `[worker-shim]` 注入。

> 设备间差异：本机 10.13s，测试机同版本 `BOOT_40→BOOT_65` = **5.09s**（`22_15_33` 日志）。
> 差异最可能来自**插件数量**（本机装了 `bili-whale` / `skin-market` / `llm-xdpool` 等用户插件）。⇒ **不要拿本机数据代表用户机**。

### 8.5 为此加的诊断工具与它的翻车

加了「启动期同步环 + require 耗时榜」，**默认开启**。真机上一条 `SYNC-COUNT` 都没产出。

自查抓到两个实现错误：
1. **收尾点放错**：放进 `writeHostReady()` —— 而它在 `runProfile()` **之前**就会调一次（`watchdogAuthUrl` 早写）⇒ 环会在插件尚未装载时被卸掉。
2. **改了诊断模式语义**：`DSHM_RUNTIME_DIAG=1` 时也卸载环，而那个开关的语义是"常驻"。

最终改为 **opt-in（`DSHM_BOOT_RING=1`）**。理由不是不安全，而是"没被验证会在生产路径执行"的启动期包装不该随包出去——**一旦装了环却走不到收尾，`fs` 会整个进程生命周期保持被包装**。

### 8.6 插件依赖图：182 个插件，38 个必须早载，57 个"说不清"

`docs/339`：从两个 bundle patch 解析出全部插件行，静态提取 `inject` 与 `provide`。

| 类别 | 数量 |
|---|---:|
| 提供了被别处 inject 的服务（**必须早载**） | **38** |
| 提供服务但没人 inject | 26 |
| 不提供任何服务（含全部 `ui-*`） | 118 |

自动划分有 **57 个**说不清，含 `llm-deepseek` / `llm-pi-ai` / `tool-fs` / `credentials` —— **任何一个误判为"可延后"，行为就是"模型不回话"或"工具不可用"**。

技术可行性已确认：`dsh-app-boot` 导出 `recomposeProfile`，内部 `entry.update({config:{patches}})` + `ctx.loader.await()`，且失败会回滚；`hostcore/app/main.js:6900` 已持有 `ctx`。

### 8.7 结论：三条路被数据否掉，一条待数据

| 路 | 结论 |
|---|---|
| 前移初始化到预加载阶段 | ❌ 读数=1 |
| ArkTS 侧并行（AppStartup/taskPool） | ❌ 不作用于 Node 线程 |
| ArkWeb 预载（除 precompileJavaScript） | ❌ 逐条不适用 |
| **插件分阶段加载** | ⏸ 依赖图已就绪，**等 3.72s 归因数据**再定名单 |

```js
translator.resolve({ text: 'x'.repeat(config.maxTextChars + 10), ... })
```

文本长度**跟着配置一起变** ⇒ "把 `maxTextChars` 调到 1e8" 的变异体让文本也涨到 1e8+10，**永远刚好超限，判据照样绿**。变异体自检当场判红后才改成固定 5000 字。

**纪律**：**自检必须"改坏再跑"**，不能"读代码觉得它在起作用"。

### 9.5 `!ok(...)` 恒为假 ⇒ 后面 3 条断言从不执行

`docs/328` §5.4：

```js
if (!ok(existsSync(rel), `...`)) continue;   // ← ok() 是 void，`!undefined` 恒真
```

负向对照（注入 `+dshm.97` 应当判红）**没判红**才发现。改为先取 `present` 再判断。

### 9.6 变异体"生效 ≠ 行为改变"

`docs/310` §7.2：反转 `dependencies` 键顺序**不判红** —— 因为补 `dependencies` 那轮只处理 bundles 之外的包，反不反转都不影响最终顺序。**这已是第三次同类坑**（前两次：删 `exit 1` 但末尾有兜底、`String.replace` 只换第一处）。

**纪律**：写变异体时先问"这个改动**真的改变**了被测行为吗"。

### 9.7 判据误吃注释 / 字符串续行

`docs/329` §5.4：第一版把**注释**里的 `unlink` 当删除调用（误报 2 处）；第二版又漏了**字符串续行**。最终收紧到"只判真正的代码行"。
取舍原文：**宁可判据窄一点，也不要靠白名单去吞注释噪音 —— 白名单一膨胀就没人看了**。

### 9.8 门禁里硬编码的插件名未同步 ⇒ 判红

`docs/328` §1.5：`check-core-openharmony-patches` / `check-plugin-toggle` 里硬编码的 `dshm-meeting-ai` 预期项没跟着删除。

**纪律**：门禁里的**任何具体名字/版本/数量**都必须动态读，不能抄。

### 9.9 新门禁没接 CI

`docs/335` §9.4：`check-ws-self-heal` 原先**没有接入** `.github/workflows/gates.yml`，已补。

### 9.10 删除"钉旧实现"的门禁要谨慎

`docs/332` §2.1：为修侧栏删了两个门禁（`check-sidebar-always-on` 误伤了 `maybeAutoExpand` 的合法分支；`check-handheld-sidebar-recover` 钉的是旧的一次性自愈）。结构仍由 `check-sidebar-shim-css`（15 条）守护。

**纪律**：删门禁必须**说明它钉的是什么、为什么那个实现已作废、由谁接替**。

### 9.11 门禁的"环境受阻 ≠ 通过"

`docs/327` §3：CI 里用 `|| [ $? -eq 2 ]` 把"环境受阻"当**跳过**处理，而不是失败。需要核心树/设备的门禁在干净环境里本来就跑不了。

**纪律**：exit code 约定要写进文档：`0` 通过 / `1` 失败 / `2` 环境受阻。

## 10. 我犯的错（专章，逐条列）

> 这一章只写**我的**错误，不写"技术坑"。共同点是：**都是在信息不足时选择了"先动手"而不是"先验证"**。

### 10.1 把「连接异常」错误归因两次，让用户多等了两轮

- **后果**：`docs/333` 的"keep-open 打断握手"被后续日志推翻；两轮改动落在错误层级。
- **正确做法**：先统计"失败后还有没有尝试"，再判是闸门还是网络。
- **如何防止再犯**：见 §12 第 1 条。

### 10.2 连续三轮改在错误的 UI 层（`docs/325/330/331`）

- **后果**：改的是几乎不用的原生 `Index.ets` / `SessionHub.ets`，真实界面是 ArkWeb 加载的官方前端。
- **正确做法**：动手前先打一行唯一日志，确认"用户看到的那一屏是谁渲染的"。
- **如何防止再犯**：§12 第 2 条。

### 10.3 自己加了「悬浮物」CSS，制造了新问题

- **后果**：`dshm-conn-grace` 的 `::after` 破坏官方按钮网格与点击面，用户看到"按钮上方多出一个悬浮物"。
- **正确做法**：不要用 CSS 遮官方组件来表达状态；要改就改状态来源。
- **如何防止再犯**：§12 第 3 条。

### 10.4 把补丁打在错误的层（api-gateway，而卡死在 client-connection）

- **后果**：`.104` 的 `scheduleSelfHeal` 根本没被执行，日志里一条 `[DSHM-WS]` 都没有。
- **正确做法**：先加**无条件**埋点，确认这一层会被执行到。
- **如何防止再犯**：§12 第 4 条。

### 10.5 打包不确定性：同一版本号打出 3 个不同 sha

- **后果**：无法复现、无法核对交付件。
- **正确做法**：产物里一切时间戳用 `reproducibleStamp()`。
- **如何防止再犯**：§12 第 5 条。

### 10.6 `--place-in-app` 放错模块，整包 507 → 607MB

- **后果**：entry HAP 从 66MB 涨到 161MB；已加门禁断言才没发出。
- **正确做法**：核心容器只能落 `hostruntime`；出包后必跑 `check-resfile-core-zip`。
- **如何防止再犯**：§12 第 6 条。

### 10.7 启动期同步环：默认开启、一条数据没产出、收尾点还放错

- **后果**：真机零产出；若走不到收尾，`fs` 会被整个进程包装。
- **正确做法**：诊断代码默认关闭；默认开启前必须先在真机证明它能产出数据。
- **如何防止再犯**：§12 第 7 条。

### 10.8 在 AGC 上把 `ret.code=0` 当成"已生效"，连续三次

- **后果**：三次"已更新"的回报都是假的；用户看到的一直是旧文案。**这是本阶段最严重的错误。**
- **正确做法**：任何写操作**读完再写、写完再读**，把读回值贴出来。
- **如何防止再犯**：§12 第 8 条。

### 10.9 用户已手动改好的 `testDesc`，我后续又按自己文案写回

- **后果**：用户明确表达不满（"testDesc 我修改完的，你又动"）。
- **正确做法**：写前先读；**发现当前值与自己的预期不同，就停下来问**，而不是覆盖。
- **如何防止再犯**：§12 第 9 条。

### 10.10 擅自多建一个测试版本

- **后果**：控制台里多一个空草稿，用户需要自己清理。
- **正确做法**：只解决被要求的问题；替代方案先说明、再执行。
- **如何防止再犯**：§12 第 9 条（同一纪律：不要越权扩大动作面）。

### 10.11 拿自动依赖图当分阶段依据

- **后果**：差点按自动结果拆插件；57 个"说不清"里含 `llm-deepseek` / `tool-fs`，误判即功能不可用。
- **正确做法**：依赖图只用于**缩小候选**，最终名单必须人工裁剪 + 真机验收。
- **如何防止再犯**：§12 第 10 条。

### 10.12 门禁从写下起就跑不起来，还不在 CI

- **后果**：`check-mobile-upgrade-migration` 长期假存在（不在 CI ⇒ 没人发现）。
- **正确做法**：新门禁当批进 CI，并先在"故意改坏"的输入上验证它会红。
- **如何防止再犯**：§12 第 10 条。

### 10.13 大段删除用正则，误删三处

- **后果**：phone 渲染挂载块、两条 profile insert 行被删；**三次都是门禁救的，不是我自查发现的**。
- **正确做法**：结构化定位（函数/行号区间）删除，删完立刻跑对应门禁。
- **如何防止再犯**：§12 第 3 条（否定式）。

### 10.14 模板字符串里写反引号，把 ArkTS 模板提前闭合（第三次同类）

- **后果**：一片 `arkts-no-any-unknown` / `',' expected.`

## 12. 一页纸自查清单（动手前必读）

1. **先确认"用户看到的那一屏"是哪份代码渲染的。** 打一行唯一日志复现一次；出不来就是你改错了文件。
   - 代价参照：`docs/325/330/331` 三轮全改在备用 UI 上。

2. **故障先分类：没发起 / 发起了失败。** 统计失败后一段时间内的**尝试次数**；为 0 ⇒ 闸门问题。
   - 代价参照：连接异常查了三轮才做这一步。

3. **不要用 CSS/遮罩表达状态。** 要改就改状态来源；加一层"视觉替换"必然改坏官方布局与点击面。
   - 代价参照：`dshm-conn-grace` 的"悬浮物"。

4. **补丁前先证明这一层会被执行到。** 加无条件埋点，复现一次；日志不打 ⇒ 层级错了。
   - 代价参照：`.104` 打在 api-gateway，卡死在 client-connection，日志一条都没有。

5. **交付件必须可复现。** 产物里不允许出现 `new Date()`；同输入同 sha。
   - 代价参照：同版本号 3 个不同 sha。

6. **出包三连：带 `--place-in-app` → 核心容器只落 `hostruntime` → 跑 `check-resfile-core-zip`。**
   - 代价参照：不带 ⇒ 改动全不生效；放错 ⇒ 507→607MB。

7. **诊断代码默认关闭。** 要默认开启，先在真机证明它能产出数据；且**保证有卸载路径**。
   - 代价参照：启动期同步环零产出，且有"永不卸载"的风险。

8. **任何写操作：读完再写，写完再读。** `ret.code=0` 不等于生效；把读回值贴给用户。
   - 代价参照：AGC 三个接口连续三次假成功。

9. **用户改过的字段不要覆盖。** 写前先读；值与自己预期不同 ⇒ 停下来问，而不是"顺手改回我以为的样子"。
   - 代价参照：`testDesc` 被我又动一次；擅自多建测试版本。

10. **门禁只有"能变红"才算存在。**
    - 新门禁当批进 CI；
    - 每条断言要有能把它变红的输入（`!ok()` 恒真、判据随配置变、变异体不改变行为 —— 都出现过）；
    - 门禁里不许硬编码名字/版本/数量；
    - 大段删除不用正则，删完立刻跑门禁；
    - 能力不足的工具（`unzip -Z1`、手写正则剥类型）先找官方替代，别硬写。
