## 1. 手机端为什么没有「云同步」——日志先定性，再判断"横置"这个猜测

### 1.1 日志读数（`~/Download/com.huawei.hmos.browser/2026-10-30 22_36_29.log`）

| 读数 | 值 |
|---|---|
| 手机侧 Host 核心树 | `/data/storage/el2/base/haps/**entry**/files/dsh/cores/**0.2.1-rc.4+dshm.97**/…` |
| `dshm-cloud-sync` / `settings.section` / `云同步` 命中 | **0** |
| `cloudSync*` 命中 | 61 条，**全部是系统 `cloudfileservice`**（与本应用无关） |
| 模块名 | 手机 = `phone`（`EntryAbility/com.dshm.dshclient/**phone**`），平板 = `entry` |

⇒ 手机端跑的核心树里**根本没有这个插件**（`+dshm.97` 早于插件加入；`+dshm.98` 才有）。

### 1.2 "设置 UI 横置"这个猜测：不是它

`SETTINGS_SHIM_JS` 只对**直板机**把设置导航改成横向胶囊条（`html.dshm-phone`）。
我们的分区与「内置插件」走**同一个** `settings.section` 槽位、由官方 React 一起渲染 ——
横向条里被挤掉的话「内置插件」也会一起消失，而用户看到的是"平板有、手机没有云同步"。
⇒ 与布局无关，问题在"这个分区压根没注册/没桥"。

### 1.3 真正的第二层原因：`phone` 那条原生壳里没有云同步

`319` 只改了 `entry`（PC / 平板）的桥与面板。而 `phone/src/main/ets/pages/WebApp.ets`：

- `methodList` 里**没有** `cloudSyncState` / `cloudSyncAction`；
- 整个 `phone` 模块 `grep` 不到 `SyncEngine` / `CloudSyncSettings`；
- 同步中枢当时住在 `entry/src/main/ets/sync/`（entry 私有目录），手机壳**结构性**拿不到。

截图与日志都指向同一个结论：**手机端缺的不是 UI，是能力本身。**

## 2. 修法：把云同步收成**跨壳共用的一份**（platform）

```text
platform/src/main/ets/
  sync/            ← 2026-10-30 从 entry/src/main/ets/sync/ **整体搬入**
    SyncEngine.ets      同步中枢（登录态 / 开关 / 上传 / 拉取导入 / 插件恢复）
    SyncModel.ets       统一 unit 与任务状态机（纯数据，可离线门禁）
    SyncStore.ets       同步表 + 端云同步 + Asset
    SyncPlanner.ets     传什么（排除面 / 工作区稳定 ID）
    UploadRunner.ets    怎么传（五阶段进度）
    ImportRunner.ets    拉取与六道闸导入
    PluginManifest.ets  插件清单
    PluginRestore.ets   插件恢复
    SyncActions.ets     ★ 新增：动作判定（login/signout/enable/disable/upload/pull/restore）
    SyncState.ets       ★ 新增：状态快照 JSON + SyncRoot（会话根/profile 目录）
    SyncLauncher.ets    ★ 新增：拉起承载页并请求"落地即弹登录"
  view/CloudSyncSettings.ets  ← 原生面板（官方 LoginPanel 只能渲染在页面里）
  ui/Tokens.ets               ← 设计令牌（从 appstate 搬来，见 §2.3）
```

### 2.1 为什么搬到 platform

`entry` 与 `phone` 是两个 HAP，**都依赖 platform**（`oh-package.json5` 里就有）。
把中枢放进 platform，两个壳拿到的是**同一份实现**：

| 面 | 收口后 |
|---|---|
| 状态 JSON 的形状 | `encodeCloudState()` 一处（字段名/口径不可能两端漂移） |
| 动作受理与拒绝文案 | `decideCloudAction()` 一处（"点了没反应"这类问题不会只在一台设备上出现） |
| 会话根 / profile 目录口径 | `SyncRoot.attach()` 一处（拼错一层只会显示 0，不会报错） |
| 登录面板 | `openCloudPanelWithLogin()` 一处（参数键 `autoLogin` 两侧同源） |

### 2.2 手机壳补上的三件事

1. **桥**：`cloudSyncState()` / `cloudSyncAction(action)`（`methodList` 同步登记）；
2. **面板**：`CloudSyncSettings` 挂到页面浮层（点"登录"/"恢复插件"时出现）；
3. **设置入口**：`CLOUD_SETTINGS_ITEM_JS` 注入垫片（与 `entry` 同一份，含 `MutationObserver`
   抗重渲染 —— `docs/318` 的教训）。

「落地即弹登录」的链路：`startAbility(pages/WebApp, {autoLogin:true})` →
`EntryAbility.applyLaunchParams()` 解析后写 AppStorage（与快捷方式动作 `dshAction` 同一套做法）→
页面 `aboutToAppear` → `consumeCloudLaunchParams()` 读一次、**用完即清**。

### 2.3 两个被搬动的公共件（都有硬理由）

| 件 | 从 → 到 | 为什么 |
|---|---|---|
| 设计令牌 `Tokens.ets` | `appstate/ui/` → `platform/ui/` | platform **不能反向依赖 appstate**（appstate → platform 已是既成方向），而共享面板要用 `Sp/Fs/Radius/Sz`。appstate 侧改成再导出，调用点零改动 |
| 云同步中枢 `sync/` | `entry/sync/` → `platform/sync/` | 见 §2.1 |

> 同时把 `SyncEngine` / `SyncPlanner` 里 `from 'platform'` 的自引用改成相对导入，
> 把 `SyncLauncher` 里的计算属性名 `{ [KEY]: true }` 改成逐条赋值 —— ArkTS 规则
> `arkts-identifiers-as-prop-names` 禁止前者（编译期就会 FAIL）。

## 3. 更名「鲸鸿」与换标（`Desktop/logo.png`）

### 3.1 品牌素材管线（**零第三方依赖**是硬要求）

本机 **没有 Pillow / numpy**：PyPI 没有 openharmony-arm64 的轮子，源码装 numpy 在引导期失败（实测）。
旧 `make-icon.py` 依赖这两件 ⇒ 换标时**跑不起来**。因此：

- 新增 `tools/lib/tinypng.py`：纯标准库 PNG 读写（8 位 RGBA/RGB/灰度/调色板 + tRNS）、
  **预乘 alpha** 的面积平均降采样 / 双线性升采样、RGBA 合成、抠白；
- 新增 `tools/make-brand-master.py`：从源件生成母版（见下两条硬约束）；
- 重写 `tools/make-icon.py`：不再需要 PIL/numpy，产物从 12 件扩到 **16 件**（补 phone 侧与 Agent 图标）。

**白底源件抠白的两条硬约束**（第①版做错了，是看了渲染预览才发现的）：

| # | 约束 | 做错会怎样 |
|---|---|---|
| ① | 只从**画布四边泛洪**抠"连通的背景白"（每通道 ≥248） | 按"离白多远"一刀切 ⇒ **鲸身内侧的浅蓝面被挖成透明洞**（白底上看不出，深色底上是个洞） |
| ② | 环内 / 鲸身与环之间的**封闭白**是原画留白，必须保持不透明 | 同上，光环圈里会透出底色 |

> ①的效果：墨迹 bbox 从 1139×602 变成 1144×671（差的那部分是原先被误挖的鲸肚与环内）。

### 3.2 重新标定（换标必做）

| 判据 | 旧（虎鲸） | 新（鲸鸿） | 处置 |
|---|---|---|---|
| 母版墨迹 bbox | 757×634 | **757×444** | 口径不变（长边占画布 0.739） |
| 前景体积 | 59.3KB | **55.6KB** | 带改 15–400KB |
| 托盘外接框 | 62×52 | **62×36** | `TRAY_BBOX_H` 改 36（62 ÷ (757/444) ≈ 36.4） |
| 托盘框内留白 | 46.5% | **40.2%** | 判据仍 >30% |

### 3.3 用户可见的品牌名（逐处）

| 位置 | 改前 → 改后 |
|---|---|
| `AppScope/.../string.json` | `app_name` DSHM → **鲸鸿**；`app_name_beta` DSHM beta → **鲸鸿 beta** |
| entry / phone 的中英 `string.json` | 应用名、模块描述、托盘提示（鲸鸿正在运行 / Jinghong is running）、会话卡片、会话窗体名、A2A 描述、联网权限理由 |
| `AboutPanel`（关于页） | 「鲸鸿（HarmonyOS 客户端）」「鲸鸿应用与鸿蒙适配：MIT License…」 |
| `Index.APP_NAME` | 诊断报告抬头 |
| `StatusBarTray` | 托盘菜单标题、悬停提示兜底文案 |
| `UsageCard` / `StartNewSessionImpl` | 卡片标题、意图关键词 |
| `dshcompat/WebBrand.ets` | 侧栏品牌名 `content:"鲸鸿"`、文档标题把上游产品名替换为「鲸鸿」 |
| `tools/check-brand-surface.mjs` | 判据改成常量 `BRAND_NAME='鲸鸿'`（换名不必再改断言；自检臂同步） |

**故意没改的**：`com.dshm.dshclient`（包名）与 `DSHM.db`（同步库文件名）。前者一改就是"卸载重装 ⇒
用户数据迁移"，后者改名等于让已同步的数据"消失"。两者都不在用户可见面上。**这一步要你拍板**（§6）。

## 4. 开屏动效：`curves.springMotion`

旧写法是**固定时长补间**（淡入 `Curve.Friction` 640ms、呼吸 `Curve.EaseInOut` 1800ms）。
现改为物理弹簧（两壳同一口径）：

| 用途 | 参数 | 取法 |
|---|---|---|
| 品牌标淡入 | `springMotion(0.42, 0.86)`，delay 80ms | `response` 0.42s（一次完整振荡），`dampingFraction` 0.86 略欠阻尼 ⇒ 落定有极轻一下"弹到位" |
| 常驻呼吸 | `springMotion(0.62, 0.62)`，`iterations:-1` + `Alternate` | 明显欠阻尼，往复带惯性与过冲 |

- SDK 原文：弹簧曲线**没有 duration**（"duration depends on the springMotion parameters and the
  previous velocity, rather than the duration parameter"）⇒ 代码里不再传 `duration`；
- 不用 `springCurve(velocity, mass, stiffness, damping)`：SDK 标 `@deprecated since 9`；
- **进度条不吃弹簧**：它仍是匀速线性（用户对"冲"的反馈见 `docs/277`），弹簧只用于品牌标本身；
- 手机壳原先**没有淡入**（只有呼吸）⇒ 补 `brandOpacity` + `markOpacity()`，否则同一个应用在两台设备上
  "手感不同"。

## 4.1 出包前抓到的一个真缺陷：共享面板引用了别的模块的资源

`CloudSyncSettings` 搬进 platform 后，`LoginPanelParams.appInfo` 里仍写着

```ts
appIcon: $r('app.media.layered_image'),
appName: $r('app.string.EntryAbility_label')
```

`$r('app.…')` 只能解析**本模块**的资源；platform 与 hostruntime 这条编译链里没有 entry 的
`app.string` / `app.media` ⇒ 全量 `assembleApp` 报 `10903329 Unknown resource name`。

**修法（顺带把换名也收成一处）**：

| 资源 | 位置 |
|---|---|
| 品牌名 | `platform/src/main/resources/{base,en_US}/element/string.json` 的 `brand_app_name`（鲸鸿 / Jinghong） |
| 品牌图标 | `platform/src/main/resources/base/media/brand_icon.png`（由 `tools/make-icon.py` 产出，与启动页大标识同图） |

> 这就是"编译过了不等于能出包"的实例：单模块 `assembleHap` 只编 entry/phone 自己的树，
> 不会编 hostruntime → platform 那条链。**改 platform 必须用 `assembleApp` 复核**。

## 4.2 审核轮（2026-10-30 第三轮，出包前）补的三处

| # | 发现 | 处置 |
|---|---|---|
| 1 | **真缺陷**：手机壳「落地即弹登录」只在 `aboutToAppear` 消费一次；`launchType: specified` 下应用**在前台**时点「登录」走 `onNewWant`，页面不重建 ⇒ 点了没反应 | 补齐三层消费（与 `dshLaunchAction` 同范式）：`@StorageProp+@Watch('onCloudAutoLoginChanged')` + `onPageShow` 再消费一次；消费逻辑复用同一函数，幂等 |
| 2 | **门禁假红**：`check-handheld-back` 的对照臂用 "', 'requestSystemBack']"（末项形态）做变异锚点，本轮 methodList 追加云同步方法后锚点失配 ⇒ 臂"没生效"判红 | 锚点改成删**名字本身**（不假设位置），且锚点失配时**显式抛错**（宁可吵，不悄悄漏判）；修后 45 正例 + 6 臂全过 |

## 6. 要你拍板的两件事（我没擅自做）

1. **包名 `com.dshm.dshclient` 保持不动**。改包名 = 系统视为另一个应用 ⇒ 必须卸载重装 ⇒
   用户会话 / 插件 / 工作区要迁移（`docs/243` 那套）。要不要做、什么时候做，你定。
2. **同步库文件名 `DSHM.db` 保持不动**。它是端云同步的本地表名（AGC 云侧已按这个库同步过数据）；
   改名等于让云端旧数据"对不上号"。若一定要改，需要配一次数据迁移。

真机验收清单：`319` §6（云同步能否出现/操作）+ 本节新增三项：
开屏动画是否顺滑回弹、桌面图标/名称是否已是「鲸鸿」、手机设置里是否出现「云同步」。
