## 1. 实测状态

```sh
devecocli auth status
# Current user: So****          （默认 auth source：已登录）

DEVECO_CLI_AUTH_SOURCE=deveco-code DEVECO_CODE_AUTH_DIR=/tmp/emptyauth devecocli auth status
# Not logged in                 （deveco-code 源读的是另一份凭据）

devecocli device list
# HUAWEI MateBook 14  127.0.0.1:45595  device  2in1
```

结论：

- **设备回环可用**：MateBook 14 2in1（API 26）在线，可直接 `install -r`。
- **登录状态取决于 auth source**：
  - 默认 source：已登录 ⇒ `signature generate` 可用；
  - `DEVECO_CLI_AUTH_SOURCE=deveco-code`：`Not logged in` ⇒ 若在该环境执行 `signature generate` 会报
    `Run devecocli auth login to sign in`。
- 这也解释了双方看到的分歧：同一台机器、不同 `DEVECO_CLI_AUTH_SOURCE`。

## 2. 与构建的关系（重要）

| 动作 | 是否需要登录 |
|---|---|
| `devecocli build --product default` / `--product phone` | **不需要** |
| `tools/build-beta.mjs`（canonical Beta） | **不需要**（用仓库内 debug 物料） |
| `tools/build-agc.mjs`（AGC） | **不需要**（用仓库内 release 物料） |
| `devecocli signature generate`（local-install 重签） | **需要** |

实测（2026-11-18）：`DEVECO_CLI_AUTH_SOURCE=deveco-code` + 空 auth dir 下，
`signature generate` rc=1，而 `devecocli build --product default` rc=0 / BUILD SUCCESSFUL。

## 3. 为什么本轮没有直接出 local 包

按 `AGENT-HANDOFF.md` §3.3，local-install 需要**临时改写并逐字恢复 16 个身份文件**，其中包含：

```text
AppScope/app.json5
build-profile.json5
entry/src/main/ets/entryability/EntryAbility.ets
entry/src/main/ets/...（资源与 module.json5）
hostruntime/src/main/ets/runtime/NodeRuntime.ets
hostcore/app/dshm-installer.js
phone/src/main/resources/...
```

而 JD 硬规则是"不要动 WorkBuddy 正在改的源码"；`JD/STATUS.md` 也把 JD-003 写成"解除后由 WorkBuddy 出包"。
当前 WorkBuddy 仍在改 `hostcore/plugins/dshm-vm-bash/lib/terminal.js`（工作树 `M`），
本机也没有文件锁能保证 16 文件的"替换 → 构建 → 恢复"窗口内没有并发写入。
**为避免把对方的在途改动卷进 beta 身份窗口，本轮不出包。**

## 4. 解除阻塞的做法（二选一）

1. **WorkBuddy 出包**：确认 `devecocli auth status` 在其会话 shell 里是已登录（必要时
   `unset DEVECO_CLI_AUTH_SOURCE` 或显式 `devecocli auth login`），按 §3.3 执行；DevEco 只做包结构核验。
2. **DevEco 出包**：用户/WorkBuddy 明确"当前无并发写码"，DevEco 再执行 §3.3 的 16 文件备份 →
   构建 → 恢复 → `hdc install -r`（HSP → HAP）→ 冒烟。

两种做法都必须遵守：只覆盖安装、不卸载；出包后 16 文件按 MANIFEST 逐字还原并重跑 `place-host-app`。
